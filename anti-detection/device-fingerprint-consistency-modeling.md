# 设备指纹一致性建模：联合分布、时间间隔与生命周期

> 来源: 方法论整理（设备指纹一致性建模）
> 原始发布时间: 2026-09-15
> 归档日期: 2026-09-15
> 分类: 反检测/风控对抗 — 设备指纹一致性建模
>
> 服务端审查设备指纹，看的不是某几个字段单独像不像，而是字段之间的联合分布、时间间隔的统计形态，以及多次采集之间的状态演化。把真实指纹拿来抖动几个字段，联合分布和时序一对照就会露馅。本文只整理识别面与建模原则，不收录生成代码、设备 ID 原值或可打生产的改机脚本。

本文不是改机手册，也不给生成器实现。看懂原则不等于能做好；作者自己也认为这套还粗糙，不够现代化。硬锚点（Widevine `deviceUniqueId`、Key Attestation、Play Integrity）不在本文范围内。

## 核心判断

设备指纹侧的关键不是「随机化」，而是 **一致性建模**。

服务端不会因为你是某个特定机型就一票打死，也不会因为开了 VPN 就一定判死（少数场景会）。它综合看这套字段能不能交叉印证成一个普通用户。单点危险分可以很高，但往往罪不至死；真正致命的是整机画像在联合分布上不像真人设备。

常见失败路径：拿一批真实指纹，对若干字段做均匀随机或小幅抖动。字段各自「看起来合法」，联合起来却对不上。服务端算法吃的就是这种不一致。

## 1. 联合分布，不是单字段真假

服务端审查指纹质量时，不会只核某几个字段对不对。它看的是字段之间的 **联合分布** 是否合理。交叉印证过关，这套指纹才像普通用户。协议还原和改机做不好，经常卡在这一层，而不是某个 `Build.*` 写错。

典型不一致：

| 现象 | 为什么不像真人 |
|------|----------------|
| 骁龙 8 Gen 3 机型，ROM `build` 时间停在几年前 | SoC 世代和系统发布时间对不上 |
| APK 里 OkHttp 已经很新，核心安全 SDK 还停在两年前 | 依赖库版本和安全 SDK 版本没有沿同一条升级路径走 |
| 开机时间晚于注册时间 | 时序因果反了 |
| 开机后 30 秒内走完下载、安装、注册 | 人类行为间隔不会这么齐、这么短 |

机型本身、出口是不是 VPN，都只是危险分的一部分。综合判定「这台设备很不正常」，靠的是多字段互相打脸。推荐目标仍是跟普通人同一套联合分布，而不是在单字段上赌「服务端不看这个」。

`hardware-fp` 解决的是 **同一条 catalog 行内部** 的 SoC / GPU / 内存 / 核数 / 分辨率 / 年份绑定。它不自动保证 ROM 发布时间、APK 依赖、安全 SDK、开机与注册间隔也在同一条故事线上。

## 2. APK 自身也是指纹面

很多人只盯 `Build.*`、`Settings.Secure` 这类系统字段，忽略 APK 自己也会被风控 SDK 采集：

- APK 版本号、`versionCode`、签名证书、渠道信息
- 打进包里的第三方库版本：OkHttp、Retrofit、Protobuf
- 核心安全 SDK 版本：`sgmain`、阿里安全、腾讯御安全；每次升级都会改采集逻辑和上报字段
- 资源文件、`assets`、DEX 常量、字符串表，以及某些硬编码配置

一个 App 升级过程中，核心安全 SDK 往往 **在某一个 versionCode 突然跳版本，然后沿用很久**。包很新、安全 SDK 很旧，或反过来，都是联合分布上的异常。做协议或改机时，系统画像和 APK 自身画像要当成同一套指纹的两面，不要只改系统字段。

落地时先按目标 App 收一批历史 APK，抽版本族上的证书、渠道、依赖库和安全 SDK 版本，再谈系统字段。不要对单个 APK 拍脑袋填版本串。

## 3. 时间间隔用右偏分布

开机时间、安装时间、注册时间之间的间隔，不能均匀随机。真实用户的行为间隔是 **右偏** 的：大量短间隔，加上一条长尾。均匀分布会造出「太整齐」的序列，广告等强风控场景里这是最基本要避开的形态。

| 分布 | 适合描述什么 | 用在指纹里的位置 |
|------|----------------|------------------|
| 均匀分布 | 每个间隔等概率 | 不适合当间隔主模型；序列太整齐 |
| 泊松分布（间隔对应指数分布） | 单位时间内事件发生次数 / 随机到达 | 登录、前台、关键行为这类「随机到达」 |
| 对数正态分布 | 多个独立因素相乘得到的总时长 | 开机到安装、安装到注册这类受多因素影响的间隔 |

约束先于采样：

```text
开机时间 < 安装时间 < 注册时间
```

间隔本身再按真实数据的分布采样，而不是先随机三个时间戳再排序。均匀随机区间、随手 `sleep` 一个整数秒，都只是勉强能跑的占位，不是这一层的模型。

工程上这一层适合收成可复用采样器：按间隔类型取样，自动满足先后约束。调用面接近一次等待，不必每次手想「随机多久看起来像人」。本文不给实现；没有真实间隔语料就标 `insufficient-evidence`，不要用均匀分布冒充已建模。

## 4. 静态字段之外的动态信号

现代风控还会采时间序列，而不是只看注册那一帧静态表：

- 传感器噪声：加速度计、陀螺仪的微小偏差
- 触摸屏采样特征
- 电池充放电曲线
- 网络 RTT / 路由特征
- GPU 渲染指纹

静态字段可以改。传感器噪声、触摸采样节奏、电池放电、网络抖动来自硬件和物理环境，是「天然随机性」。SDK 可以在后台静默采成一条时间序列。设备在这些维度上 **太干净** 或 **太一致**，本身就是标记。

这一层的语料来自大量真实采集，再统计噪声分布或变化曲线，而不是对静态字段再抖一次。没有曲线语料，就不要声称动态信号已对齐。

## 5. 指纹是有状态对象

设备指纹不是注册那一刻生成一组字段之后就不管了。风控会多次采集：

- 注册时一次
- 登录时一次
- 使用过程中定期一次
- 支付、改密等关键行为再一次

多次采集之间有强关联：

| 维度 | 多次采集时应该怎样 | 异常形态 |
|------|--------------------|----------|
| 硬件字段 | 基本不变 | 中途换 SoC / 型号 / 屏幕 |
| 传感器噪声 | 同一套统计特征 | 每次采集换一种噪声分布 |
| 电池曲线 | 连续，充放电模式可解释 | 满电跳到另一套充放电模式 |
| 开机时间 / 运行时长 | 单调递增 | 倒退 |
| APK 版本 | 可以升级，路径要合理 | 新版本跳回旧版本 |

每次采集都重新随机一套，或前后字段互相矛盾，时序一致性检验很容易抓住。指纹应建模成 **有状态对象**：从出生到退役有生命周期，每次采集是在当前状态上做合理演化，而不是重新生成。

上量失败经常被归因到签名，实际是同一设备在第二次、第三次采集时自己打了自己的脸。包顺序见 [设备注册包顺序](../mobile-app-reverse/protocol-register-packet-order.md)；这里多出来的是 **同一身份跨请求的状态连续性**。

## 6. 分层装配的概念方案

先把语料分层，再按绑定关系装配，而不是把几百条扁平指纹随机挑一条再抖动。

```text
硬件 catalog 行
    │
    │  1 : N（一台机器多套 ROM，含 OTA）
    ▼
ROM / build 族
    │
    ├── APK 版本族
    │     证书 / 渠道 / OkHttp 等依赖 / 核心安全 SDK
    │     安全 SDK 常在某个 versionCode 跳变，然后沿用很久
    │
    ├── 内核相关
    │     与硬件绑定的编译/内核字段
    │     开机时间：可采样，但必须和注册时间拉开，服从右偏分布
    │
    └── App 初始化
          文件创建、进程信息、安装时间
          分析清楚启动后才出现的字段之后，这一层相对好对齐
```

生成时的顺序是绑定，不是抽卡：

1. 从硬件指纹库抽 **一套** 合适的 catalog 行（SoC / GPU / 内存 / 屏幕同一行）。
2. 在该硬件对应的 ROM 集合里选一套；硬件到 ROM 是一对多，含更新，不要跨硬件借 ROM。
3. 针对目标 App 收一批历史版本，抽每个版本的证书、渠道、OkHttp / Retrofit / Protobuf、核心安全 SDK 版本，按升级路径选，而不是混版本。
4. 内核字段能跟硬件绑定的就绑定；开机时间按分布采样，并满足与安装 / 注册的间隔约束。开机后一分钟内下载完 App 再注册完，是异常，不是「效率高」。
5. App 初始化字段先对照真实启动路径，再填；不要在注册包里提前出现启动后才有的文件或进程态。
6. 把上面五层收成一个有状态对象。后续登录、定期采集、支付采集只做演化：硬件不动，噪声统计特征保持，电池连续，uptime 递增，APK 只允许合理升级。

连续一致性有的可以直接对照手机 SDK 自己的更新逻辑，有的必须靠自己采到的时间序列。没有语料就停在该层 `insufficient-evidence`。

## 边界

- 本文只整理风控识别面和建模原则。生成算法、采样器实现、传感器曲线合成、可打生产的改机脚本都不收录。
- Widevine `deviceUniqueId`、Key Attestation、Play Integrity 是硬锚点，见 [ACE deviceUniqueId](./android-ace-deviceuniqueid.md)。一致性建模解决不了 TEE 派生身份。
- `hardware-fp` 禁止 hybrid；本文同样禁止跨机型借 ROM、跨 APK 版本借安全 SDK、跨生命周期重随机。
- 均匀分布、字段级抖动、单次采集后丢弃状态，都视为未建模。
- 动态信号没有真实曲线语料时，不得把静态字段对齐写成「指纹已完成」。
- 作者认为这套仍粗糙，不够现代化；当作讨论起点，而不是已闭合的生产方案。

## 速查

| 点 | 结论 |
|----|------|
| 关键动作 | 一致性建模，不是随机化 / 抖动真实指纹 |
| 服务端看什么 | 联合分布、交叉印证、时序、多次采集演化 |
| 系统字段不够 | APK 版本、证书、依赖库、安全 SDK、资源与 DEX 常量也是采集面 |
| 时间间隔 | 右偏（泊松 / 指数、对数正态）；`开机 < 安装 < 注册` |
| 动态信号 | 传感器噪声、触摸、电池、RTT、GPU；太干净也是异常 |
| 生命周期 | 有状态对象；每次采集是演化，不是重新生成 |
| 装配顺序 | 硬件 → ROM（1:N）→ APK 版本族 → 内核/开机 → 初始化 → 状态演化 |
| 完成口径 | 单次字段能对拍 ≠ 联合分布合理 ≠ 多次采集连续 |
