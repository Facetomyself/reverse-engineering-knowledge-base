## 正文

> 本文仅做技术方法论分享,目标信息已脱敏处理,不提供可直接使用的完整实现,请勿用于未经授权的用途。

某短视频平台的接口请求上带着一个签名参数a_bogus,算法藏在一台自定义的栈式字节码虚拟机里,里面塞了SM3双哈希、一个改过初始化方式的RC4、外加一层可逆的位混淆。拆开来看每一层都是标准算法配了个不一样的常量,没有一处是真正意义上的自研密码学。

拆完这套VM才发现,这不是真正卡门的那一关。请求上还带着另一个签名参数,算法只是最普通的MD5,输入是几段拼起来的字符串加一把写死的密钥。抓包比对下来,真正决定请求能不能通过的是这一个,不是费了大力气逆清楚的a_bogus。

VM的字节码不在明文JS里,是塞进一段伪装成zip文件头的base64数据块,运行时才解包成字节码,静态直接搜索算法特征找不到东西。这台VM结构上完全反汇编清楚,常量池、函数表、77种指令全部读通,离线复现的密文和真实抓包逐字节一致,还找到一份独立的公开参考实现做过交叉核对。

##  环境

签名逻辑挂在一个fetch拦截器上,请求发出前先算好参数拼进URL。请求上一共有好几个跟身份相关的参数:一个是本文主要拆的这个,VM算出来的,另一个是接下来会讲到的、真正卡门的那个;此外还有几个存在cookie里的会话令牌,由服务端下发,不是能算出来的。

##  工具

本文用到的动态观测,靠cc配合自研的Chromium魔改版运行时追踪工具vmtrace完成,未开源。

##  加密流程

###  三层外壳:从伪装的zip头到字节码

签名脚本本身是压成一行的混淆代码,算法相关的字符串一个都不明文出现,连编解码用到的两个函数在全文里都只各自出现一次。真正的算法数据是一大段base64字符串,解码后开头几个字节故意伪装成zip文件的文件头,想让人以为这是个压缩包资源。

往下剥三层:


    raw       = base64_decode(伪装zip头的数据块)checksum  = sum(raw[4:8]) % 256 # 从固定位置的4个字节算出一个校验值key       = checksum # 当异或密钥plain     = [b ^ ((key + key%10*i) % 256) for i,b in enumerate(raw[8:])]bytecode  = raw_deflate_inflate(plain) # 标准deflate解压,得到最终字节码流

三层壳全靠静态分析就能剥完,不需要跑代码。

###  自定义栈式VM怎么读指令


字节码流开头是两段用变长编码写的数据:


    W()  = 读一个signed LEB128变长整数K()  = 读一个UTF-8变长字符串(先读长度再读内容) 常量池 Z = [ K() 重复 W()次 ] # 1001项,清一色明文字符串函数表 z = [ {参数个数,局部变量数,异常表,字节码} 重复 W()次 ] # 796个函数

把整段字节码流按这个结构解析,精确吃完一个字节不剩,说明结构读对了。

VM解释器本身是一个栈式的执行循环,大致形状:


    function X(t, r, e, n) {  var v = [], p = -1;              // 操作数栈 + 栈指针  var o = 当前函数字节码, a = 0;    // 字节码 + 程序计数器(pc)  for (;;) {    var op = o[a++];               // 取一条指令    handlers[op](v, p, o, a, Z);   // 按opcode查表执行,77种指令之一  }}

反汇编器覆盖了全部77种指令,796个函数没有一个反汇编不通过,说明这张指令表是准的。

###  完整算法流程

先看整条链路怎么走,再逐段拆细节:


    query / body / UA   │   ├─ SM3(SM3(query + 固定盐))  ──────→ params_code(2字符,随query变)   ├─ SM3(SM3(body  + 固定盐))  ──────→ method_code(2字符)   ├─ SM3(RC4(UA)编码后)        ──────→ ua_code(2字符)   ├─ Date.now() 按小端拆开的时间戳字节   ├─ 屏幕分辨率/UA拼出来的固定环境字符串   └─ 请求计数器分桶值        │        ▼   按固定字段顺序拼成一个中间结构,再按一张固定的重排表打乱位置        │        ▼   inner主体(50+字节)        │                    ┌─ 8字节前缀(几个标志位+随机源混合而成)        ▼                    │   4:3可逆位混淆(见下节) ───────┘        │        ▼   ^ 改过的RC4密钥流(见下节)        │        ▼     string_2        │      ┌─ string_1(4字节:魔数+浏览器码+随机,见后文)        ▼      ▼   string_1 + string_2        │        ▼   base64(自定义码表)        │        ▼      a_bogus

这条链路里,真正随请求变化、每次都要重新算的只有三处哈希和时间戳;屏幕分辨率、UA这类环境信息采一次能反复复用;掩码、密钥、码表这些常量全程不变。8字节前缀这一处最容易漏,它和后面的位混淆主体拼在一起才是完整的编码输入,单独拆位混淆那一层很容易把它当成主体的一部分而不自知。

###  a_bogus核心算法:标准算法配了不一样的常量,不是自研算法

VM里那个看着最复杂的哈希函数,拆开之后是标准SM3算两次:


    h1 = SM3( 请求路径 + <固定盐,写死在VM常量池里> )h1_hex = hex(SM3(h1))params_code = h1_hex[9] + h1_hex[18] # 取双重哈希十六进制串里两个固定位置的字符

固定盐的具体内容不在这里展开,方法论上说清楚一件事就够:算法本身没有任何魔改,输入前面掺进去的那一小段固定字符串才是让人一开始按标准SM3去对总是对不上的原因。

反爬这类保护最常见的做法就是这样:标准算法一字不改,悄悄改一个输入常量或者取值位置,静态先去常量池里翻有没有可疑的固定字符串,往往比一上来就怀疑算法本身被魔改更快。

###  可逆位混淆:看着像加密的编码层

签名payload组装过程里有一段处理,乍看像是某种加密,拆开之后是一种可逆的位混淆:


    输入:  真实字节 inp0, inp1, inp2   +   一个随机字节 rnd输出:  4个字节 o0, o1, o2, o3 o0 = (rnd & 掩码A1) | (inp0 & 掩码A2) # 掩码A1和A2互补,刚好覆盖8个比特不重叠o1 = (rnd & 掩码B1) | (inp1 & 掩码B2)o2 = (rnd & 掩码C1) | (inp2 & 掩码C2)o3 = (inp0 & 掩码A2') | (inp1 & 掩码B2') | (inp2 & 掩码C2') # 纯数据,不含随机 还原: inp0 = (o0 & 掩码A1) | (o3 & 掩码A2') # 丢掉随机源贡献的位,留下真实数据位

每3个真实字节配1个随机字节,组合成4个输出字节。真实数据的比特位和随机源的比特位被拆开分布到不同的输出字节里,第四个输出字节比较特殊,只由三个真实字节里各自的一部分位拼成,不含任何随机成分。

要复原真实字节,只需要知道这套掩码怎么分配的,把每个输出字节里属于随机源的那部分位丢掉,剩下属于真实数据的那部分位重新拼回原始字节。具体的掩码取值不在这里展开,概念上这就是一种代换式的可逆编码,不是不可逆的加密。

###  一个改过初始化方向的RC4

VM里另外还带着一个改过的RC4:


    标准RC4 KSA:                              这里的KSA:  S[i] = i        (顺序初始化)              S[255-i] = i     (倒序初始化)  j = (j + S[i] + key[i%len]) % 256         j = (j*S[i] + j + key[i%len]) % 256   (多插一次乘法) PRGA(生成密钥流那一步):标准,没有改

密钥本身是写死的一个字节,具体值不在这里展开。

这类手法在其他短视频类目标的签名里也见过:挑一个标准算法里非核心但足够敏感的环节动一刀,算法名字对得上、跑起来却对不上标准实现的输出。

##  真正卡门的不是这个参数,是旁边那个签名(名字太长简化成"x-secsdk")

VM这条链全部拆完、离线复现的a_bogus和真实抓包逐字节一致之后,拿离线算出来的值去请求真实接口,发现请求并不总是被接受,规律不在a_bogus本身对不对。

进一步做抓包比对才定位到:请求上还带着另一个签名参数,这个参数才是服务端真正独立校验的门槛。

###  反汇编读出真正的门

这个参数背后也是一台独立的字节码VM,算法比a_bogus那台简单得多,反汇编出来的分派表节选:


分派表不是靠猜出来的。VM内部用一个巨大的switch语句做分派,每个case编号对应一条指令,直接从switch语句里逐条读出case编号和指令的对应关系,比反复试错猜表准得多。

这里就吃过一次亏:早期按经验猜过一版表,漏掉了"读闭包捕获变量"这一条指令,漏掉的编号后来被别的指令复用,导致某个关键位置被错误标注成"无效指令",一直卡在这个位置上。换成直接读switch语句里的真实对应关系之后,这条路径立刻打通,入口函数才反汇编得出来。

对着这张表把入口函数反汇编出来,能读出一段很干净的逻辑:构造一个4项数组(会话标识、时间戳、密钥、参数拼接串),逐项用下划线拼成一整段字符串,过一次标准MD5,再转成十六进制字符串写进请求头。整个过程没有分支也没有额外处理,是这两套算法里最直白的一段:


    x-secsdk = MD5_hex( 设备/会话标识 + ”_” + 秒级时间戳 + ”_” + <固定密钥,写死在代码里> + ”_” + params.join(”&”) ) params = 这次请求全部查询参数,按原始URL编码形态”k=v”顺序拼接(不做URL解码)

几段字符串用固定分隔符连起来,整体算一次标准MD5,就是这个参数的值。密钥具体是什么不在这里展开。

###  两个参数的分量差距

两个签名参数摆在一起对比,差距很直观:


这个参数覆盖的是整条查询字符串,包括a_bogus在内。也就是说,a_bogus本身的具体内容并不参与服务端这一层独立校验,真正被校验的是"这次请求的所有参数拼起来,和后面这个签名对不对得上"。

类似的结构在其他短视频类目标身上也见过:一个看起来复杂的参数经过千辛万苦逆清楚,结果服务端真正卡的是覆盖面更广的另一个更简单的签名。算法上的复杂程度和它在整条校验链里的重要程度,不是一回事。

##  那段"指纹"字节,其实是查表算出来的常量

签名payload里有一段字节,一开始被当成某种设备指纹:字节内容确实每次请求都不太一样,看起来像是从canvas绘图、WebGL渲染这类真实硬件特征采集来的。

定位到这段字节的生成函数之后发现不是这么回事:


    指纹字节 = floor(random() * N) + 浏览器偏移量[当前浏览器] 浏览器偏移量 = { Chrome: <值1>, Firefox: <值2>, Safari: <值3>, Edge: <值4>, ... } # 查表,不展开具体值

是一个查表映射的结果:不同浏览器对应一个固定的偏移常量,再加一个规定范围内的随机小整数,两者相加拼出来的。生成过程和任何真实硬件测量都没有关系,一张固定的对照表加一次随机数就能算出来,不需要真的用浏览器渲染任何东西去采集特征。具体的偏移对照表不在这里展开。

这一处修正提醒的是同一件事:字节"看起来像"随机的硬件特征,不等于它真的依赖硬件生成,判断依据只能是追到生成它的那段代码,不能靠字节本身的统计特性猜。

##  VM调试的三个通用坑

拆这台VM的过程中踩到二个坑,和这个目标本身无关,换一台栈式VM大概率还会踩到。

栈指针和数组长度不是一回事
。这台VM用一个独立的栈指针变量控制读写位置,弹栈操作只把指针往回移一格,并不会真的把数组末尾的元素删掉。如果观测的时候习惯性去读数组的最后一个元素,读到的其实是弹栈之后留下的残留值,不是真正的栈顶。真正的栈顶要按这个独立的指针变量去取,不能假设它和数组长度是同步的。

字节码原生序列化的数据,单步指令追踪看不到
。这台VM在处理payload字节的时候,走的是原生字符串构造函数,数据是作为参数直接传给底层构造调用的,不会经过JS层面的累加器变量。这种情况下逐指令的执行轨迹记录会看到一长串空值,不是数据真的没有,是记录方式看不到这条路径。改用直接读取解释器内部状态(栈、作用域这些)在关键节点做快照,才能拿到真实的值。

##  落地验证

算法逆出来之后先用一批真实抓包样本挨个核对,离线算出来的a_bogus和抓包里的真实值逐字节一致。另外找到一份独立公开的第三方参考实现,和这边的分析结果完全独立产出,拿这份参考实现的输出对着这边解出来的算法结构和固定数据交叉核对,常量、取值位置、算法家族全部吻合。

请求层面还确认了前面提到的结论:抓包对照下来,a_bogus这个参数的具体内容不参与服务端的独立校验,真正决定请求能不能通过的是另一个覆盖整条查询字符串的签名参数,这个参数如果和实际请求内容对不上,会直接收到签名无效的错误。除此之外,请求还需要几个由服务端下发、和设备/会话绑定的cookie令牌,这几个值拿不到自己算,只能通过一次真实会话获取。

##  小结

这个案子里最值得记的一点是"算法复杂程度"和"校验重要程度"完全不对等:a_bogus这一层塞了自定义VM、双重哈希、改过的RC4、位混淆,拆解成本很高,拆完却发现它不是真正的门;真正的门是旁边一个只用标准MD5加一把固定密钥的参数,算法简单得多。反爬设计上常见的思路是把最复杂的那层做成一个诱饵,真正决定放不放行的可能是另一个看起来朴素得多的参数。

但"不校验"和"不留痕迹"是两回事,这条边界不能混着理解。抓包能确认的只是这次请求当场没有因为a_bogus的内容被拒,这类反爬系统通常还有一层异步的风险评分,不在请求返回的那一刻生效,是事后批量分析。

字段值明显不正常,比如浏览器码和实际浏览器对不上、指纹段缺胳膊少腿,当场响应可能还是200,但这类异常值本身是个强信号,留在服务端日志里,事后可能被拿去做设备、账号或者IP层面的风险标记,跟这次请求成不成功是两套判断逻辑。同步不校验只说明这一层的门槛松,不说明这条数据没被记下来慢慢算总账。

这套方法目前只在这一个目标上验证过,遇到多签名叠加的场景,欢迎评论区聊聊你们是怎么定位到哪个参数才是真正卡校验的。
