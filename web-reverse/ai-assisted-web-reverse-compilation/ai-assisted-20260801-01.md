## 正文

rs6的P
cookie在进最外层AES加密之前,basearr要先过两道处理:一道是确定性的伪随机置换,另一道是自定义Huffman压缩。两道都是标准算法结构。

但property57的编码表一度被误判成"每会话变化、离线算不出来",原因是分析时用的源码插桩探测被站点的反注入检测识破,拿到的是一份故意喂出来的假数据。换成不碰源码的观察方式后,编码表其实是写死的静态常量。

这是fangdi
rs6逆向系列的第二篇。第一篇画过整条链路的地图,这篇往下拆链路中间那两道”打乱+压缩”的处理;codeUid公式和basearr结构留给后面两篇。

basearr组装完之后不会直接进AES,中间还夹着两道处理:LCG打乱字节顺序,再用property57的Huffman
codebook把它压缩编码,出来的东西才轮到外层AES-CBC:


    raw basearr(约150字节) → LCG生成伪随机序列 → Fisher-Yates置换,得到打乱后的字节序 → property57编码(Huffman压缩,自定义codebook) → 交给外层AES-CBC

##  加密流程

###  LCG与Fisher-Yates置换

伪随机数生成器是一个线性同余生成器:


    state = (state & 0xFFFF) * 15679 + 2531011

第898次调用后会reseed回初始种子,这个常量组合跨会话固定,两个不同会话验证过一致:


    call_count = 0def PRNG(): global state, call_count call_count += 1 if call_count == 898: state = seed # 第898次调用,悄悄重播种 state = (state & 0xFFFF) * 15679 + 2531011 return state

第一次看到这个reseed点会怀疑是不是巧合,跑两个不同会话核对之后,两边都精确停在第898次调用,不是凑出来的边界。拿这个PRNG跑Fisher-
Yates置换:


    i = 900while i > 1: i -= 1 j = PRNG() % i swap(arr[i], arr[j])

用真实种子复现整条序列,900个位置对应的920次(i,j)对全部精确命中,置换本身没有隐藏的额外扰动。

###  property57的codebook

property57是basearr进AES之前的最后一步,把字节流压缩编码成更短的位序列,压缩方式是Huffman:符号0的频率权重是36,符号255的频率权重是6,其余254个符号权重都是1。高频符号权重压得比标准Huffman常见的分布更极端,是因为basearr里字节0和255本来就大量出现(占位、填充位置),故意把它们的编码压到最短能省下不少输出长度。

用这三个频率值重建一棵Huffman树,产出的编码表和运行时真实codebook逐项比对,256个符号全部一致,取三条对照:


    符号 编码值 位长0 6 31 184 83 374 9

符号0权重最高,编码位长最短,符合Huffman"越常见越短"的基本规律,和运行时抓到的真实codebook一一对应。

编码过程本身是标准的累加器打包,完整流程写出来是这样:


    acc, accbits, out = 0, 0, []for byte in basearr: code, bits = codebook[byte] acc = (acc << bits) | code accbits += bits while accbits >= 8: accbits -= 8 out.append((acc >> accbits) & 0xFF)if accbits > 0: # 收尾不满8位 acc = (acc << (8 - accbits)) | (184 >> accbits) out.append(acc & 0xFF)

每个输入字节按codebook查到对应的编码位长和编码值,累加进bit缓冲区,凑够8位就吐一个字节;最后不满8位的部分补固定填充值184后flush。这套逻辑对不对,不看理论,直接拿真实抓包的basearr跑一遍:输出和真实property57函数的返回值逐字节相同,包括那个容易被漏掉的收尾字节。

##  codebook差点被误判成session-derived

编码表要是真的每次会话都不一样,离线复现这条路直接走不通。第一轮分析时,想直接从源码层面确认这个codebook是不是固定的,用了往源码里插桩打点、把参数dump出来的办法。插桩生效后拿到了一份"codebook",数据本身看起来完全正常,几个会话抓下来编码值真的在变。

这份数据后来发现是假的:插桩本身触发了站点的某种检测,实际执行路径切换成了一条专门喂给分析工具的decoy分支,返回的codebook看起来会随会话变化,一度被记成"session-
derived,离线不可复现"。

换成不修改源码本身的观察方式后,同一个位置抓到的才是真实数据,连续多次会话的codebook逐字节相同,跟前面插桩抓到的"每次都不一样"完全对不上。真相是property57的编码表从一开始就是确定性静态常量,之前"随会话变化"的结论完全建立在被喂了假数据的基础上。

##  落地验证

把复现的LCG、Fisher-Yates置换、Huffman
codebook和encode逻辑串起来,输入真实抓包拿到的basearr,输出和property57函数的真实返回值做端到端比对,逐字节相同。这一步验证的是整条"打乱+压缩"链路自洽,不依赖任何单点的巧合。

##  小结

这两道处理本身是标准算法,真正花时间的是分辨拿到的数据是不是真的,不是推导公式。往源码里插桩这类会改动运行环境的观察方式,一旦目标有能力识别探测行为,拿到的结果可能是精心准备的干扰项而不是错误;换一个不留痕迹的观察角度,重新验证一遍此前的结论,往往比死磕一条走不通的路更快出结果。这套方法目前在fangdi这一个目标上验证过,遇到类似的反插桩/decoy设计,欢迎评论区聊聊你们怎么分辨真假数据。
