#  某 dewuX web 签名逆向：三层签名逐字节复现，最硬的是一次五层套娃的握手

本文所有内容仅供安全研究与技术学习，目标已脱敏，站点以「某 dewuX」代称，域名、SALT、AES 母串、RC4
密钥等关键常量以占位代替，不提供成品签名器。严禁用于商业或非法用途，后果自负。


某 dewuX 的 web 站，一条业务请求身上挂了三层签名：body 里第一个键是  ` sign  ` ，请求头有个  ` hsn  ` ，另外还有一路
` data  ` 设备上报。再往上，设备凭证  ` sk  ` /  ` ak  ` 不是本地生成的，是开页时跟服务端握一次手换来的。

这一篇把这套东西逐字节复现的过程写出来，包括三个我觉得值得单独讲的点：  ` hsn  ` 是  ** 签名套签名  ** 、一个  ` grep  ` 0
命中差点让我下错结论的坑、以及最硬的一关：设备握手的响应是  ** 五层套娃  ** ，最里面还埋了个魔改 RC4。


##  一、一页纸

先把全貌摆出来，后面逐个拆：

值  |  位置  |  算法
---|---|---
` sign  ` |  body 首键  |  ` MD5(参数按 key 排序拼 key+value + SALT)  `
` hsn  ` |  请求头  |  ` MD5({requestBody, ua} 按键排序拼)  ` ，  ` requestBody  ` 是  ** 含 sign 的完整 body 串  **
` data  ` |  设备上报 body  |  ` AES-128-CBC/Pkcs7(JSON.stringify(指纹))  ` → 大写 hex，key/iv 从一个母串 substr 切出来
` ltk  ` /  ` adi  ` |  请求头  |  共用编码器  ` RC4(key) → UTF-8 → base64  `
` sk  ` /  ` ak  ` /  ` sm  ` |  头 + storage  |  服务端握手  ` /webSk  ` 下发，响应五层解密后才拿得到

载体是设备风控域下的一个单行约 515KB 的 SDK，  ` eval  ` 出来的，obfuscator.io 控制流平坦化，但  ** 不是
JSVMP  ** ，CryptoJS 的调用明文可见。同页还挂着一个第三方设备指纹（  ` sm  ` 就是它的设备 id）和一个 JS 加固（文件头自报
` JS DUN PROTECT  ` ），这两个不在本文范围。

##  二、sign 和 hsn：签名套签名

` sign  ` 是最规矩的一个：把 body 里的参数按 key 字典序排好，依次拼成  ` key1value1key2value2…  `
，末尾接一个固定 SALT，整体 MD5。


    def sign(params: dict) -> str:
        s = "".join(k + str(params[k]) for k in sorted(params))
        return md5((s + SALT).encode()).hexdigest()      # SALT 占位，32 位固定盐

` hsn  ` 有意思在它的输入。它签的不是原始参数，而是  ** 一个已经含了  ` sign  ` 的完整 body 字符串  ** ：


    def hsn(body_str: str, ua: str) -> str:
        m = {"requestBody": body_str, "ua": ua}           # requestBody = 序列化后的整个 body
        s = "".join(k + m[k] for k in sorted(m))          # 还是"按 key 排序拼 key+value"
        return md5(s.encode()).hexdigest()

也就是说复现时有  ** 严格的顺序依赖  ** ：先算  ` sign  ` 塞回 body，把整个 body  ` JSON.stringify  `
成字符串，再拿这个字符串当  ` hsn  ` 的输入。你改任何一个业务参数，  ` sign  ` 变、body 串跟着变、  ` hsn  `
又跟着变，一层套一层。

有个容易踩的细节：  ` hsn  ` 的  ` requestBody  ` 是  ** 序列化后的字符串  ** ，不是 body
对象。序列化时键的顺序、有没有空格，都得跟浏览器发出去的那条完全一致，差一个空格 MD5 就全变。所以别自己重新  ` json.dumps  `
，要用实际发出去的那个 body 串。

##  三、重定位：grep 0 命中，不代表字符串每次重编码

脚本 id 每次刷新都漂（实测 s25 → s26 → s27），所以  ** 别写死 id  ** 。这个是常识。真正让我卡了一下的是下面这个。

我上去先 grep 那几个关键常量（SALT、AES 母串、RC4 key），  ** 一个都搜不到  ** 。第一反应是 obfuscator.io
的老套路：字符串进了字符串表、每次运行重新编码，所以静态 grep 当然不中，得动态 dump。

这个结论是错的，而且会把你引向一条贵得多的路。真相很朴素：  ** 常量在源码里写成了  ` \uXXXX  ` 转义  ** ，raw grep
搜的是字面字符，当然搜不到。先 unescape 再搜，全在：


    u = re.sub(r'\\u([0-9a-fA-F]{4})',
               lambda m: chr(int(m.group(1), 16)), src)
    u.count(SALT)        # 1  ← SALT 在
    u.count(母串M)       # 2  ← AES 母串在
    u.count(ltk的RC4key) # 1  ← RC4 key 也在

** 教训：grep 不中，先怀疑常量的书写形态（转义、拆开拼接、  ` charCode  ` 还原），再去怀疑"运行时重编码"这种更贵的假设。  **
一次 unescape 能省掉整套动态 dump 的功夫。

跨会话稳定、可以拿来当锚的是  ** 结构特征  ** 而不是字符串本身：  ` AES.encrypt  ` 、  `
.toString().toUpperCase()  ` 、  ` getLtk  ` 这些调用形态每次都在。要拿运行时真值，再走零扰动断点 watch。

##  四、data 上报：AES 的 key 藏在一个母串的 substr 里

` data  ` 是设备指纹上报，  ` AES-128-CBC/Pkcs7  ` 加密一段指纹 JSON，再转大写 hex。

它的 key 和 iv 不是两个独立常量，是从  ** 同一个母串  ` M  ` 里切出来的  ** ：


    key = M.substr(5, 16)
    iv  = M.substr(10, 16)      # M 是一个 32 字符母串，占位

这里有个真会串的坑：一轮请求里，这个 SDK 同时有  ** 四个以上的 AES 在并发跑  ** ，各自用不同的母串。我一开始把设备指纹另一条 AES
路径的母串套到了  ` data  ` 上，怎么解都是乱码。  ** 同一个页面里同一个算法有多把 key，按用途分清楚，别拿这条的 key
去解那条的密文。  **

##  五、设备握手 webSk：响应是五层套娃

前面的  ` sk  ` /  ` ak  ` /  ` sm  ` 从哪来？开页时 POST 一个握手接口  ` /webSk  ` ，body 同样带
` sign  ` （复用第二节那个函数），请求头  ` dsn  ` 里带着  ` sm  ` /  ` sk  ` / SDK 版本号  ` bcv
` 这些。

难点在响应。服务端回来的是一大串大写 hex（实测 1472 个 hex 字符、736 字节），直接解怎么都不对，因为它套了五层：


    gzip（网络传输层）
      → 大写 hex 解码成字节
      → AES-256-CBC/Pkcs7 解密        （key = deNewKey1，iv = key 的前 16 字符）
      → base64 解码
      → 魔改 RC4 解密                  （key = newKey3）
      → JSON：{ "k": "<base64(sk)>", "adk": "<ak>", "sm": "<设备id>", … }

一层一层剥到最里面，  ` sk  ` /  ` ak  ` /  ` sm  ` 才现身。每一层用的 key 都不一样，下一节讲这些 key 怎么来。

##  六、魔改 RC4：标准骨架加两个整数扰动

第四层那个 RC4 是魔改过的。骨架还是标准的 KSA 加 PRGA，改动是往里注了  ** 两个整数扰动  ** ：


    c = Σ charCode( MD5(bcv).hex() )        # bcv 是 SDK 版本串
    v = Σ charCode( MD5(sk 或 sm).hex() )   # 冷启动时 sk 为空，退回用 sm

    # c % 5 决定把 v % 64 加在算法的哪一步：
    #   0 → KSA 里的 T[]      1 → KSA 里的 j
    #   2 → PRGA 里的 i       3 → PRGA 里的 j       4 → 输出字节

认这类魔改的思路，和之前写过的魔改 CRC32、魔改 SM3 是一样的：  ** 主体结构一字不动，就在某一两个固定位置注入一个和环境相关的扰动量。  **
你套标准 RC4 一定对不上，得盯着"标准算法里凭空多出来的那几个加法"。这里多出来的就是  ` c  ` 和  ` v  ` ，而且  ` c  `
还决定了扰动落在哪一步，等于用版本号给每个 SDK 版本换了套 RC4。

##  七、KDF 纯离线，和一个抗漂移的定位技巧

上面那些 key（  ` deNewKey1  ` /  ` newKey3  ` 等）由一个 KDF 从  ` (sk, sm, ua)  `
派生。逆出来是一组异或拼接：


    d = MD5(sk 或 sm 或 ua括号里的平台串)          # JS 的 || 取首个真值

    # A/B/P/F 是 SDK 里硬编码的四个母串（占位）
    XOR10(a, b)[i] = a[i] ^ b[i % 10]              # 组合子一
    XOR(a, b)[i]   = a[i] ^ b[i % len(b)]          # 组合子二
    B64U(x)        = base64(utf8(latin1(x)))

    newKey3   = B64U(XOR10(B, A))                  # 常量，跨会话不变
    deNewKey1 = B64U(XOR(newKey1, d))              # 随 d 变

关键结论：这条链  ** 唯一可变的输入是  ` sm  ` ，而  ` sm  ` 本来就在自己发出去的  ` dsn  ` 头里  **
。所以整条握手响应的解密可以完全离线完成，不用再跟服务端交互。

拿这些 key 时用了个抗漂移的技巧值得记一下。混淆后的变量名每次刷新都变，写死变量名的断点第二次就失效。但  ** KDF 输出对象的属性名是稳定的
** （  ` normalRKey1  ` 这种语义名没被混淆），于是拿属性名当内容锚下断点，断下来 dump 一次寄存器和作用域，整套派生 key
直接可见，全程不依赖任何会漂的变量名。

还做了个冷启动的对照实验：清掉 localStorage / sessionStorage / cookie / indexedDB 再
reload，连跑四次。每次服务端都发  ** 全新  ** 凭证（  ` adk  ` /  ` sm  ` /  ` sk  ` 都不同），但客户端
CryptoJS 那几把加密 key  ** 冷热完全相同  ** 。由此能推断：  ** 加密方向的 key 不由  ` sk  ` /  ` sm  `
派生  ** ，是静态母串算出来的。不用读代码，四次冷启动的 key 集一比就知道了。

##  八、验证，以及做到哪为止

验证是逐字节对的，不是"跑通了"就算：

  * •  ` sign  ` /  ` hsn  ` ：离线重算的值和真实浏览器那条请求  ** 逐字节相同  ** 。
  * • 握手：KDF 的十个输出，和断点实测值逐字节一致；  ** 两个独立冷启动会话  ** （  ` sm  ` /  ` adk  ` 全不同）各自解出的  ` adk  ` ，都和该轮实测值 byte-exact。纯 Python 复现，自带 AES，无第三方依赖。

诚实说清做到哪：  ** 我做到的是算法侧逐字节复现，以及握手响应的纯离线解密。  ** 用复现值去发真实请求拿 200
这一步我没走通，卡在一个服务端会话校验上，那属于反爬工程，不在这篇算法逆向的范围里。

最后留一条工具层面的提醒。同一轮里 AES 解密确实发生了（整条链已经逐字节验证），可我挂在加密块上的断点只记到了 203 次加密、  ** 0 次解密
** 。断点为什么漏掉解密帧我没查清，但结论很清楚：  ** 别把"断点没记到"当成"没发生"  ** ，链路验证和断点计数是两回事，以能对上的字节为准。

##  九、这一篇记住几点

  1. 1\.  ** 签名套签名  ** ：  ` hsn  ` 签的是含  ` sign  ` 的完整 body 串，复现有严格顺序依赖，且输入是序列化后的字符串，别自己重拼。
  2. 2\.  ** grep 不中先怀疑书写形态  ** ：  ` \uXXXX  ` 转义、拼接、  ` charCode  ` 都会让 raw grep 落空，unescape 一下再搜，别急着上"运行时重编码"这种贵结论。
  3. 3\.  ** 认魔改  ** ：RC4 / CRC32 / SM3 这类，主体不动、固定位置注扰动，盯标准算法里凭空多出来的加法。
  4. 4\.  ** 抗漂移定位  ** ：变量名会漂，就拿稳定的属性名 / 调用结构当内容锚，dump 寄存器一次拿全。
