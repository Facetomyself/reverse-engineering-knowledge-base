## 正文

> 本文仅做技术方法论分享,不提供可直接使用的完整实现,请勿用于未经授权的用途。

某东商品接口的签名参数h5st,由JD自研反SDK(js_security_v3_0.1.4.js)里一段VM字节码算出来。拿到CDP断点权限后,10个字段全部拆清楚:所有哈希函数共用同一套预处理编码,自定义base64是反转输出的PKCS7填充变体,固定字符串里还藏着一处专门给爬虫脚本下的拼写陷阱。离线签名器生成的h5st,真实接口测试返回200和code
0。

##  环境

h5st是某东商品接口请求参数里的签名字段,加密核心在js_security_v3_0.1.4.js这个SDK文件里,以VM字节码形式实现,内部函数全部走_$前缀命名,靠PC(程序计数器)地址索引,静态读不出逻辑。h5st本身是10个字段用;拼接的字符串:


    h5st = ts_str;nonce;fp_short;token;md5_sign;5.3;ts_ms;payload;md5_body;final_sign ts_str 20260514054600999 格式化时间戳(UTC+8, yyyyMMddHHmmssSSS)nonce ijj175bijiieyei9 PSign._fingerprint(设备常量)fp_short b5216 PSign._appId(设备常量)token tk03wb... 来自服务器下发md5_sign b9347a91... _$gs(key, sorted_params)version 5.3 常量ts_ms 1778708545012 Date.now()payload of7ruCLjy... _$clt()设备指纹编码md5_body aa1e15fc... _$gsd(key)final_sign of7r3ekgHGHQ... _$qo.encode(_$qX.parse(param_keys))

##  加密流程

###  整体结构

十个字段里,token来自服务端下发,nonce/fp_short是设备常量,剩下六个由本地算法算出。整条调用链:


    signSync(opts) → _$cps(opts) 参数验证+排序 → _$rds() 刷新设备随机字段 → _$pam(token, genKey) 设置密钥生成函数 → _$clt() 计算payload(设备指纹编码) → _$ms(sorted_params, payload) key = __genKey(token, fp, ts_str+'62', appId) md5_sign = _$gs(key, params) md5_body = _$gsd(key) final_sign = _$qo.encode(_$qX.parse(param_keys)) → 拼成h5st

六个本地字段全部绕不开同一层预处理和同一套自定义编码,拆开看。

###  seData1预处理

在字节码PC=199处找到的_$seData1函数,是所有哈希函数共用的前置编码:


    ALPHA_S = ”<64字符自定义字母表,从字节码字符串池取>” def sedata1(s: str) -> bytes: n, k = len(s), len(s) // 4 codes = [ord(c) for c in s] mid = [] for i in range(3): g = sum(codes[i*k:(i+1)*k]) if k else 0 mid.append(ord(ALPHA_S[(g * 11) % 64])) mid.append(ord(ALPHA_S[sum(codes[3*k:]) * 11 % 64])) return s.encode('latin-1') + bytes(mid) + b'<固定后缀>'

把字符串切四段求码点和,映射进64字符自定义字母表,拼在原串后面,再加一段固定后  PSign._algos.SHA256(s) =
sha256(sedata1(s)),MD5(s) = md5(sedata1(s))  ,所有哈希函数都先过这层预处理,不直接对输入做标准哈希。

###  自定义Base64与密钥生成

_$qo.encode在字节码PC=451,是final_sign和payload共用的编码器:


    ALPHA_B = ”<另一张64字符自定义字母表,与ALPHA_S不同>” def jd_b64_encode(data: bytes) -> str: pad = 3 - (len(data) % 3) padded = data + bytes([pad] * pad) # PKCS7填充,补到3的倍数 return stringify(padded)[::-1] # 自定义字母表编码后整串反转

密钥生成函数__genKey来自_$pam()传入的字面量,加了固定盐:


    KEY_SALT = ”<固定盐,字面量取自_$pam()传入的genKey函数体>” def jd_gen_key(token, fingerprint, ts_str, app_id) -> str: s = token + fingerprint + ts_str + '62' + app_id + KEY_SALT return sha256(sedata1(s))

ts_str拼接固定后缀'62'才进key,这个后缀藏在_$ms函数内部的一个中间变量里,不看字节码猜不出来。

###  md5_sign与md5_body

两个MD5签名字段算法结构相同,但输入完全不同。md5_sign(字节码PC=4399)依赖排序后的参数:


    def jd_gs_sign(key, params) -> str:
     # params按key排序,格式是”key:value”而不是”key=value” ps = ”&”.join(f”{p['key']}:{p['value']}” for p in params) return md5(sedata1(key + ps + key))

md5_body(字节码PC=4492)完全不依赖params,只用key拼一段固定字符串:


    GSD_FIXED = ”<多个key:value字段用&拼接的固定字符串,见下节>” def jd_gsd_sign(key) -> str: return md5(sedata1(key + GSD_FIXED + key))

###  payload与随机字段

payload字段(_$clt,字节码PC=4891)把设备指纹对象编码进去:


    def jd_clt(rd1_snapshot, fingerprint) -> str: obj = copy.deepcopy(rd1_snapshot) obj['fp'] = fingerprint if str(obj.get('bu4', '')) == '0': obj['bu4'] = '-1' json_str = json.dumps(obj, indent=2, separators=(',', ': ')) return jd_b64_encode(json_str.encode('utf-8'))

rd1_snapshot是设备指纹快照,需要真实浏览器采集一次,离线复现时直接复用。每次签名前,SDK还会用_$q8刷新两处随机字段:


    Q8_ALPHA = ”<54字符字母表,数字+小写字母+部分大写字母+'_-'>” def jd_q8(n) -> str: chars = [Q8_ALPHA[secrets.randbelow(54)] for _ in range(n)] s = ''.join(chars) if len(s) > 4: s = s[:4] + '3' + s[4:len(s)-1] # 位置4插入固定'3',删末位保持长度 return s

顶层random取11字符,extend.random取13字符,生成规则相同,只是长度不同。位置4插入的固定'3'不参与随机,推测是SDK版本标记。

##  固定串里的拼写陷阱

md5_body用到的GSD_FIXED固定字符串里,某个字段名的  function  被拼成了  fnuction
,是刻意拼错的,不是提取时的笔误。追字节码PC=4492处的14个字符串片段拼接过程,拼出来的就是这个错误拼写。

凭直觉重写这段固定串,大概率会不自觉按正常拼写打字,这样算出来的md5_body会和真实客户端算的不一致,签名直接失效,而且从报错现象上完全看不出问题出在一个拼写错误上。唯一可靠的做法是从字节码里把字符串片段原样拼出来,不做任何"看起来像笔误"的修正。

##  落地验证

按上面的算法链拼出完整h5st,拿真实商品详情接口测试  (functionId=jsfbox_pre_gb)  ,请求返回HTTP
200,响应体code字段为0(成功),正常拿到业务数据。算法链每一段单独验证过和字节码逐值匹配之外,这一步确认的是整条链拼起来之后,服务端真的会接受。

##  小结

十个字段里六个能离线复现,拆解下来最有价值的两点是"所有哈希函数共用同一套预处理"这个结构性发现,和固定字符串里那处刻意拼错的陷阱。前者让六个独立字段的逆向工作量骤减,后者提醒:VM字节码保护下,任何看起来像笔误的固定内容都不能凭直觉去"修正",必须原样从字节码里抠出来。这套方法目前只在v5.3上验证过,遇到其它版本或类似的预处理层设计,欢迎评论区聊聊你们的思路。
