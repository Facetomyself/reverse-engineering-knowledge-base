#  一文讲透：什么时候该逐 opcode 逆 JSVMP，什么时候该直接反混淆

本文所有内容仅供学习交流使用，目标为公开的逆向练习靶站，不用于任何其他目的；不提供可直接批量采集的成品脚本，严禁用于商业及非法用途，否则后果与作者无关。


我在一道题上抓了 141MB 的字节码执行流，逐 opcode 往下逆，连撞六层陷阱。

每一层都像算法，每一层都不是。

最后换成静态反混淆，十分钟出结果。

这篇讲的就是那个判断：  ** 面对一个 JSVMP，什么时候该逆 opcode，什么时候该直接反混淆。  ** 判据在第一节，案例和完整代码在后面。


##  一、判据：算法编进 opcode 了吗

一句话：

> ** 先问「算法编进 opcode 了吗」，再决定要不要逆 opcode。  **

混淆 ≠ 虚拟化。obfuscator.io 这类混淆器只是把源码搅烂，算法还是  ** 源码级  ** 的；真正的 VM 保护才会把算法编译成字节码。

两者要用完全不同的工具。

现象  |  说明什么  |  该用什么
---|---|---
热点函数全是 add/mul，结果是 NaN  |  诱饵  |  换采集范围，不是换假设
几十万步纯位运算，发生在脚本最开始  |  字符串解码器  |  忽略，往后看
成千上万个  ` debugger  ` 语句  |  反调试层  |  忽略
静态断点 0 命中，但签名照跑  |  VM 是 eval 出来的  |  静态断点作废
AST 扫不到任何标准 crypto 常量  |  常量在被解释的程序里  ** 或  ** 被混淆器藏了  |  ** 先反混淆再判断  **
** 反混淆后源码结构直接可读  ** |  算法没编进 opcode  |  ** 静态反混淆，别逆字节码  **
反混淆后仍然只剩 dispatcher + 常量池  |  算法真的编进了 opcode  |  这时候才轮到逐 op / devirt

倒数第二行是分水岭。下面用一道题把它走完。


##  二、案例：一个 64-hex 的 token

猿人学 match/26，  ` GET /api/question/26  ` 带一个 token：


    GET https://match.yuanrenxue.cn/api/question/26
        ?page=1&pageSize=10&kw=
        &token=c5e9de2e02c8b10b29a1d75b857c710de47339bba37591efef3916e35b61aa29
        &now=1785825405648

64 hex = 32 byte = 256 bit，第一反应是 SHA-256。

先做最便宜的排除——19 种明文拼法，逐个撞：


    import hashlib, itertools
    path, now, page, size, qid = "/api/question/26", "1785825405648", "1", "10", "26"
    cands = [path+now, path+now+page, now+path, path+now+page+size,
             path+now+page+qid, now+page, "$"+path+now, path+"|"+now+"|"+page]
    for c in cands:
        print(hashlib.sha256(c.encode()).hexdigest() == token, c)
    # 19 种全 False

** 全不命中  ** → 含盐、多轮、或魔改的定制哈希。

签名器栈从 XHR 记录里直接可读：


    VMXHR url=…/api/getTime      stack: <$.ajax@s18> <A@s13> <ilMTI@s13> …
    VMXHR url=…/api/question/26?…&token=a785a926…&now=1785899999501
          stack: <XMLHttpRequest.<computed>@s13> <send@s5> <ajax@s5> <D@s13> …

` now  ` 不是本地时钟，是服务端  ` /api/getTime  ` 下发的，签名时原样回传。


##  三、VM 形态：table 型，40 个 opcode

签名器是 53KB 的  ` 26.js  ` 。静态识别：


    dispatch_type : table       # 区别于三元分派、线程栈机
    case_count    : 40          # 40 个 opcode
    dispatcher_fn : L
    opcode_var    : aH
    pc_var        : _pc
    buf_var       : _buf

AST 扫出 1401 个数字字面量、21 个大常量，  ** 没有一个  ** 是标准 SM3/SHA-256 的 IV/T/K。

到这里我做了那个错误判断：  ** "哈希常量藏在被解释的字节码程序里，所以得逐 op 逆。"  **

判据表倒数第三行说得很清楚——扫不到标准常量，有两种可能，我只考虑了一种。


##  四、六个陷阱

###  1\. NaN 诱饵

热点  ` 16:1  ` ，  ` add=234 mul=156  ` ，看着就是哈希核。

实际在对  ** undefined 的全局堆  ** 做算术，结果全是 NaN。纯粹污染热点统计。

###  2\. fn 范围陷阱（最阴的一个）

exec-trace 默认 target 只跟到  ` fn 0..60  ` ，而  ** 哈希核在 fn > 60  ** ，被静默排除。

于是我得到一个假象：


    op mix  add=630  mul=420  shift=0  xor=0  and=0
    FAMILY GUESS: unknown

零移位、零异或 → "这不是 SHA/SM3 族，是自定义的加乘构造"。

** 这个结论错得非常自洽。  ** 任何"全场没有 X"的结论，先查采集范围，再怀疑算法族。

###  3\. string decoder

热点  ` 16:306  ` ，38 万步纯位运算，比哈希还像哈希。

它是 obfuscator.io 的  ** base64 + RC4 字符串解码器  ** ——混淆器要在运行时把字符串数组解出来，位运算量天然巨大。

###  4\. 反调试

` script19  ` ，25 万步，  ** 43303 个  ` debugger  ` 语句  ** \+ 自防御闭包。

一步算法都没有。

###  5\. eval 生成

在 26.js 上下内容锚断点，签名连跑 5 次：


    --break-at 'match/26:@](B,A[0x4],A[0x5],A[0x6]' --dump-ctx
    → armed at 26.js col 22709, hits = 0

真正执行的 VM 是  ** eval 出来的  ** ，运行时 script id 会漂，静态脚本里的断点永远等不到。

###  6\. 常量巧合

AST 扫出  ` 0x7c179d8a  ` ，和 SM3 的 T 常量  ` 0x7a879d8a  ` 只差几位。

标准 SM3 + 改 T + 6 种输入变体，全否。

** 纯属巧合。  ** 后来证明 SM3 猜对了，但改的是 IV 不是 T——猜对方向猜错位置，比全猜错更费时间。


##  五、分水岭

六层撞完，我问了一个问题：

** 这六层里，有哪一层是算法？  **

没有。字符串数组、解码器、debugger、eval、诱饵——全是  ** 防御基础设施  ** 。

我在用拆虚拟机的方式，拆一层包装纸。

换工具：


    # 先试 webcrack —— 装不上，isolated-vm 在 node v26 编译失败
    npm i -g webcrack                        # ❌ node-gyp 报错

    # 换 deobfuscator（synchrony），纯 JS，无 native 依赖
    npx deobfuscator 26.js -o 26_deob.js     # ✅

控制流平坦化、字符串数组、死代码一起还原。

打开  ` 26_deob.js  ` ——  ** 魔改 SM3 类直接摆在那里  ** ：  ` reset()  ` /  ` write()  `
/  ` _compress()  ` /  ` _fill()  ` /  ` sum()  ` ，一个不少。

** 算法没编进 opcode。判据表倒数第二行，成立。  **


##  六、魔改点：每个常量挂一个环境探测

结构一字未动：消息扩展、P0/P1 置换、FF/GG 布尔函数、64 字节分块、padding，全部标准。

魔改全在常量上——而且  ** 每个常量都挂在一个不同的环境检测上  ** 。

先看 IV，  ` 26_deob.js:194-201  ` ：

###  这套设计的真正杀伤力

** 补环境漏掉任何一个探测点，token 不会报错，它会安静地给你一个错的值。  **

八个 IV + 两个 Tj + 一个掩码 + 一个字节掩码 =  ** 十二个独立开关  ** ，任意一个翻转都导致全盘不同。

传统"补环境补到不报错"的做法在这里完全失效——它根本不报错。

只能反过来做：  ** 先拿真浏览器的输入输出样本，再暴搜哪套常量能对上。  **


##  七、完整复现代码

从  ` 26_deob.js  ` 逐行转写，真浏览器（headless chrome）分支：


    #!/usr/bin/env python3
    """match/26 token = 魔改 SM3(path + now + page)"""

    M = 0xFFFFFFFF
    def rotl(x, k):
        k %= 32
        return ((x << k | x >> (32 - k)) & M)

    # 魔改 IV —— 26_deob.js:194-201 真浏览器分支
    IV = [1937770108, 1983173321, 385893078, 3666375988,
          2701930684, 353449901, 3816598093, 4008382286]

    def Tj(j):                       # 非标准 0x79cc4519 / 0x7a879d8a
        return 2044544281 if j < 16 else 2098347407

    Z  = 4244635647                  # q &= z   document.__proto__ === HTMLDocument.prototype
    MT = 4294967290                  # t &= 0xFFFFFFFA
    MU = 4289724415                  # u &= 0xFFB6FFFF

    def ff(j, a, b, c):
        return (a ^ b ^ c) if j < 16 else (a & b | a & c | b & c)

    def gg(j, e, f, g):
        return (e ^ f ^ g) if j < 16 else (e & f | (~e & M) & g)

消息扩展，标准 P1，一字未改：


    def expand(blk):                 # 返回 W[0..67] + W'[68..131]
        m = [0] * 132
        for n in range(16):
            m[n] = ((blk[n*4] << 24) | (blk[n*4+1] << 16) |
                    (blk[n*4+2] << 8) | blk[n*4+3]) & M
        for q in range(16, 68):
            r = m[q-16] ^ m[q-9] ^ rotl(m[q-3], 15)
            r = r ^ rotl(r, 15) ^ rotl(r, 23)
            m[q] = (r ^ rotl(m[q-13], 7) ^ m[q-6]) & M
        for q in range(64):
            m[q+68] = (m[q] ^ m[q+4]) & M
        return m

compress，比标准 SM3 多三步 AND 掩码：


    def compress(reg, blk):
        n = expand(blk)
        o = reg[:]
        for p in range(64):
            q = (rotl(o[0], 12) + o[4] + rotl(Tj(p), p)) & M
            q = q & Z                                      # 魔改掩码 1
            q = rotl(q, 7)
            s = (q ^ rotl(o[0], 12)) & M
            t = (ff(p, o[0], o[1], o[2]) + o[3] + s + n[p+68]) & M
            t = t & MT                                     # 魔改掩码 2
            u = (gg(p, o[4], o[5], o[6]) + o[7] + q + n[p]) & M
            u = u & MU                                     # 魔改掩码 3
            o[3] = o[2]; o[2] = rotl(o[1], 9);  o[1] = o[0]; o[0] = t
            o[7] = o[6]; o[6] = rotl(o[5], 19); o[5] = o[4]
            o[4] = (u ^ rotl(u, 9) ^ rotl(u, 17)) & M      # 标准 P0
        return [(reg[v] ^ o[v]) & M for v in range(8)]

字节转换，注意  ` k & 254  ` ：


    def str_to_bytes(s):             # charCodeAt 大端，真浏览器分支清最低位
        out = []
        for ch in s:
            k = ord(ch); l = []
            while True:
                l.append(k & 254); k >>= 8
                if not k: break
            out += l[::-1]
        return out

padding 和出口：


    def sm3_mod(msg):
        data = str_to_bytes(msg)
        size = len(data)
        chunk = data + [0x80]                       # _fill: 0x80 + zeros + 64-bit 位长
        while len(chunk) % 64 != 56:
            chunk.append(0)
        bitlen = size * 8
        chunk += [(bitlen >> (8*i)) & 255 for i in range(7, -1, -1)]
        reg = IV[:]
        for m in range(0, len(chunk), 64):
            reg = compress(reg, chunk[m:m+64])
        return reg

    def token(path_now_page):        # reg → 32 byte 大端 → 每 byte 2 hex
        reg = sm3_mod(path_now_page)
        b = []
        for q in reg:
            b += [(q >> 24) & 255, (q >> 16) & 255, (q >> 8) & 255, q & 255]
        return ''.join('%02x' % x for x in b)

##  九、回到判据

把这一趟对照第一节那张表：

我遇到的  |  判据说什么  |  我做了什么
---|---|---
AST 扫不到标准 crypto 常量  |  两种可能，先反混淆  |  ❌ 直接认定"在字节码里"
add/mul 全是 NaN  |  诱饵，换范围  |  ❌ 当成算法特征
全场 shift=0 xor=0  |  先查采集范围  |  ❌ 推翻了算法族假设
静态断点 0 命中  |  VM 是 eval 的  |  ✅ 这步判断对了
反混淆后源码可读  |  别逆字节码  |  ✅ 十分钟出结果

前三条判断错了，代价是 141MB 执行流和一堆时间。

** 那 141MB 也不是全白抓  ** ——它最后的价值退化成了"提供验证样本"：输入明文 + 对应 token，让离线复现器有东西可校验。

这个降级本身也是结论的一部分：  ** 采集永远不亏，亏的是拿采集结果去回答它回答不了的问题。  **


##  十、三条带走

  1. 1\.  ** 先问「算法编进 opcode 了吗」  ** 。混淆 ≠ 虚拟化，工具完全不同
  2. 2\.  ** 「全场没有 X」先查采集范围  ** ，再怀疑算法族
  3. 3\.  ** 常量挂在环境检测上时，别指望报错  ** 。补环境补错了它照样出值，只是出错值——只能靠真浏览器样本反推
