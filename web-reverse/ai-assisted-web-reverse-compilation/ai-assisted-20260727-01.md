## 正文

> 本文仅做技术方法论分享,目标信息已脱敏处理,不提供可直接使用的完整实现,请勿用于未经授权的用途。

某财经/股票信息平台的每个API请求URL上都带一个签名参数,记作md5__1038。不带或带错,请求被WAF拦截。

##  环境

站点叠了三层不同厂商的反爬:

早期把设备指纹那层的脚本错当成md5__1038签名器,也从瑞数风格的cookie误推"这是jsvmp"。三层混一起看会全乱,得先按标志把参数分归到具体哪一层。

token长这样:


    md5__1038 = <11位会话前缀>-<~186字符自定义编码>

前缀21个真实请求全部相同,编码段随URL和时间变。

md5__1038的签名器是一个166KB的JScrambler混淆bundle,带源码自校验:字符串解码器的偏移常量由对bundle自身源码做MurmurHash3算出,改一个字符校验值就变、解码全错。webcrack这类通用反混淆工具只能重命名变量,解不开这层自卫。

##  工具:vmtrace

本文用到的执行轨迹、字段来源定位,都靠自研的Chromium魔改版运行时追踪工具vmtrace抓取,未开源。

##  第一次误判:当成国密签名算法

早期从执行轨迹里看到Sm2/Sm3/HMAC字符串,判定md5__1038是国密SM2签名(带随机k,理论上不可复现)。后来抓到编码函数的真实输入才发现看错了对象,那几个字符串是另一个SDK厂商代码里的,跟md5__1038没关系。md5__1038实际是确定性的自定义编码,不含随机k,原则上可以完全离线复现。

##  加密流程

###  整体结构

payload是7个字段拼出来的定长明文,md5__1038是它的LZString编码:


    payload = deviceFp(16) | digits(16) | num(8) | ts1(13) | MAC(44,base64) | ts2(13) | hexFp(22)md5__1038 = <11位会话前缀> + ”-” + LZString(payload, ALPHA)

deviceFp/digits是同一个数组的两种格式化输出,num是一个上游计数器,ts1是Date.now(),MAC是32字节指纹签名,ts2是另一个WAF状态时间戳,hexFp是本地缓存的设备id。七个字段来源各不相同,得逐个拆。

###  编码算法

确认是确定性编码后,开始逆编码函数内部的字节到索引变换。这个函数被JScrambler虚拟化过,每个运算都拆成独立的handler函数动态派发,静态读代码读不出算法形状,只能靠执行轨迹一步步还原,197个执行点里筛出真正随输入变化的部分,再重建成能跑的解释器,通用bug修了一路(布尔值解码方向反了、累加器读取差一步)。这条路走通了,但走远了。

回头看,更快的解法是把编码函数直接当黑盒,不管内部怎么虚拟化,只喂真实的(输入,输出)样本对。5组数据(输入137/138字节,输出175-191字符不等)一测,输出就是业内常见的LZString压缩,只是默认字母表换成了站点自定义的64字符集:


    ALPHA = ”TXiPqC/jvmu_y61N2At0c=ezZwknOK4bfxJsWl8SGQFLhHgM9YDI7pVUoBaRd53Er”callback(idx) => ALPHA[idx] // idx∈0..62,实测覆盖

核心算法60行Python写完,不需要字节码级还原。

###  MAC来源

编码层解决后,payload七个字段里最关键的是一个44字符的base64值(记作MAC,解码后32字节)。静态读WAF代码,看到一段XHR响应钩子:监听readyState===4,读getResponseHeader,按|切分存进window.
_ waf  _ *键,模式很像服务端在响应头下发。

抓NetLog(全量网络日志)做确定性验证:当次请求真实的MAC值在网络日志里出现0次,  _
waf_前缀本身也出现0次。响应头钩子确实存在,但读写的是别的_waf  _ *键,不是MAC那个。

又一度以为MAC是WAF客户端计算的指纹哈希(canvas/webgl渲染出的设备指纹),验证后发现更简单:MAC就在GET页面返回的原始HTML里,一个标签直接写着{"_waf_bd8ce2ce37":""}。不用计算,不用等WAF运行时生成,请求一次页面就能拿到。

追执行轨迹能看到签名器组装函数按key读出这个值,不是算出来的:


    @807 obj.W → ”_waf_bd8ce” @825 obj.T → ”2ce37”@835 Add → ”_waf_bd8ce” + ”2ce37” = ”_waf_bd8ce2ce37” ← 拼出key@838 GetKeyedProperty: obj#1031341[”_waf_bd8ce2ce37”] → MAC ← 按key读,不是算

###  deviceFp推导

deviceFp(16位十六进制)的格式化函数不难找:输入是数字数组,输出deviceFp;另一个函数把同一数组每位加3输出digits字段,这层关系12/12真实样本验证吻合。难的是数字数组从哪来,连续踩错了三次:

  * 怀疑是环境指纹哈希(canvas/webgl渲染特征),但deviceFp每请求都变而环境指纹该是稳定的,数据不支持,撤回。
  * 冻结客户端时钟测试(Date.now()钉死),deviceFp跟着冻住,一度判定"时间派生"。后来发现是测试方法本身有问题:冻结时钟的两次运行恰好是两次不同的页面加载,MAC才是每次加载才换,deviceFp其实跟着MAC走。
  * 找到一个函数里裸露着MurmurHash2魔数0x5BD1E995,以为是deviceFp的哈希核心,抓28个真实调用样本才发现这个函数签的是"MAC+方法+URL",是请求URL签名,认错了对象。

最终逐函数追值定位:一个32字节中间哈希值,每次调用都变、但同一URL调用多次会重复,拿它和请求方法、目标URL拼起来测,13/14组真实样本里同一URL对应同一deviceFp(剩一组是URL截断导致的例外):


    deviceFp = format( MurmurHash2( MAC + 请求方法 + 会话前缀 + 域名 + URL, seed=0 ) )

魔数m=0x5BD1E995、位移r=24,数字化输出十进制旋转补位到16位,逐位加3得到最终十六进制串,12组真实样本全部验证通过。deviceFp本质是确定性的URL请求签名,不含时间随机也不含设备指纹。

hexFp顺着localStorage一个固定key找到,是首次访问生成、缓存180天的设备ID:DJB2哈希(对随机数拼时间戳)加当前时间的十六进制值拼接而成,同样是确定性算法。

##  落地验证

全部字段来源定位清楚后,用真实cookie做了一轮对照实验访问行情接口。带cookie不带md5__1038、带垃圾md5__1038、带过期md5__1038,接口照常返回200和真实数据;不带cookie,md5__1038给什么都拒绝。真正卡数据的是登录态cookie,md5__1038是反爬遥测信号,被收集但不逐请求校验。这个结论只能靠真实请求测出来,光看算法推不出对方在用它做什么。

##  小结

SM2误判、响应头下发误判、deviceFp三次认错对象,一条案子里五次错误方向,每次都靠更完整的样本或一次确定性抓包纠正,源码模式推出的结论和数据证明的结论是两个置信等级;遇到虚拟化混淆也不用急着逐字节反编译到底,先花点时间猜"这会不会是个已知算法",往往比直接开始逐字节还原划算。这条案子的方法论目前只在这一个目标上完整走过,遇到类似的多层反爬叠加站点,欢迎评论区聊聊你们的经验。
