## 第一篇：fangdi rs6 P-cookie逆向:从412挑战到离线签名的完整链路

来源：微信公众号：ai辅助逆向手记 · 原始发布时间：2026-07-31 · 归档日期：2026-09-06

### 正文

#

> 本文仅做技术方法论分享,不提供可直接使用的完整实现,请勿用于未经授权的用途。

某房地产“ZmFuZ2RpLmNvbS5jbg==”用rs6做反爬,核心是一个叫P的cookie。这条链路曾经被判定”架构上不可能做成纯离线签名器”:签名逻辑是每次会话重新生成的字节码VM,种子来自服务端下发的nsd,VM生成一次就废弃。后来陆续攻破,现在的结论反过来了:从412挑战响应里拿到nsd/cd,不用起浏览器,纯HTTP请求就能拿到200,实测12/12。

这篇先把地图画完整,标出每一段是什么、由哪一块负责。熵引擎与property57编码、codeUid公式、basearr结构与外层加密这三块留到后面分别拆开讲。

###  环境

rs6的反爬体现在两个cookie上:


    UA1L1zGonajvO httpOnly,服务端下发,门票性质,删掉直接400/412UA1L1zGonajvP 非httpOnly,JS写入,客户端指纹证明,本系列文章的主体

P的生成逻辑藏在一个eval出来的脚本里,由两层VM构成:一层bootstrap(搭建host函数池),一层主签名VM(991字节程序,156个opcode的二叉树dispatch,threaded-
code执行)。这层VM每次页面加载都重新生成一份新的,opcode编号、字节码、数据池全部per-
session重排,是这个案子早期被判定"离线不可能"的直接原因。

第一次请求页面,服务端直接回412,响应体里带着这次会话专用的几个值:


    412响应体 → nsd(种子,整数,例如91055/121772/122962) cd(编码数据,后续派生密钥要用) O(完成态标记,浏览器跑完整套流程后才会置位)

后面所有计算都是围着nsd和cd转,O只在判断"这次会话有没有被浏览器正常走完"的时候用得上,不参与加密。

###  工具

本文分析流程由cc配合自研的Chromium魔改版运行时追踪工具vmtrace完成:cc负责梳理逆向路径、定位下一步该抓什么、交叉核对多轮实验结果;vmtrace负责在字节码执行层面拿函数真实输入输出,不依赖函数名。vmtrace未开源。

###  加密流程

####  整体结构

完整链路:


    curl请求412挑战 → 响应体提取 nsd(种子) / cd(编码数据) / O(完成态标记) → derive_keys(nsd, cd) → keys(45个派生密钥) → vm_full(nsd) → kH(codegen塔生成的源码,~293KB) → codeuid_final(kH, keys) → codeUid → 合成 basearr(约150字节,结构化指纹序列化): env段 = 一次性模板(浏览器环境常量,服务端不校验具体值) sec2 = 时间戳 + keys派生值 + 随机 + hostname sec3 = 固定常量 + codeUid sec6[1] = encryptMode2(decrypt(keys[22]), keys[16], 1) fixedValue20 = 查表(keys[29..32] 在会话洗牌表 gX 里取值) → property57编码(Huffman压缩,自定义codebook) → AES-CBC(key17, iv=key2[:16]) → 加时间戳/调试位等frame信息 → AES-CBC(key16, iv=随机) → 自定义base64编码P cookie → 提交请求 → 200

九个环节里,基础密钥派生和VM代码生成两步相对直接;codeUid的取值规则、basearr的字段构成、property57的编码细节、外层两层AES-
CBC各自的推导过程,分别是接下来三篇要讲的内容。

###  站点的反调试手段

rs6的签名代码每次访问都现场生成一份新的,生成的时候顺手在代码里埋了好几层防分析的东西。

####  代码层的两道拦截

代码里随机撒debugger语句
:生成出来的签名代码里,每隔几行就有一个debugger,而且"隔几行"是用随机数现算的,每次生成的位置都不一样,不是固定在某一行。开发者工具里手动删代码这种办法没用,删了这次的,下次生成代码又是新的位置。真正能解决的办法是让浏览器直接把debugger语句当空气,不管它出现在哪一行都不暂停,不用去追它藏在哪。

插桩插太多,跑得慢了会被识别
:分析工具如果给每一条字节码指令都挂个钩子记录数据,执行速度会比正常情况慢出好几倍。站点会盯着执行到底花了多长时间,发现明显不对劲,直接切到一条专门喂假数据的分支,签名照样能生成出来,只是内容是错的,拿去请求服务端还是会被拒。解决办法是别把每条指令都钩上,只在真正要看的几个关键点插桩,把额外开销压到站点感觉不出来的程度。

####  识别到分析手段就换算法

发现有人用Proxy包底层函数,直接换一套算法
:调试时常用的一招是把浏览器提供的底层函数用一层Proxy包起来,这样每次调用都能记下参数和返回值。站点能识别出底层函数被Proxy包过,一识别到就切换成另一套完全不同的算法生成签名,产出的数据和真实数据对不上,等于白抓一场。目前的应对办法是换一种不用碰底层函数本身的观察方式,不去包它,只在旁边悄悄看。

环境指纹采集这一层,目前只能靠真实浏览器
:除了签名主体,页面上还有一个专门收集navigator、screen、canvas这些环境信息的模块,顺带算一个"像不像爬虫"的判断标志。这部分逻辑目前没找到能绕开真实浏览器的办法,是目前唯一没有完全攻破的一堵墙。

###  落地验证

链路走通之后拿真实请求测了两件事。第一,合成的basearr里哪些字段真的被服务端校验:sec2、sec3、fixedValue20这几段字节改了会直接拒;env模板、sec6的部分字节、结构性占位段改了不影响结果,说明校验没有覆盖basearr全部内容。

第二,纯离线合成P去请求真实接口,连续测试12次全部返回200。期间遇到过几次空响应的400,排查后确认是特定412挑战会话在服务端处理流程上的拒绝,和是否被识别成爬虫无关,换一次新的412挑战重试就能通过。

###  小结

这条链路从"服务器硬墙,纯Python必然400"走到"纯HTTP请求12/12成功",靠的是算法和反调试两头一起啃。加密链路这头:property57编码的codebook查清是静态确定性的,codeUid的取值规则验证到fresh会话100%命中,basearr被发现是结构化序列化,细节在后续文章里展开。

站点这头:debugger随机插入、插桩测速、Proxy检测这几层逐个拆开,不算复杂,只是每一层都得先确认自己踩中了才知道该往哪个方向调整观察方式。欢迎关注后续,也欢迎评论区聊聊你们遇到的rs6目标是什么形态。

## 第二篇：fangdi rs6逆向:确定性LCG置换与Huffman codebook

来源：微信公众号：ai辅助逆向手记 · 原始发布时间：2026-08-01 · 归档日期：2026-09-06

### 正文

> 本文仅做技术方法论分享,不提供可直接使用的完整实现,请勿用于未经授权的用途。

rs6的P
cookie在进最外层AES加密之前,basearr要先过两道处理:一道是确定性的伪随机置换,另一道是自定义Huffman压缩。两道都是标准算法结构。

但property57的编码表一度被误判成"每会话变化、离线算不出来",原因是分析时用的源码插桩探测被站点的反注入检测识破,拿到的是一份故意喂出来的假数据。换成不碰源码的观察方式后,编码表其实是写死的静态常量。

这是fangdi
rs6逆向系列的第二篇。第一篇画过整条链路的地图,这篇往下拆链路中间那两道”打乱+压缩”的处理;codeUid公式和basearr结构留给后面两篇。

basearr组装完之后不会直接进AES,中间还夹着两道处理:LCG打乱字节顺序,再用property57的Huffman
codebook把它压缩编码,出来的东西才轮到外层AES-CBC:


    raw basearr(约150字节) → LCG生成伪随机序列 → Fisher-Yates置换,得到打乱后的字节序 → property57编码(Huffman压缩,自定义codebook) → 交给外层AES-CBC

###  工具

本文用到的函数输入输出捕获,靠cc配合自研的Chromium魔改版运行时追踪工具vmtrace完成,后者支持在字节码执行边界非侵入地拿到真实参数,不需要改动页面源码,未开源。

###  加密流程

####  LCG与Fisher-Yates置换

伪随机数生成器是一个线性同余生成器:


    state = (state & 0xFFFF) * 15679 + 2531011

第898次调用后会reseed回初始种子,这个常量组合跨会话固定,两个不同会话验证过一致:


    call_count = 0def PRNG(): global state, call_count call_count += 1 if call_count == 898: state = seed # 第898次调用,悄悄重播种 state = (state & 0xFFFF) * 15679 + 2531011 return state

第一次看到这个reseed点会怀疑是不是巧合,跑两个不同会话核对之后,两边都精确停在第898次调用,不是凑出来的边界。拿这个PRNG跑Fisher-
Yates置换:


    i = 900while i > 1: i -= 1 j = PRNG() % i swap(arr[i], arr[j])

用真实种子复现整条序列,900个位置对应的920次(i,j)对全部精确命中,置换本身没有隐藏的额外扰动。

####  property57的codebook

property57是basearr进AES之前的最后一步,把字节流压缩编码成更短的位序列,压缩方式是Huffman:符号0的频率权重是36,符号255的频率权重是6,其余254个符号权重都是1。高频符号权重压得比标准Huffman常见的分布更极端,是因为basearr里字节0和255本来就大量出现(占位、填充位置),故意把它们的编码压到最短能省下不少输出长度。

用这三个频率值重建一棵Huffman树,产出的编码表和运行时真实codebook逐项比对,256个符号全部一致,取三条对照:


    符号 编码值 位长0 6 31 184 83 374 9

符号0权重最高,编码位长最短,符合Huffman"越常见越短"的基本规律,和运行时抓到的真实codebook一一对应。

编码过程本身是标准的累加器打包,完整流程写出来是这样:


    acc, accbits, out = 0, 0, []for byte in basearr: code, bits = codebook[byte] acc = (acc << bits) | code accbits += bits while accbits >= 8: accbits -= 8 out.append((acc >> accbits) & 0xFF)if accbits > 0: # 收尾不满8位 acc = (acc << (8 - accbits)) | (184 >> accbits) out.append(acc & 0xFF)

每个输入字节按codebook查到对应的编码位长和编码值,累加进bit缓冲区,凑够8位就吐一个字节;最后不满8位的部分补固定填充值184后flush。这套逻辑对不对,不看理论,直接拿真实抓包的basearr跑一遍:输出和真实property57函数的返回值逐字节相同,包括那个容易被漏掉的收尾字节。

###  codebook差点被误判成session-derived

编码表要是真的每次会话都不一样,离线复现这条路直接走不通。第一轮分析时,想直接从源码层面确认这个codebook是不是固定的,用了往源码里插桩打点、把参数dump出来的办法。插桩生效后拿到了一份"codebook",数据本身看起来完全正常,几个会话抓下来编码值真的在变。

这份数据后来发现是假的:插桩本身触发了站点的某种检测,实际执行路径切换成了一条专门喂给分析工具的decoy分支,返回的codebook看起来会随会话变化,一度被记成"session-
derived,离线不可复现"。

换成不修改源码本身的观察方式后,同一个位置抓到的才是真实数据,连续多次会话的codebook逐字节相同,跟前面插桩抓到的"每次都不一样"完全对不上。真相是property57的编码表从一开始就是确定性静态常量,之前"随会话变化"的结论完全建立在被喂了假数据的基础上。

###  落地验证

把复现的LCG、Fisher-Yates置换、Huffman
codebook和encode逻辑串起来,输入真实抓包拿到的basearr,输出和property57函数的真实返回值做端到端比对,逐字节相同。这一步验证的是整条"打乱+压缩"链路自洽,不依赖任何单点的巧合。

###  小结

这两道处理本身是标准算法,真正花时间的是分辨拿到的数据是不是真的,不是推导公式。往源码里插桩这类会改动运行环境的观察方式,一旦目标有能力识别探测行为,拿到的结果可能是精心准备的干扰项而不是错误;换一个不留痕迹的观察角度,重新验证一遍此前的结论,往往比死磕一条走不通的路更快出结果。这套方法目前在fangdi这一个目标上验证过,遇到类似的反插桩/decoy设计,欢迎评论区聊聊你们怎么分辨真假数据。

## 第三篇：fangdi rs6 codeUid逆向:两行CRC32公式

来源：微信公众号：ai辅助逆向手记 · 原始发布时间：2026-08-02 · 归档日期：2026-09-06

### 正文

> 本文仅做技术方法论分享,不提供可直接使用的完整实现,请勿用于未经授权的用途。

codeUid是rs6的P
cookie里basearr的一个字段,写进sec3段,和签名结果强关联。最终公式只有两行,是两个CRC32异或再取低16位,难的是公式里两个输入各自怎么从生成的代码里选出来,公式本身反而简单:一次早期验证只用了公式的一半就误以为算对了,真正在多个会话上稳定复现,靠的是把wrapper函数的选取规则和分段规则啃清楚。

这是fangdi rs6逆向系列的第三篇。前两篇分别讲了整体链路和熵引擎/property57编码,这篇专门拆basearr里最难定位的一个字段。

codeUid的输入不来自basearr本身,来自vm_full生成的那份动态源码塔(kH,约293KB)。这份源码每次会话都重新生成,codeUid要在里面定位两段特定内容再各自算CRC32,算出来的结果写进basearr的sec3段。

###  工具

本文用到的多会话交叉验证,靠cc配合自研的Chromium魔改版运行时追踪工具vmtrace完成,vmtrace负责在字节码执行边界抓每个会话的真实keys/codeUid值,cc负责比对多轮结果找出公式里遗漏的部分,未开源。

###  加密流程

####  整体公式


    codeUid = (CRC32(one) ^ CRC32(two)) & 0xFFFF one = CRC32(functionsNameSort[keys33].wrapper)two = CRC32(mainFunction.substr(741 * keys34, 741))

CRC32是一种校验和算法,输入任意长度的数据,输出一个32位整数,压缩包、网络包校验常用它来快速判断两段数据是否一致。它不是加密算法,谁都能算,也不抗碰撞,但计算便宜,拿来给"你这边跑出来的代码和我这边生成的是不是同一份"做轻量指纹刚好合适,不需要上真正的密码学哈希。

one和two都是对kH里的一段文本取CRC32,取哪一段是关键。

####  one:选中哪个wrapper

kH里有几十个这样的wrapper函数,举一个真实样本里对上号的:


    function _$_1(){  var Q=[27];  Array.prototype.push.apply(Q,arguments);  return G.apply(this,Q);}

函数体不做任何实质计算,就是把一个固定数字(这里是27,即key2)塞进参数数组开头,再原样转发给真正干活的函数G。几十个wrapper长得几乎一样,区分它们的只有外壳的函数名和这个塞进去的key2常量。先按累积代码块大小把它们分成几段:


    段边界(累积大小) = 38, 46(38+8), 53(46+7), 56(53+3)段0: [0, 38)   段1: [38, 46)   段2: [46, 53)   段3: [53, 56)

再从functionsNameSort这个排序结果里,用keys[33]当索引取出对应的wrapper。这四个边界数字不是配出来的,是先从真实wrapper列表反推段长,再拿好几个会话交叉核对才定下来的,4段里最麻烦的是最后一段(代码里叫c4段),它内部还按wrapper自己携带的一个key做了二次排序,单靠外层这四个边界数字算不对,得连这层二次排序一起还原。

这个排序一开始按几种直觉方式试过(按提取顺序、按函数名、按key2值排序),用真实样本对都对不上。最终定位到排序要通过源码里一份专门的索引结构(codegen塔内部用来生成函数名的opdata)才能算对,不是wrapper列表本身的任何简单排序规则能得出的。

####  two:定位mainFunction

mainFunction是kH里最大的一个函数,长度上限150000字符,并且要排除最外层包裹整个塔的IIFE(否则会选到框架代码而不是有效载荷)。找到之后按741乘keys34起始、截取741个字符的子串,对这段做CRC32。

###  一次只验证了一半的公式

一个样本验证通过,是不是就能收工了?早期用单个样本验证时,发现某个wrapper的CRC32单独算出来正好等于抓包里的codeUid,当时的结论是"codeUid
= CRC32(某个wrapper),不需要异或第二项"。这个结论只在一个样本上成立,换成新的会话去测就不对了。

回头看basearr结构较早期的版本,sec3字段只写入了one这一项;当前版本sec3写入的是one和two异或之后的结果。算法本身没有大改,是basearr组装时用到公式的哪一部分变了,只测过一个样本时,恰好落在只用one就能算对的旧结构上,才得到了"公式更简单"这个错误印象。

###  落地验证

把wrapper选取规则、分段规则、mainFunction定位规则和最终公式串起来,在7个相互独立、通过fn-
io单独抓到的新鲜会话上重新计算codeUid,7个全部命中,包括wrapper选取里最容易出错的c4分段(靠wrapper内嵌的key排序,3个位置逐一验证过)。取4组真实样本对照:


    keys[33]   选中的wrapper   codeUid49         _$_1            3263320         _$h4            944131         _$jg            759822         _$cU            22144

keys[33]每次会话都不一样,选出来的wrapper函数名也跟着变,4组数据里没有两组选中同一个wrapper,算出的codeUid却全部和抓包里的真实值对上,说明选取规则不是碰巧对了几次。

###  小结

一个样本能验证通过不代表公式完整,codeUid这次的教训是早期版本的basearr恰好只用了公式的一半,单样本验证撞对了这个特例,掩盖了真实公式还有另一半。往多个独立会话上扩大验证范围,才把"看起来简单"和"实际完整"的差距填上。这套codeUid公式目前在fangdi这一个目标上验证到7/7,遇到类似的多段CRC组合校验,欢迎评论区聊聊你们的定位思路。

## 第四篇：fangdi rs6 basearr逆向:150字节结构化字段

来源：微信公众号：ai辅助逆向手记 · 原始发布时间：2026-08-03 · 归档日期：2026-09-06

### 正文

#

> 本文仅做技术方法论分享,不提供可直接使用的完整实现,请勿用于未经授权的用途。

basearr是rs6的P
cookie在进入property57编码之前的明文载荷,约150字节。一个150字节的载荷,真的没办法拆开看吗?早期分析把它定性成一种"全局雪崩"结构:任何一个输入位变化会扩散影响几乎所有输出字节,理论上只能整体重新计算,拆不出单个字段的含义。

后来换了观测方式,发现这个判断错了:150字节里大部分是固定不变的环境指纹,只有一小部分随会话变化,而且每个字段的位置和编码方式都能对应到具体的浏览器属性。

这是fangdi
rs6逆向系列的第四篇,也是最后一篇。前三篇分别讲了整体链路、熵引擎与property57编码、codeUid公式,这篇卡在链路的头尾两端:前半段讲basearr自己怎么拼出来,后半段讲它压缩编码完之后怎么套上两层AES-
CBC,变成真正提交上去的P cookie。

四篇合起来是这条链路从412挑战到P cookie的完整逆向过程。

basearr的组装逻辑写在动态生成的VM字节码里,不是普通JS函数,常规的函数边界观测(钩住JS函数拿参数返回值)完全看不到它的组装过程。

###  工具

本文用到的host调用序列捕获,靠cc配合自研的Chromium魔改版运行时追踪工具vmtrace完成:cc负责判断每一轮观测结果说明了什么、该往哪个方向调整观测点;vmtrace负责在host函数调用这一层记录每次调用的参数和返回值,这一层刚好跨过了字节码VM内部不暴露给JS层的边界。vmtrace未开源。

###  决定性发现:雪崩混淆其实是字段序列化

basearr的组装逻辑在字节码VM内部执行,一般的函数级观测(钩JS函数入参出参)完全看不到里面发生了什么,只能看到一坨不透明的最终字节。换成记录host函数调用序列的观测方式后,情况变了,截取组装区间的几条真实记录:


    [idx=439, args=(...), ret=(4字节大端数)]     ← numToNumarr4,数字转4字节[idx=77,  args=(累积arr, 新值), ret=追加后的arr] ← numarrJoin,往结果里拼一段[idx=122, args=(), ret=当前时间戳]             ← 读时间

看到这几条记录才反应过来:组装过程其实是一串"读取一个值,拼接进结果"的重复调用,不是某种把所有输入搅在一起的单向散列。

拿4个不同会话的basearr做逐字节diff,结果证实了这个判断:150字节里约80字节在4个会话里完全相同,这部分是浏览器环境的固定指纹(平台、窗口尺寸、域名等);剩下约70字节才会随会话变化,而且变化的字节能进一步拆成时间戳、少量VM派生值、纯随机三类。所谓"雪崩"其实是把结构化的字段挨个拼起来,不是不可逆的整体混淆。

###  加密流程

####  整体结构

basearr由多个段拼接而成,每段前面带一个类型/长度前缀:


    basearr = numarrJoin(  3, sec1,  10, sec2,  7, [codeUid],  6, sec6,  2, fixedValue20,  9, sec9,  13, [0])

####  env-fixed字段

跨会话恒定的部分,直接对应浏览器环境属性,一次采集可以长期复用:

sec1段本身也是这么拼出来的,几个字段各自的来源:


    maxTouchPoints        直接取值,当前环境是0evalLen                eval函数toString后的字符串长度,固定33uuid(UA)               CRC32(navigator.userAgent)platform               len前缀 + ”Win32”屏幕尺寸               935/996/1086/1010,四个数分别是inner/outerHeight/Width一个固定校验值         CRC32('/')的结果,恒为[121,211,210,212]

CRC32('/')这种对固定字符串取校验和的写法,单看很像某种指纹哈希,只是往sec1里塞一个恒定不变的占位校验值。

####  会话相关字段

sec2里有两个时间戳,一个是秒级、一个是毫秒级,都是当次请求时刻的Date.now(),纯计算得到,不依赖任何运行时状态。sec6的第二个元素来自一次实打实的加密运算,不是简单的哈希值:


    sec6[1] = encryptMode2(decrypt(keys[22]), keys[16], 1)

fixedValue20是从一张会话内洗牌过的查找表里取值:用keys[29]到keys[32]四个派生密钥当索引,在洗牌表里查出对应的4个字节。

####  外层两层加密

basearr经property57编码之后,要过两层AES-CBC才变成最终的P
cookie。第一层最初被记成"整体和key2做异或",这个结论是从密文和key2的字节对齐规律里推出来的,复现出来的cookie却始终和真实抓包对不上。

往下查证据是解密方向反推:把真实P cookie按标准AES-
CBC解一遍,IV位置固定取key2的前16字节,能干净解出basearr原文;而"异或整个key2"这种猜测在超过16字节之后就开始和真实密文对不上。第一层的真实结构就是:


    AES-CBC(key17, iv = key2[:16])

解密出basearr之后,外面还包了一层frame:


    frame = 时间戳(r2mkaTime, startTime) + keys[2] + 调试标志位 + 长度信息

frame再过第二层AES-CBC(key16,IV是随机值),最后用自定义base64编码,才是完整的P
cookie。两层AES叠起来看容易觉得是同一把锁上了两道,key、IV、加密对象三样其实都不一样,是两道独立的锁,不是同一把锁转了两圈。

###  完整链路回顾

四篇写完,现在能把整条链路从头到尾拼成一份可执行的清单:


    curl请求412挑战 → 响应体给出 nsd(种子) / cd(编码数据) / O(完成态标记)  → derive_keys(nsd, cd) → keys(45个派生密钥)  → vm_full(nsd) → kH(动态源码塔,~293KB,每会话重新生成)  → codeUid = (CRC32(one) ^ CRC32(two)) & 0xFFFF       one = CRC32(functionsNameSort[keys33].wrapper)       two = CRC32(mainFunction.substr(741*keys34, 741))  → 合成basearr(约150字节):       80字节env-fixed段:一次采集,长期复用       70字节会话相关段:sec2时间戳/sec6=encryptMode2(...)/                        fixedValue20查表/codeUid写入sec3  → LCG(15679,2531011)+Fisher-Yates置换(920/920验证)  → property57 Huffman编码(codebook 256符号验证)  → AES-CBC(key17, iv=key2[:16]) → 包frame(时间戳+keys[2]+调试位+长度)  → AES-CBC(key16, iv=随机) → 自定义base64P cookie → 提交请求 → 200(12/12)

拼这份清单之前,链路上四处地方都拿到过错误结论,回头看正好连成一条线:property57的codebook被decoy骗成"session-
derived";codeUid早期样本只验证了公式的一半;basearr被当成不可拆解的雪崩混淆;外层加密被记成"整体异或"而不是AES-CBC。

四处错误的共同点是都只看了一部分证据就下了结论,样本不够多、观测点不够干净。换成更完整的多会话交叉验证和不侵入源码的观测方式后,四处全部被纠正回真实公式。

###  落地验证

拿真实请求测试basearr里每个字段是否被服务端校验:sec2、sec3(含codeUid)、fixedValue20这几段字节改了会直接拒;env字段模板、sec6的部分字节、结构性占位段改了不影响请求结果。离线合成的basearr走完两层AES-
CBC和base64编码后提交,能拿到200,和用真实浏览器生成的P在服务端看来没有区别。

###  小结

这个案子最大的认知转折是先入为主的"雪崩混淆不可拆解"这个判断本身是错的,换一层观测视角就能看出结构,不是破解了某个具体公式。150字节里八成是可以一次性采集、长期复用的环境常量,真正每次都要重新计算的部分很小,而且集中在少数几个可以单独验证的字段上。这套basearr结构目前在fangdi这一个目标上验证过,遇到类似"看起来不可拆解"的载荷,欢迎评论区聊聊你们是怎么找到切入点的。
