## 正文

> 本文仅做技术方法论分享,不提供可直接使用的完整实现,请勿用于未经授权的用途。

yuanrenxue
match/28的反爬参数token,算法本身是标准的RSA-1024,没有自定义密码原语。真正决定能不能离线复现的是它的填充方式:标准PKCS  #1
v1.5填充里随机字节部分被写死成了固定值,同一段明文永远算出同一段密文。

RSA运算不是明文调库,是塞进一台52-handler的JSVMP栈机里跑jsbn大数库的modPow执行的。离线签名器验证过,拿服务端下发的时间戳换算token,请求真实接口拿到200和真实数据。

##  环境

match/28的接口是GET /api/question/28,签名参数是token。token的结构:


    明文 = ”/api/question/28” + now + ”28” + ”$” + page填充 = PKCS#1 v1.5 type-2: 00 02 [填充字节×N] 00 <明文>密文 = 填充后的block ^ 65537 mod N (RSA-1024, e=65537)token = base64(密文)

now来自服务端接口/api/getTime下发,不是本地时钟。RSA本身不难,难的是这段运算被编译进了一台每次访问都重新生成的JSVMP栈机,静态读不出计算过程。

##  加密流程

###  VM执行栈机

RSA运算不是JS直接调crypto库,是一台单分派器线程栈机在跑,大致形状:


    (function p(n,o,u,t,i,h,c,f,s,r,a){  h = [ /* 52个handler */ ];  for (; !c; ) try { h[n[o++]]() } catch(e) {}  return f;})(...)

n是程序数组,o是指令指针,i是操作数栈,u是帧链,h  n[o++]
就是"取一条指令,查表执行"的标准字节码派发循环。这个分派函数p在一次签名里被递归调用2984次。

RSA用的大数库是jsbn(一个纯JS大数库,曾经不少站点拿它实现RSA),用28位一组的limb数组表示大整数,这些数组就活在VM的操作数栈i上。RSA模数N不是从源码字符串里抠出来的,是直接从操作数栈上的limb数组重建出来的整数。

###  52个handler做什么

52个handler拆完是一套完整的栈机指令集,覆盖压栈取值、算术、位运算、比较、控制流、属性访问、函数调用、字符串解码、自修改这九类:


九类里前八类是随便一台栈机VM都会有的标配,单独看没什么特别的,真正带来分析难度的是最后两个:h[7]这个字符串解码器意味着连API路径这种字符串常量都不会明文出现在字节码里,得跑起来才能看到解码结果;h[12]更麻烦,执行到这条指令,程序数组本身被替换成从当前位置往后的切片,静态反汇编到这条指令就断了,只能动态跟。

###  N怎么从操作数栈里重建

jsbn把RSA大数拆成若干个28位一组的limb,存成一个普通JS数组,形态大致是[limb0, limb1, limb2,
...],每个limb取值在0到2^28-1之间,按小端权重limb[k] *
2^(28*k)累加起来才是完整的1024位模数。这些limb数组从头到尾都待在VM的操作数栈i上,跟其他临时值混在一起进进出出,不会以数组字面量的形式出现在源码里。

要拿到N,不用去反混淆源码,在h[49]调用modPow前后截一次操作数栈快照,栈上能定位到一段连续的、长度和数值范围都符合28位limb特征的数组,按上面的公式重建成整数就是完整的RSA模数,位长和真实抓包解出来的密文长度对得上,可以交叉验证。

##  填充写死0x01:确定性从哪来

标准PKCS  #1  v1.5 type-2填充,00
02之后跟的那段填充字节应该是随机生成的非零字节,这是设计规范的一部分,为的是同一段明文每次加密出不同密文,不能被拿去做确定性分析。match/28这里填充字节全部固定成0x01,不是随机的。

这个"本该随机却写死"的细节,是整段分析里最关键的一步:填充一旦固定,同一段明文(接口路径+时间戳+题号+分隔符+页码)永远算出同一段密文,才有可能绕开"这台VM每次访问都重新生成"这堵墙,不用跑VM本身,直接在VM外面用标准RSA库重算整个填充和幂运算过程。

##  站点的反调试手段

match/28没有单独的debugger语句或者插桩检测,防的方式是结构性的,不随每次访问VM重新生成而改变:

JSVMP栈机把算法编译成字节码  :RSA运算全在这台VM里跑,看不到明文的crypto调用,只能看到一堆opcode派发。

XOR-85隐藏字符串常量  :接口路径这类字符串不会明文出现,得等h[7]解码器跑起来才现形。

自修改字节码打断静态反汇编  :h[12]执行到就把程序数组原地替换成后半段切片,静态工具在这条指令上直接断轨,只能上动态跟踪。

VM每次访问都重新生成
:opcode编号会跟着漂,同一个handler这次访问是h[7],下次访问可能变成别的数字。单个断点在固定位置蹲守基本抓不到东西,得对每个匹配的脚本文件都下断点,才能稳定命中。结构性结论(栈机执行方式、XOR-85解码、jsbn大数运算、自修改这几点)不随编号漂移改变。

##  小结

match/28这个案子里,RSA-1024标准算法查文档就有,真正值得记录的是"填充本该随机却被写死"这一个实现细节,直接决定了这套签名能不能离线复现。VM栈机、XOR-85解码、自修改字节码这些手段挡住的是静态分析,挡不住这一个填充字节的观察结果,这套方法目前在match/28这一个目标上验证过。遇到类似的标准算法配反常参数的组合,欢迎评论区聊聊你们是怎么揪出那个反常参数的。
