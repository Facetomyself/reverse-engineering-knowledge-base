## 正文

> 本文仅做技术方法论分享,不提供可直接使用的完整实现,请勿用于未经授权的用途。

yuanrenxue match/10的反爬参数m,算法本身没有自定义字节码VM,全是标准密码原语的组合:AES-256-CBC、AES-
CBC、SHA-1、CRC-8、自定义base64、XOR。读通全部原语只是第一步,最后验证出m的每个字节都能从静态程序数据、请求时间和URL算出来,连浏览器都不用起,纯HTTP请求就能连续凭空签出5页真实数据。

##  环境

match/10接口/api/question/10带一个签名参数m,不带或算错直接拒。签名逻辑写在页面JS里,标识符全是_yrx前缀的乱码名,函数体是能直接读的标准JS,不是编译成字节码的自定义VM,难点在一堆同名近似名的函数里认出谁是谁。m的结构:


    m = ”4” + customBase64( material65 XOR chk 65B 会话数据与校验和逐字节异或 + chk 1B CRC-8(多项式0x07) + AES-256-CBC(plaintext,key) 96B 确定IV(16)+密文(80),会话块 + AES-CBC(reqData,tailKey) 48B 随机IV(16)+密文(32),逐请求尾部)

##  加密流程

###  整体结构

plaintext(68字节)由时间戳16字节、4字节会话值、48字节请求常量段拼成,aesKey是两段SHA-1交错生成,tailKey经过一次非标准长度的AES密钥扩展:


    plaintext(68) = 时间16B + 会话4B + new_wp(请求常量段48B)aesKey(32) = 交错( SHA1(keyMat+nmu)[:16], SHA1(其它派生值)[:16] )tailKey = 密钥扩展(Nk=16, Nr=22, 非标准长度) ↑ 标准AES是Nk=8,这里内部函数总返回16元素数组, 不够的位置留空,JS空位在位运算里当0处理

###  第一次误判


    误判1:fn-io看到__webdriver_evaluate/__selenium_evaluate字符串 → 以为m读自动化工具指纹 → 实际:该函数是字符串解码器,返回的是混淆数据里的常量串 → 真正读navigator的函数不在m的调用路径上 误判2:哈希初始化前4常量MD5/SHA-1公用,只看4个就认成MD5 常量 = [0x67452301, 0xEFCDAB89, 0x98BADCFE, 0x10325476, 0xC3D2E1F0] ^^^^^^^^^^ 第5个,MD5没有 轮常量 = 0x5A827999 ← SHA-1专属,MD5不用这套机制 → 看完5个常量+轮常量,确认是SHA-1,换算法就对上

##  reqData里一个带bug的SHA-1

尾部AES加密的reqData前16字节,是对大写请求URL做哈希得到的,标准SHA-1对不上,原因是这个SHA-1实现本身有bug:


    标准SHA-1最后一块: W[0..13] = 消息内容(含padding) W[14:16] = 消息总长度(64位大端) ← 关键的长度字段 这个实现的最后一块: block = new Array(16) # 固定16个位置,不会自动扩容 block[0..13] = 消息内容(含padding) block[14], block[15] = undefined # 长度字段从未被写入,静默清零
     # undefined在算术/异或里都当0,不抛异常也不截断 复现要求:刻意把W[14]/W[15]置0,不能按RFC算出真实长度再填进去

##  从抓包复现到零浏览器凭空签名

###  静态数据能算多少

细拆每个字段的来源:


    material65 ← 池字符串(纯静态字面量,连config都不需要)时间16B ← 老时间常量(写死在字面量里,非实时)+ 当前时间戳拼接会话4B ← b64解码(池字符串切片 + config某键值)[:4]请求常量段48B ← 若干固定常量 + 时间衍生值 + 一段AES-128解密结果aesKey32B ← 两段SHA-1交错,输入来自config + 实时秒数

material、时间16字节、会话4字节、请求常量段全部能从程序里的静态字面量加请求参数算出来,不用任何浏览器运行时状态。但第一版"m全部字段都能凭空算"的结论站不住:


    以为的情况:静态字面量 == 服务端下发的原始代码,拿来直接用真实情况: 静态字面量来自一次运行时反混淆快照 真实下载的响应里配置对象/长字符串根本不存在(count=0) 同一接口每次请求都重新随机混淆几十万字节 连同一会话重复请求,内容都不一样⟹ 凭空算的前提,其实是运行时VM先把配置解码出来这一步已经替别人做完了

###  全新会话独立验证


    新会话(sec与旧会话不同)→ 从静态配置+URL+时间逐块独立重算 → 对比真实wire m结果:全部字段一次性对上意义:排除”凑巧对上旧会话捕获值”,证明算法本身是通的

###  零浏览器凭空签名


    第一步(同会话离线伪造): 运行期输入 = 请求时间戳 + URL参数(仅此两项) 密钥、尾部全部前向算出 → 拼出m → CDP替换浏览器发出的真实m 结果:服务端200 + 真实数据 第二步(完全去掉浏览器): sec ← 接口响应头里的服务端时间 一次性随机值 ← 另一个接口的响应内容 配置 ← 本地保存的静态配置(一次性解码,长期复用) 纯前向计算出完整m → 直接请求 结果:200 + 真实数据

浏览器唯一不可替代的工作只是第二步里"配置"那一次性解码,拿到之后不需要navigator指纹、canvas、webdriver检测规避,或任何其它浏览器状态。

##  落地验证

用零浏览器方案连续翻页请求第1到第5页,每页都拿到不同的真实数据:


    page1: {”data”:[182460, ...]}page2: {”data”:[565849, ...]}page3: {”data”:[631989, ...]}page4: {”data”:[518538, ...]}page5: {”data”:[”请”,”将”,”UA”,”改”,...]} ← 末页提示,翻到头了


    会话内只定一次,后续每页复用: 时间相关常量(sec/IV) ← 每页重算反而对不上服务端记录的会话时间每页都要更新: 一次性随机值 + 页码对应的URL哈希

##  小结

match/10的m拆开全是标准密码原语,真正的难点在认清哪些字段是静态的、哪些字段只需要确定一次、哪些字段每次请求都要重新算,这个分类比破解某一个具体算法更重要。零浏览器凭空签名是验证算法闭环最强的方式,推导出的公式如果连服务端下发内容之外的东西都不需要,签名照样成立,说明公式是真的对。这套方法目前在match/10上完整跑通,遇到类似的多阶段签名,欢迎评论区聊聊你们的拆解思路。
