# 同一个 signer 的两条调用面：请求签名与 Cookie 维护

> 来源: null119 提供的 Elong 接口测试会话导出；仅提炼同一签名 SDK 的调用面混淆与报告纠偏。
> 原始发布时间: 2026-06-22（导出文件标注）
> 归档日期: 2026-09-27
> 分类: web-reverse
>
> 找到 signer 还不够。业务 GET 与 Cookie 维护可能调用同一个导出，却使用不同 URL、body 和消费位置。复制错调用点时，SDK 可以正常出值，HTTP 也可以返回 200，但业务结果仍被拒绝。

## 来源中的转折

| 证据等级 | 静态材料显示的过程 | 限制 |
|---|---|---|
| 来源自述 | 早期采用真实浏览器调度；中途称请求已成功，后续又发现业务字段缺失和拒绝码；末段称纯 Node 路线可用 | 本篇不确认任一路线当前有效 |
| 静态核验 | 导出后半段将真实 GET 的 signer 调用与维护 Cookie 的调用分开：前者没有 body，后者带设备标识相关 body；并明确修订早期文档 | 确认的是会话内部证据与结论发生修正，不是外部服务器规则已被独立证实 |
| 独立运行复现 | 本次为 0 | 未执行 SDK、浏览器或网络请求 |

该会话是「文档已收口，后续又暴露缺口」的例子。最终摘要应保留纠偏链，而不是把前后多次成功声明叠加成更高可信度。

## 调用面表比函数名更重要

| 调用面 | 输入差异 | 输出消费位置 | 应验证什么 |
|---|---|---|---|
| 业务 GET | 完整 URL 与实际 query；是否无 body 由调用点确定 | 当前请求头或 query | 签名输入与实际发送字节一致 |
| Cookie 维护 | 设备或上下文 body，以及自己的调用条件 | Cookie 或状态缓存 | 更新触发、值来源、作用域与生命周期 |

以上是来源该版本的区分，不是所有 SDK 的通用参数规则。不要把维护路径的 body 搬到 GET，也不要因为字段名相似就断言请求头必然等于某个 Cookie。

定位时记录「谁调用、传什么、输出交给谁、何时更新」，而不仅是 signer 函数地址。两个调用共享导出，仍可能属于不同协议状态机。

## 失败归因的正确顺序

先检查实际调用点与输入合同，再检查状态来源，最后用受控实验区分环境和传输因素。来源曾怀疑新浏览器画像、Cookie 历史和时效窗口，这些都只能是待验证假说；若同时改变持久化状态、采样时间和请求参数，后续成功不能证明某个单因素就是根因。

HTTP 200 后仍需解析业务码和目标数据结构。空字段、拒绝码或验证页面不能被「签名长度正确」「前缀相同」「任务状态 completed」覆盖。旧字段名与实际响应结构不一致时，也应先确认响应类型，而不是一律按风控处理。

## 可复用验收清单

1. 将页面真实业务请求与维护调用分别记录为 fixture，保留资源版本和调用栈证据引用。
2. 对照 URL 编码、字段顺序、body 是否存在，以及 signer 返回值的消费位置。
3. 只改变一个变量；环境、会话、传输和业务参数的实验分开记录。
4. 本地出值、字节 parity、业务读回分别验收；不让一个阶段替代另一个。
5. 回写已经失效的早期结论，并标出新结论适用的版本窗口。
