# JSVMP 动态版本：重试成功不等于提取器修复

<details data-kb-history="legacy-metadata">

> 动态 JSVMP 的结构、opcode 与 key 构造方式会随资源变化。一次失败后换新资源重试，可能只是绕开不支持的变体，并没有修复分析器。可靠性指标要以资源版本和失败谱系分组，而不是只看最终成功次数。

## 与已有 TDC 文章的区别

现有 [TDC 算法分析](./tencent-tdc-slider-vmp-part2-tea-collect-pow.md) 和 [XTEA 提炼案例](./tencent-tdc-slider-xtea-purecalc.md) 讲插桩、轮结构和输入输出。本篇不重复算法、动态 key、指纹或验证码求解过程，只分析「旧样本能处理，新样本失败」应如何记录与验收。

## 来源中发生了什么

| 证据等级 | 可保留的事实 | 边界 |
|---|---|---|
| 来源自述 | 会话称已建立 opcode 分析、key 提取与候选实现，并进行过调用测试 | 这些成功声明未在本次重新执行 |
| 静态核验 | 导出末段记录提取器报错：key builder 未覆盖全部预期索引；随后把底层 `ValueError` 转换为上层可重试异常 | 这是异常分类调整，不是支持缺失变体的证明 |
| 独立运行复现 | 本次为 0 | 未验证任何当前资源、端点或通过率 |

末段总结仍提及这一兼容性问题。因此不能用「任务完成」「重试生效」覆盖更具体的未解决事实，也不能把异常捕获当作新 opcode 已被识别。

## 失败谱系最小记录

每次分析绑定资源 hash 与来源时段，保留 bytecode/dispatcher 的版本线索、分析器版本、输入类型、目标边界以及失败阶段。原始资源可以只在受控证据区保存，公开报告仅留下结构和结论。

| 失败阶段 | 示例 | 应记录的结论 |
|---|---|---|
| 资源获取 | 内容缺失、截断或不是目标脚本 | acquisition failure，不能算算法失败 |
| 解析与映射 | opcode 或构造器形态无法匹配 | 当前变体不支持；保存最小反例 |
| 语义提取 | 预期槽位缺失、位宽或 signedness 未确认 | 候选不完整，不填默认值继续 |
| 本地对拍 | 候选与原始执行不一致 | 保留首个分叉和对应输入 |
| 下游请求 | 本地一致但业务拒绝 | 与资源时效、会话和请求面分别分析 |

同一资源重试、同类新资源重试和换了变体重试必须分开统计。第三种即使最终成功，也只说明至少一种变体可处理。

## 真正修复的验收

1. 保留原失败资源，定位缺失槽位来自哪个 handler、常量构造或控制流分支。
2. 修复后先用同一失败资源回放，确认不是换样本掩盖问题。
3. 在多个独立资源变体上交叉验证；资源数量本身不是充分条件，重点是覆盖结构差异。
4. 对齐候选与原始执行的输入、状态、位宽、输出和必要副作用；未知 opcode 或未确认分支继续标未知。
5. 将解析兼容性、本地语义一致和下游业务结果分别报告，不合成一个模糊的「成功率」。

无需将整个 VM 还原为源码才能修复边界。若宿主原语已提供稳定观测点，可先按 [宿主原语分流](./vmp-host-primitive-to-purecalc.md) 缩小问题；但更小的边界仍须绑定动态资源版本。
