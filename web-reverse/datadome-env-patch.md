# DataDome 无感验证补环境

> 来源: 微信公众号转载 / 知识星球技术稿
> 原始发布时间: unknown
> 归档日期: 2026-09-06
> 分类: web-reverse
>
> DataDome 无感 interstitial 的补环境路径：jsdom + vm 跑原脚本出 payload/plv3，难点在 iframe Realm 生命周期、Worker/OffscreenCanvas 异步链、六万步 VM 第一处分叉，以及 CSS 自定义属性驱动的 offsetWidth；成功口径是 view=redirect 后新 Session 连续业务 200。

## 正文

## 前言

前段时间找了个 DataDome 的设备检查练手，本来以为就是常规的指纹补环境：缺什么补什么，最后把参数跑出来就完事。

真正开始做才发现没那么简单。

它不光会读取 navigator、screen、Canvas、WebGL，还会创建 iframe 检查不同 Realm，读取 DOM 布局、CSS 自定义属性、调用栈，最后再把数据送进一个自定义 VM。最麻烦的是，Node 本地可以正常出值，但“能出值”和“值正确”完全是两回事。

整个分析前后做了不少对照，最终实现的效果是：

*   最终 payload、plv3 由 Node.js + jsdom + vm 生成；

*   无感验证返回 view=redirect；

*   只带生成的 Cookie，新建 Session 连续访问目标页和首页都返回 200。


下面把整个过程梳理一下，重点说几个比较难定位的地方。

## 目标网站

地址做了 Base64 处理：

```
aHR0cHM6Ly93d3cueWVscC5jb20vc2VhcmNoP2ZpbmRfZGVzYz1KYXBhbmVzZSZmaW5kX2xvYz1Nb3VudGFpbitWaWV3JTJDK0NB
```

本次只研究设备检查的无感流程。浏览器使用全新 Profile，Cookie 全部清空，即可稳定触发无感设备检查。

## 抓包分析

先直接请求目标页面，返回状态码 403，响应服务器是 DataDome，同时下发一个临时 datadome Cookie。

403 页面里包含生成设备检查地址所需的信息，主要有：

*   cid：本次 Challenge 标识；

*   hash：站点配置标识；

*   e、s、b：设备检查参数；

*   host：验证服务地址；

*   cookie：初始化时下发的临时值。


根据这些参数拼出 /interstitial/ 地址，再请求一次，就能拿到完整的 Device Check HTML 和核心 JS。

整体请求顺序如下：

```
GET 目标页面
```

### 验证 POST

核心请求是：

```
POST https://geo.captcha-delivery.com/interstitial/
```

请求体里比较重要的参数有：

*   payload：浏览器指纹和环境数据加密结果；

*   plv3：另一段与运行环境、布局和时间相关的数据；

*   cid、hash、seed：Challenge 页面给出的动态配置；

*   env、userEnv：服务端下发的环境标识；

*   ps：页面尺寸相关数据。


服务端返回 JSON。view=captcha 表示升级到了交互验证，本次不分析；view=redirect 且带 Cookie，才算无感验证通过。

## 加密入口定位

核心 JS 在 Device Check 页面内联脚本中，体积接近五十万字节，里面带有一层模块打包和一个自定义 VM。

直接搜索 payload 很容易定位到发送位置。继续往上看可以看到，脚本先调用大量环境采集函数，把字段写入内部容器，最后生成：

```
{
```

随后再将字段集合加密成 payload，通过 XHR 发往 /interstitial/。

入口虽然找到了，但这里不能直接调用内部的 sendPayload()。浏览器中它是由页面初始化、异步探针和定时器自然触发的，如果本地手动调用，字段顺序、时间状态和调用栈都会变化。

所以本地执行器使用 jsdom 创建页面，再通过 vm 执行原始脚本，只把 XHR 替换成请求捕获器。最终请求仍然由目标代码自己触发。

整个补环境和验证过程可以概括为：

```
干净 Chrome 采集
```

## 补环境

先把脚本放到 Node 里跑起来。

常规的 window、document、navigator、screen、Canvas、WebGL 就不展开了，使用 Proxy 记录真实读取，再根据 Chrome 的属性描述符逐项补齐。

但这次真正难的不是普通属性，而是下面几个点。

## iframe 与 Realm

脚本会创建 iframe，再从 iframe 的 contentWindow 中读取 Math、原型链和原生函数信息。

开始时我把 jsdom 暴露出来的内部属性全部删掉，表面上更像 Chrome，但有一个字段始终无法自然生成。继续追调用栈才发现，这个字段其实来自干净 iframe Realm 的 Math 完整性检查。

如果内部资源加载能力一开始就不存在，iframe 虽然能创建，对应 Realm 的行为却不完整；如果一直保留，后面的环境枚举又会检测到它。

最后的处理方式是分阶段控制：

这块不能简单理解成“缺啥补啥”。有些对象只应该在特定时间存在，生命周期不对，属性值再像也没用。

## Worker 与 OffscreenCanvas

Worker 也是比较容易误补的一块。核心脚本不是简单判断 window.Worker 存不存在，而是先生成 Blob，再通过 URL.createObjectURL() 创建地址，随后启动 Worker，等待多组异步消息返回。Worker 内还会读取 UA、语言、硬件并发数，并调用 OffscreenCanvas、WebGL。

Node 中没必要真的启动一个浏览器 Worker，重点是复刻脚本实际走到的最小通信链：

```
Blob 脚本
```

本地先维护 Blob 与临时 URL 的对应关系，再实现 Worker 的构造、postMessage、onmessage、addEventListener 和 terminate。Worker 使用的环境数据从统一 Provider 中读取，消息按照浏览器观测到的顺序异步投递；OffscreenCanvas 则复用已经补好的 Canvas、WebGL 能力。

这里有两个容易踩的坑：一是不能在构造 Worker 时同步返回，否则字段顺序和定时状态都会变化；二是不能直接写死最终字段或密文，只能补 Worker 读取到的环境和通信语义。这样换 Challenge 后，字段仍由原脚本自然生成。

## 浏览器轨迹怎么采

浏览器在这套流程里只负责提供“真值”，不负责生成最终提交值。每次采集都从清空 Cookie 的新 Profile 开始，记录主页面与 iframe 的创建顺序、网络请求、XHR 发起栈、脚本来源、明文字段序列以及关键环境读取。

只抓一遍并不够，因为动态 Challenge、随机数、时间和异步探针都会制造差异。实际做法是跨多个 Challenge 分别采集多次，再把结果分成三类：

*   每次都相同的稳定环境字段；

*   随 Challenge 变化的配置字段；

*   允许出现顺序差异或缺失的异步字段。


稳定部分进入 Provider，动态部分继续从当前页面解析，异步部分则保留明确的允许范围。这样 Chrome 轨迹是校准依据，而不是把某一次浏览器结果整包复制到 Node。

当最终值仍然不一致时，再把范围从“整段脚本”缩到 VM。浏览器与 Node 使用相同的随机、时间序列，在 VM 循环的唯一入口增加轻量记录，只保留 step、pc、sp 和少量观察点。先找控制流第一次分叉，再回头查是哪个环境读取改变了分支，比盯着两段密文猜原因快得多。

## VM 轨迹对比

环境字段补完后，Node 和浏览器都能出值，但 plv3 还是不一致。

核心逻辑跑在自定义 VM 中，一次执行有六万多步。只看最终密文根本不知道哪里错了，于是分别记录浏览器和 Node 的：

*   VM step；

*   程序计数器 pc；

*   栈指针 sp；

*   局部变量读取；

*   关键表和中间数组。


然后逐条比较 (step, pc, sp)，找第一处分叉。

这里有个很关键的思路：最终只差一个字节，不代表错误发生在加密末尾。加密只是把上游的一点语义差异放大了。正确的排查顺序应该是：

```
明文字段
```

修复最早分叉后，同一组随机和时间序列下，浏览器与 Node 的六万多条控制轨迹完全一致，VM 摘要和 plv3 也能逐字节相同。

## DOM 布局

另一个比较坑的地方是 offsetWidth。

第一次抓到浏览器返回 99，Node 返回 0，于是先写死成 99，结果换一个新 Challenge 后，浏览器又变成了 88。

继续查 DOM 和样式才发现，这个宽度来自一整条 CSS 依赖：

```
祖先元素自定义属性
```

Challenge 页面会随机改变祖先变量，所以最终值并不固定。

这里没必要实现完整 CSS 引擎，只需要根据脚本真实读取到的语法，补一个最小解析器，支持继承、var()、calc()、clamp() 和 px 运算。最终布局值从当前页面样式动态计算，不再写死某个像素。

## 异步字段

多次抓浏览器明文时，还发现字段总数偶尔会少一个。

原因是字体、worker 等探针是异步执行的，不同运行中存在合法顺序差异。但也不能因此把校验直接放宽成“少几个无所谓”。

最终做法是用多次独立浏览器结果证明哪些字段确实可选，然后继续严格检查：

*   字段总数和唯一键数；

*   字段集合与出现次数；

*   字段顺序；

*   显式允许缺失的异步字段；

*   Provider 队列是否有缺项或剩余。


这样可以兼容浏览器的自然异步，又不会把 Node 里的真实错误隐藏掉。

```

```

拿到 Cookie 后没有继续复用原 Session，而是新建一个只包含该 Cookie 的干净 Session：

```
目标搜索页：连续两次 HTTP 200
```

第二天拿旧 Cookie 复测已经返回 403，再重新执行一遍 Node 流程，仍然可以签发新 Cookie 并稳定返回 200。这样才能证明通过的是生成链路，而不是某个碰巧还有效的历史值。

## 总结

这次补环境，普通 API 反而不是最难的。

真正花时间的是：

1. iframe Realm 和实现层对象的生命周期；
2. 六万多步 VM 中第一处分叉定位；
3. DOM 布局和 CSS 自定义属性计算；
4. 动态配置与静态运行时代码的区分；
5. 异步字段的合法变体和严格顺序校验。
