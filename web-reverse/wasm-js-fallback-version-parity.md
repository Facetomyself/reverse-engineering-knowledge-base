# WASM 与 JS fallback：先绑定版本，再谈算法一致

> 来源: null119 提供的 `decode__1174` 测试会话导出；仅保留版本错配与输入编码的通用分析方法。
> 原始发布时间: 2026-06-22（导出文件标注）
> 归档日期: 2026-09-27
> 分类: web-reverse
>
> 同一前端里同时出现 WASM、旧 JS fallback 和新 fallback bundle，不表示三者实现同一输入合同。先绑定实际加载的模块与资源版本，再比较入口、序列化和输出；不能拿任意一条同名函数替代当前浏览器路径。

## 来源结论与本次核验

| 证据等级 | 本篇保留的内容 | 不做的外推 |
|---|---|---|
| 来源自述 | 会话经历旧 JS 样本匹配、WASM 样本不匹配，再寻找对应 fallback 的过程；末段声称完成算法与业务测试 | 不把该声明当成当前端点成功 |
| 静态核验 | 导出确实区分不同版本、不同 fallback 资源和编码严格性；匹配/不匹配结果出现在不同阶段 | 文本里的「算法不同」仍需排除输入、常量与状态错配，不能仅凭 mismatch 定论 |
| 独立运行复现 | 本次为 0 | 没有执行 WASM、fallback 或发送业务请求 |

不归档来源中的密钥、访问材料、账号数据、完整请求或下载地址。本文也不复述其业务数据和成功计数。

## 先建资源身份表

| 层 | 需要固定的身份 | 不足以固定身份的线索 |
|---|---|---|
| 页面加载器 | 入口脚本 hash、版本选择分支、实际模块 URL 的证据引用 | 仅凭文件名含相同产品词 |
| WASM | 模块 hash、imports/exports、加载方式与实例边界 | 页面里出现 `WebAssembly` 字样 |
| JS fallback | fallback hash、选择条件及其对应版本 | 函数同名或都叫 sign |
| 输入状态 | 字符串到字节的编码、序列化、字段顺序、时间与上下文来源 | 只有最终字符串长度 |

实际走了哪条分支，须由运行时观测确认。浏览器支持 WASM 不意味着本次一定走 WASM；fallback 存在也不意味着可以无条件替换。

## 找到第一处差异

对同一受控输入依次比较：业务字段、JSON/URL 编码后的文本、传入模块的字节、边界返回值和最终请求字段。若进入核心算法之前字节已不同，应先修复输入合同，而不是继续改密码算法。

WASM 指针/长度接口还应记录 memory 视图有效期、字符串编码、内存增长、返回数据长度和必要的释放责任。JS wrapper 一致只证明边界一致，不等于 WASM 内部语义已恢复。

建议覆盖空串、非 ASCII、保留字符、重复字段、空值和边界长度。对于随机或有状态输入，先固定可控条件或记录来源，不直接要求两个合法输出字节相同。

## 怎样表述结果

- 「旧 JS fallback 匹配旧 fixture」：仅证明该资源与该输入匹配。
- 「同输入下 WASM 与 fallback 不匹配」：先记录边界差异，尚不能自动归因于算法不同。
- 「当前版本边界对拍一致」：限定资源 hash、输入集合和状态，未测路径继续列出。
- 「业务读取成功」：需要当前运行时独立读回；不由离线 fixture 推导。

内部算法恢复的另一类案例见 [WASM 解密分析资料](./wasm-decrypt-ai-one-prompt-recovery.md)。这里的新增重点是版本绑定和边界 parity，不是把某份 fallback 宣称为所有版本的通用替代。
