# AES-GCM 认证加密模式实现 🔝

```
🔗 本章代码对应:04-aes_gcm.py
```

上一篇文章我们学了 AES-CTR,它把分组密码变成了流密码,加密速度可以说是拉满了。但我们也发现了它的致命弱点:没有任何认证能力,攻击者可以随意篡改密文而解密方毫不知情。
GCM(Galois/Counter Mode)就是为了解决这个问题而生的:在 CTR 加密的基础上,增加一套基于伽罗华域(Galois Field)的认证机制,让加密和认证一步到位。这就是 AEAD(Authenticated Encryption withAssociated Data) 的概念。
讲真的,这一对文字看的头疼,简单点就是加密的时候抽一些东西去做hash,然后把hash和密文都给到对方,对方收到后先验证hash,如果不对就直接拒收,如果对了再解密

💡 扩展知识:针对特定场景的高阶/非主流模式 除此之外,密码学界还针对极端场景研发了一些特殊的派生模式。你可以不用写它们的底层板子,但安全分析和底层逆向(如硬件固件和内核层)常碰到:
XTS:全盘加密(像 Windows BitLocker / macOS FileVault)的绝对标准。它不依赖前一个块(为了能随机读取磁盘),而是引入 Tweak 概念(比如把扇区编号揉进加密流),确保把一模一样的明文写在磁盘不同扇区,密文截然不同。

OCB:理论性能极限的最优 AEAD 模式。拥有比 GCM 快得多的速度和并发算力模型,运算量更小。只可惜早期严重受制于严苛的各种专利,在互联网开源大潮里彻底错过了风口。
PCBC:历史长河里想用来极度放大雪崩效应的“翻车变异体”(曾在早期 Kerberos 中风风火火),最终在数学上被查出“交换特定的几个密文块并不影响后面正常解码”的离谱反推漏洞,当场遭到废弃。

GCM 的输入比 CTR 多了一样东西:AAD(Additional Authenticated Data,附加认证数据)。AAD 是你不想加密、但又想保证不被篡改的数据,比如网络包的报文头、消息的发送者信息等。
GCM 的输出也比 CTR 多了一样东西:Tag(认证标签),通常 16 字节。解密时必须验证这个 Tag,如果不一致,说明数据被篡改,直接拒收。

2.2 五步加密流程 🔝

```
1 生成哈希子密钥 H = AES_K(0^128)
把全零的 16 字节用密钥 K 做一次 AES 加密,得到的结果 H 将在后续的 GHASH 中反复使用。
2 构造初始计数器 J0 = IV || 0x00000001
把 12 字节 IV 后面接上 4 字节的 0x00000001,构成 16 字节的初始计数器块。
3 CTR 加密计数器生成密钥流(计数器从 J0+1 开始)
注意:J0 本身不用于加密明文!从 J0+1 开始递增计数器,只递增最后 4 字节。
用 AES 加密每个计数器块得到密钥流,再和明文异或得到密文。
这一步和上一章的 CTR 模式完全一样。
4 GHASH 计算
把 AAD、密文、以及它们的比特长度拼接在一起,通过 GHASH 运算得到一个 16 字节摘要 S。
GHASH 的核心是在 GF(2^128) 有限域上做乘法和异或。
5 计算最终认证标签 Tag = S ⊕ AES_K(J0)
把 GHASH 的结果和 J0 的 AES 加密结果异或,就得到了最终的 16 字节 Tag。
```

## 3. GHASH:GCM 的认证核心 🔝

GHASH 是 GCM 中负责"认证"的关键组件。它本质上是在 GF(2^128) 有限域上做多项式求值。
3.1 GHASH 的输入 🔝
GHASH 接收一个拼接好的字节串,结构如下:

```
| AAD | padding1 | Ciphertext | padding2 | len(AAD)_64bit | len(CT)_64bit |
|     |  补齐到   |            |  补齐到  |                |               |
|     | 16字节倍数|            | 16字节倍数|    8 字节      |   8 字节      |
```

3.2 GHASH 的计算过程 🔝
把上面的输入切成 16 字节的块 X1, X2, ..., Xn,然后迭代计算:

```
Y0 = 0
Y1 = (Y0 ⊕ X1) · H      ← GF(2^128) 乘法
Y2 = (Y1 ⊕ X2) · H
...
Yn = (Yn−1 ⊕ Xn) · H   ← 这就是 GHASH 的输出
```

每一步都是:先异或,再乘以 H。这个乘法不是普通的整数乘法,而是 GF(2^128) 上的无进位多项式乘法。
3.3 GF(2^128) 乘法 🔝
和 AES 中 MixColumns 用到的 GF(2^8) 类似,只不过这里是在 128 位上做。
不可约多项式为:x128 + x7 + x2 + x + 1(对应常数 R = 0xE1 << 120)

```
def gf128_mul(X, Y):
R = 0xE1 << 120
Z = 0
V = Xfor i in range(128):
if (Y >> (127 - i)) & 1:    # 取 Y 的第 i 位
Z ^= V
if V & 1:                    # V 的最低位为 1
V = (V >> 1) ^ R         # 右移并异或 Relse:
V >>= 1
return Z
```

## 5. 解密流程:先验证,再解密 🔝

GCM 的解密顺序非常重要:必须先验证 Tag,再解密。

```
收到: 密文 + Tag + AAD
1 用同样的方式计算 GHASH → 得到 Tag'
2 比较 Tag' 和收到的 Tag
3 如果不一致 → 直接丢弃,不解密(防止了比特翻转攻击)
4 如果一致 → 用 CTR 模式解密密文,返回明文
```

⚠️ 这个顺序至关重要:如果先解密后验证,攻击者可能通过 padding oracle 等侧信道泄露信息。

所以拿到一段密文数据后,拆解方式就是:

```
data = bytes.fromhex("抓到的完整报文")
iv  = data[:12]        # 前 12 字节
ct  = data[12:-16]     # 中间部分
tag = data[-16:]       # 末尾 16 字节
```

## 8. GCM 的魔改方向 🔝

💡 逆向对抗说明:在反作弊和私有协议逆向中,为了防止标准库直接解析,防守方经常会对协议进行“魔改”。由于 GCM 强耦合的认证架构,常见的对抗特征主要集中在以下 9 点:
8.1 替换 GHASH 认证模块 🔝

```
特征:保留 IV、AAD 和 CTR 模式,完全抛弃有限域乘法,Tag 改由 HMAC-SHA256、Poly1305 或魔改哈
```

希生成。

```
逆向点:若 CTR 能解出明文但 Tag 报错,检查生成 Tag 的收尾函数。若无大量的 0xE1 异或与移位操
```

作,即判定 GHASH 被替换。
8.2 篡改不可约多项式常数 🔝

```
特征:将标准的 0xE100...00 替换为其他 128 位合法的不可约多项式(如 0x87)。
逆向点:汇编中搜索 0xE1 常数,若被替换,同步修改还原脚本的常数。
```

8.3 魔改初始计数器 $J_0$ 🔝

```
特征:规范中 12 字节 IV 会拼接 0x00000001 作为 $J_0$。魔改会将其改为 0x00000002 错位起步、改
```

用小端序递增、或强制对 12 字节 IV 也走无固定长度的 GHASH 逻辑。

```
逆向点:直接用 Frida/Unidbg Hook 底层 AES_Encrypt,拦截输入的第一块数据,提取真实的 $J_0$。
```

8.4 魔改哈希子密钥 $H$ 🔝

```
特征:标准 $H = AES_K(0^{128})$。魔改将其改为加密全 0xFF 块,或者不在本地运算,通过服务器直接
```

下发 / 硬编码 16 字节随机数。
逆向点:动态调试提取 GCM Context 头部缓存的 16 字节 $H$。
8.5 篡改内部数据拼接与补齐规则 🔝

```
特征:标准输入严格为 AAD | 0补齐 | CT | 0补齐 | len(AAD) | len(CT)。魔改通常是为了省带宽
砍掉最后的 16 字节长度区,或颠倒为 CT + AAD 分布。
逆向点:动态跟踪 GHASH 的 update 传参,Dump 其内部缓冲区的最后一块数据分析组装结构。
```

8.6 GHASH 白盒化查表 🔝
特征:将有限域乘法完全转化为庞大的查找表(Lookup Tables),并混入非线性随机扰码。
逆向点:静态分析失效。需通过侧信道(DFA 故障注入)或基于状态空间的代数变换去强行推导算式。

```
8.7 修改 Galois Field (GF) 的位序 (Bit Reflection) 🔝
```

特征:GCM 标准规范在多项式乘法时采用极其怪异的“位反射序”(低位在前)。有些外包/自研私有库为图省事或故意扰乱,改写成了人类更习惯的大端字节序,导致 GHASH 结果天差地别。
逆向点:在乘法循环中找寻是否存在位级别的镜像反转汇编指令。若加密流看起来全都对得上但就是 Tag错算,常常就是底层乘法被修改了位序。
8.8 CTR 密钥流双重注入魔改 (Masking) 🔝

```
特征:标准流密码是 明文 ⊕ CTR_KeyStream。高强度反扒防御常常会在生成 KeyStream 后,中途再多
```

异或一层动态生成、与当前业务绑定的“杂音魔数”(比如当前时间戳/设备指纹算出的杂凑流)。
逆向点:如果确信底层完全被攻破,算出的 $J_0$ 完全对的,但用标准库套皮解出的明文依然呈现有规

```
律的周期乱码,去寻找执行 XOR 命令最密集的那一层(往往紧贴内存输出区)。
```

8.9 “画蛇添足”的废数据填充 (Fake Padding) 🔝
特征:GCM 属于纯流密码模型,原理上绝不需要填充(Padding)。但不少开发者刻意在真正发进 GCM引擎前的明文末尾,强行拼接一段定长或变长的伪随机“废数据块”做诱饵。
逆向点:如果你把这套外壳拔掉,发现绝大部分是 JSON 明文,但屁股后面总是拖杂着变动乱码导致序列化出错,直接手动裁剪剥离即可。
