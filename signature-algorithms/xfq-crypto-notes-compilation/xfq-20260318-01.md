我们学完了纯正的流密码序列(RC4、Salsa20、ChaCha20、Rabbit),大家应该清楚了流密码的加密规则就是生成伪随机密钥流,然后和明文做异或(XOR)。
其实在这个思路上,分组密码(如 AES、SM4)也完全可以作为流密码来使用!怎么做呢?这就是我们要讲的CTR(Counter,计数器)模式。

## 1. 什么是 CTR 模式?它解决了什么痛点? 🔝

之前我们在 ECB / CBC 模式下,AES 只能一块一块(每次 16 字节)地加密真正的“明文”。这带来了几个大痛点:
1. 必须填充(Padding):由于必须凑齐 16 字节,最后一块总得走 PKCS#7 填充。
2. CBC 不能并行加密:加密第三块必须要等第二块加密完(因为有前后依赖)。
CTR 模式 的做法极其巧妙:我们根本不把明文扔进 AES 里加密。 我们去加密一个自增的计数器(Counter),
但是这又有一个问题,如果计数器一来就知道是0开始,那么很容易被攻击;这个也很好解决,搞一个初始值就行了,这个初始值叫做Nonce,变化的值叫做Counter,然后组成16字节的整体叫做IV; 然后加密这个计数器就可以得到伪随机密钥流,你可以把它理解成其他算法的密钥流,然后和明文做异或就行了。
CTR 的巨大优势 🔝
1. 无需填充(No Padding):跟流密码一样,不需要填充,来几个字节就取出对应的密钥流然后异或几个
字节;
2. 极致并发(Parallelizable):不管加密哪一块,它的计数器值都是提前算好的(比如第 100 块的计数器

```
就是 初始值 + 100)。多个 CPU 核心可以同时对各种不同位置的计数器进行 AES 加密,速度非常快;
```

3. 加解密代码一致:流密码的特性,加密是异或,解密还是异或,不需要调用 AES 的逆运算逻辑

```
(InvSubBytes 之类的统统不需要)。
```

## 2. CTR 模式的核心结构:彻底搞懂 Nonce、Counter 与 IV 🔝

⚠️ 这三个词在不同的文档和库里经常被混着用,是 CTR 模式里最容易搞晕的地方。别急,我们一层一层拆开来看。
2.1 唯一确定的事实:喂给 AES 的输入块,永远是 16 字节 🔝
AES 是一个分组密码,无论什么模式,它每次只吃 16 字节(128 bit) 的输入。在 CTR 模式中,这个 16 字节的输入叫做 Counter Block(计数器块)。
所以不管外面怎么称呼,最终拼出来送进 AES 加密的那个东西,一定是 16 字节。这是铁律。
2.2 Counter Block 的内部结构:Nonce + Counter 🔝
这 16 字节内部,逻辑上被切成两段:

```
|<================ 16 字节 Counter Block =================>|
|         Nonce(固定部分)        |    Counter(自增部分)   |
|     在一次加密会话中保持不变      |   每加密一块就 +1        |
```

Nonce(Number used Once):顾名思义,"只用一次的数"。在同一个密钥下,每次加密新消息时必须换一个新的 Nonce(绝对不能重用!但可以公开传输)。它的作用是保证:即使你用相同密钥加密相同明文,每次产出的密钥流也不一样。
Counter:纯粹的计数器,从 0(或 1)开始,每生成 16 字节密钥流就 +1。它的作用是保证:同一条消息内部,每一块的密钥流也不一样。
2.3 关键问题:Nonce 和 Counter 各占几个字节? 🔝

在 CBC 模式中:IV 就是那个 16 字节的初始随机块,概念清晰,没有争议。

2.5 本文代码的做法(最直观的方式) 🔝
我们采用的是传入16字节的形式,和前端加密库是一样的(cyberchef背后用的库crypto-js 默认就是16字节)
1. 外部传入一个完整的 16 字节初始块(我们在代码里既叫它 Nonce 也叫它 IV,因为它就是完整的初始
Counter Block)。
2. 把这 16 字节解析为一个 128 位大端整数。
3. 每加密完一块,就让这个 128 位整数 +1,转回 16 字节后再喂给 AES。

```
初始 Counter Block:  7869616f66656e67 3132333435363738
(  "xiaofeng"  )  ( "12345678"  )
← 完整的 16 字节当作一个大整数来自增 →
第 0 块输入: 7869616f66656e673132333435363738  (原始值)
第 1 块输入: 7869616f66656e673132333435363739  (末尾 +1)
第 2 块输入: 7869616f66656e67313233343536373a  (再 +1)
...
```

这种做法没有显式区分"哪几个字节是 Nonce、哪几个字节是 Counter",而是把整个 16 字节当成一个巨大的计数器来递增。简单、有效、且完全符合 NIST SP 800-38A 的规范。

3.2 第 0 块:AES 加密“计数器”产出密钥流 🔝
我们把初始的 16 字节计数器扔进了 AES 加密器中。虽然它只是一个极其规律的字符串(甚至如果是全 0),但AES 在经过了整整 10 轮的(SubBytes 替换、ShiftRows 移位、MixColumns 混淆、AddRoundKey 密钥异或)
之后,吐出了一块毫无规律的 16 字节乱码。这就是我们的密钥流(Keystream)!

```
--- 第 0 块密码流生成 ---当前计数器块(hex): 7869616f66656e673132333435363738
初始状态矩阵: [[120, 102, 49, 53], [105, 101, 50, 54], [97, 110, 51, 55], [111,
103, 52, 56]]
... (历经 10 轮 AES 内部核心运算 ...)
轮10结果: [[254, 182, 91, 162], [100, 114, 83, 55], [136, 76, 153, 216], [150, 65,
88, 253]]
生成的密钥流(hex): fe648896b6724c415b539958a237d8fd
```

```
我们的明文只有 8 个字节 (xiaofeng)。太简单了,直接从生成的 16 字节密钥流里按需截取出前 8 个字节,进
```

行逐位异或:

```
逐字节异或操作:
[ 0] 'x'(0x78) ⊕ 0xfe = 0x86
[ 1] 'i'(0x69) ⊕ 0x64 = 0x0d
[ 2] 'a'(0x61) ⊕ 0x88 = 0xe9
[ 3] 'o'(0x6f) ⊕ 0x96 = 0xf9
[ 4] 'f'(0x66) ⊕ 0xb6 = 0xd0
[ 5] 'e'(0x65) ⊕ 0x72 = 0x17
[ 6] 'n'(0x6e) ⊕ 0x4c = 0x22
```

至此,8 字节的明文完美变成了 8 字节的乱码密文!不需要任何 PKCS#7 填充的痕迹,干净利落。 如果要进行

```
解密,逻辑是100%一样的:把上面那个同样的初始计数器扔进 AES,算出一样的 fe6488...,然后跟密文

```

如果明文超过 16 字节怎么办?很简单,将计数器 +1 (即最后字节变成 0x39),然后走一轮完美的 AES,
得出新的 16 字节密钥流,继续跟后面的明文异或。
3.4 揭秘本质:CTR 就是用 ECB 加密计数器 🔝
一句话总结 CTR 的本质:用 ECB 模式加密"计数器"得到伪随机密钥流,再拿密钥流异或明文得到密文。
我们可以用本文的数据来验证这一点——拿同样的密钥,用 ECB 模式直接加密我们的计数器块,看看产出是不是一模一样的密钥流:

```
1 ECB 加密的密钥:   7869616f66656e677869616f66656e67  ("xiaofengxiaofeng")
2 ECB 加密的输入:   7869616f66656e673132333435363738  (计数器块,即
"xiaofeng12345678")
3 ECB 加密的输出:   fe648896b6724c415b539958a237d8fd  ← 这就是密钥流!
和 3.2 节中 CTR 模式生成的密钥流 fe648896b6724c415b539958a237d8fd 完全一致!
```

然后拿密钥流和真正的明文异或:

```
4 真正的明文:       7869616f66656e67  ("xiaofeng",仅 8 字节,截取密钥流前 8 字节)
5 密钥流 ⊕ 明文:   860de9f9d0172226  ← 最终密文
```

💡 所以你完全可以这样理解:CTR 模式 = ECB 加密计数器 + XOR。ECB 本身不安全是因为"相同明文块 → 相同密文块",但在 CTR 里我们喂给 ECB 的"明文"是不断 +1 的计数器,永远不会重复,所以反而变得安全了。

## 5. CTR 模式的致命弱点 🔝

只要是流密码(包括 ChaCha20,或者现在的 AES-CTR),都有一个致命的安全漏洞:比特翻转攻击(Bit-flipping attack)。
由于密文只是简单的明文和密钥流异或,如果攻击者在网络上截获了密文数据包,并且他猜到了某个位置的字符,他就可以精确地篡改密文包里的 0 和 1(例如把“向小明转账”偷偷修改为“向黑客转账”)。 当你收到被篡改的密文并重新异或时,解密程序完全不知道数据被改过,它只会傻傻地解密出一个变了质的假明文!
光有“加密(即让你看不懂)”是不行的,密码学还需要提供“认证(Authentication:保证没被别人篡改过)”!
这就是为什么业界抛弃了纯正的 AES-CTR 和纯正的 ChaCha20,全面转向了 AEAD(认证加密)时代。
