## 明文填充(Padding) 🔝

遵循规则就完事了: MD5算法要求输入消息的长度必须是512位(64字节)的倍数。为了满足这个要求,MD5算法会对输入消息进行填充。 md结构(merkle-damgard结构,此处的md不是md5的md,md5的md是messagedigest)要求尾部留有8字节来存储原始消息的长度,所以实际填充需要让最后一个64字节填充到56字节就结束, 最后再加个8字节的原始消息长度。
规则就 3 步:

```
1. 先补一个字节 0x80
2. 再补若干个 0x00,补到长度 % 64 == 56
```

3. 最后补上原始消息长度(bit位长度)的 8 字节小端序
至于你在网上看到的什么补1再补0,wiki百科也是这么写的; 不过那个只是算法设计,具体怎么实现得站在字节角度,逆向也是一样;
0x1000 0000=128=0x80
代码里对应的写法是:

```
original_bits_len = len(self.message) * 8
message = bytearray(self.message)message.append(0x80)
while len(message) % 64 != 56:message.append(0x00)
message += struct.pack("<Q", original_bits_len)
```

## 初始寄存器(ABCD) 🔝

这个也是由于merkle-damgard结构带来的,MD5 一开始有 4 个固定的 32 位寄存器:
密码学忌讳莫名奇妙的常量,所以这里实际上是0-f然后f-0,挨个取4字节 01 23 45 67转大端序变成0x67452301类似这种过程得到的;
代码里对应:

## 64轮压缩流程 🔝

MD5 的核心就是对每一个 64字节块 做 64 轮压缩,这里的压缩说白了就是打乱的效果,就是把这64字节块参与到一个运算,这个运算就是初始abcd到最后的abcd。
其中64大轮,每一轮的运算涉及到下面这个式子:

```
f_value      = F/G/H/I(b, c, d)
f_add        = f_value + a + T[i] + M[g]
f_rotate     = left_rotate(f_add, S[i])
b_new        = b + f_rotate
寄存器轮转:a, d, c, b = d, c, b, b_new
```

代码里对应的是:

```
f_value = f
f_value_add = (f_value + a + self.T[i] + M[g]) & 0xFFFFFFFF
f_value_rotate = self.left_rotate(f_value_add, self.S[i])
b_new = (b + f_value_rotate) & 0xFFFFFFFF
a, d, c, b = d, c, b, b_new
```

四个布尔函数 🔝
MD5 可以分成 4 大轮,每大轮 16 步,也就是一共64小轮:

```
第 0-15 步:F
第 16-31 步:G
第 32-47 步:H
第 48-63 步:I
```

代码:

```
if 0 <= i <= 15:
f = (b & c) | (~b & d)
g = i
func_name = "F"elif 16 <= i <= 31:
f = (d & b) | (~d & c)
g = (5 * i + 1) % 16
func_name = "G"elif 32 <= i <= 47:
f = b ^ c ^ d
g = (3 * i + 5) % 16
func_name = "H"elif 48 <= i <= 63:
f = c ^ (b | ~d)
g = (7 * i) % 16
func_name = "I"
```

这里是核心部分,merkle-damgard结构要安全都是基于这一块儿,所以如果你遇到改了布尔函数的地方都是不规范的,一般来说顶多是交换一下函数,不会自己乱改;
感兴趣的朋友看我代码的注释,这里面涉及选择函数、奇偶校验函数等等;像是sha1还会引入多数表决函数; 后续我可能会在密码学专栏写一些理论,聊聊为什么这么设计算法;

```
每一大轮的 g 索引 🔝
这里的 g 很关键,因为它决定了64轮中本轮到底取哪个 M[g]。
第1轮(F): g = i
第2轮(G): g = (5*i + 1) % 16
第3轮(H): g = (3*i + 5) % 16
第4轮(I): g = (7*i) % 16
```

所以从日志里看:

```
第 0 轮直接取 M[0]
第 1 轮直接取 M[1]
```

...

```
到第 16 轮开始,g 就不按顺序走了
```

这也是区分“标准核心”很重要的观察点。
这里也有一个点需要注意,所有的g都是0-16的数,那么一共4大轮,每个明文块都会被四大轮使用一次; 而且格外注意第一大轮,他的i是连续的,我们后续根据这个特点可以从trace日志中提取出明文,这对于ollvm/vmp的md5算法格外有效,使用了类似merkle-damgard结构的算法都可以的;

## 最终 digest 是怎么出来的 🔝

日志最后是:

```
last:  39dc0ae1 ab59ba49 57e056be 3e880ff2
e10adc3949ba59abbe56e057f20f883e
```

这里最容易懵的是:

```
ABCD = 39dc0ae1 ab59ba49 57e056be 3e880ff2
```

为什么最后 digest 不是把这 4 个值直接拼起来,而是:

```
e10adc39 49ba59ab be56e057 f20f883e
```

原因很简单:公式确实是拼起来,但是 MD5要求了 输出时每个 32 位寄存器按小端序写入。
比如:

```
A = 39dc0ae1
```

按小端打包后就是:

```
e1 0a dc 39
```

同理:

```
B = ab59ba49 -> 49 ba 59 ab
C = 57e056be -> be 56 e0 57
D = 3e880ff2 -> f2 0f 88 3e
```

拼起来就是:

```
e1 0a dc 39 49 ba 59 ab be 56 e0 57 f2 0f 88 3e
```

也就是:

```
e10adc3949ba59abbe56e057f20f883e
```

# 魔改md5 🔝

直接拿我的py跑一下,观察一下每一轮的输入部分哪一个地方出问题了,就可以快速定位了;

## 改输入层 🔝

这个是最常见的。
常见写法:

```
1. salt + message
2. message + salt
```

3. 前后拼固定字符串

```
4. 先 hex/upper/lower/urlencode/base64/xor 再 md5
```

5. 先做一次别的哈希/加密,再把结果喂给 md5

```
这种情况下,MD5核心往往还是标准的,只是你看到的 M[g] 已经不是原始明文了。这种情况的对抗也很简
```

单,找到明文添加的函数,如md5_update是最经典的,进阶手法是直接找md5_final拿到context,然后利用context结构体包含明文信息,从而提取出来,这个我在我的语雀文章中实战过了; 最顶级的手法就是直接从trace日志中找到规则然后提取,这种是可以应对哦利率m/vmp化的。

## 改 padding 🔝

这个也很常见,而且很容易在日志里发现。直接跟上一个坐一桌去,要么ida直接看出来,要么trace中看出来;
一般很少有人吃饱了没事干动这里;

## 改消息字装载方式 🔝

标准 MD5 是把 64 字节块按 16个小端32位字 拆开:

```
M = struct.unpack("<16I", chunk)
这一步如果被改了,后面所有的 M[g] 都会跟着变。
```

常见魔改:
1. 改成大端装载

```
2. 每个 word 先 bswap
```

3. 16个 word 顺序重排
4. 每个 word 额外 xor 一层

```
这种情况很容易误判成 g 索引改了,实际上 g 可能没动,变的是 M[g] 本身。
```

## 改各种常量 🔝

常见就是改下面这些:

```
1. 初始 ABCD
2. T 表
3. 左移量 S
4. g 索引公式
```

其中:

```
改 ABCD 最好抓 chunk[0] 的初始寄存器
改 T 表可以从ida常量池、trace、或者直接从加法处提取(编写idapython脚本或者正则表达式)
改 S 表通常能从 rotate 指令的立即数看出来
改 g 索引的话,M[g] 的访问顺序会整体变掉
```

## 改核心:四个布尔函数 🔝

这个一般不能乱改,因为安全性主要就靠这里。
常见情况:

```
1. 交换 F/G/H/I 的使用顺序
```

2. 对某个函数做一点微调
3. 完全自己写新的布尔表达式
这种对抗也不难。
如果你发现:

```
T、S、M[g] 都能对上
但是 f_value 死活对不上
```

那基本就是布尔函数这里动了。

```
逆向时直接盯着 f_value 的生成过程看就行,IDA 可读性高的话直接看伪代码;如果混淆比较重,就看汇编里and/or/xor/not 怎么拼。
```

## 改寄存器轮转顺序 🔝

这个点很多人会漏掉,但它其实很关键。

```
标准 MD5 每一步最后不是简单把 a 改掉就完了,而是:
a, d, c, b = d, c, b, b_new
```

也就是说每一轮结束后,四个寄存器会按固定方式轮转。
如果这里改了,比如:

```
a, b, c, d = d, b_new, b, c
```

或者别的交换顺序,那么你会发现:
当前轮也许还能算通

```
但从下一轮开始,a/b/c/d 的来源全乱了
```

这种魔改很容易被误判成“布尔函数不对”或者“常量不对”,实际上是寄存器传递链断了。

## 改核心迭代公式 🔝

标准写法里最核心的一步就是:

```
b_new = b + left_rotate(f + a + T[i] + M[g], S[i])
```

这里如果改了,影响会非常大。
常见魔改:

```
1. 不加 b
2. 改成加 c 或 d
```

3. rotate 前后多做一次 xor/add/sub
4. 每几轮额外混入一个常量

```
5. 把 + 改成 ^
```

这种时候你会看到:

```
f_value 是对的
M[g] 是对的
T/S 也是对的
但 b_new 对不上
那就别再怀疑前面了,直接盯住 f_add -> f_rotate -> b_new 这一段。
```

## 改轮数或大轮结构 🔝

标准 MD5 是:

```
4大轮 * 16步 = 64步
```

有些魔改会:
1. 增加轮数
2. 减少轮数
3. 交换四大轮顺序
4. 某一大轮重复一次
这种情况下日志节奏会很怪。
比如:

```
标准第 0-15 步应该全是 F
第 16-31 步应该全是 G
第 32-47 步应该全是 H
第 48-63 步应该全是 I
```

如果你在 trace 里看到这个节奏不对,那说明已经不是标准 64 轮结构了。

## 改块尾 feed-forward 🔝

这个点前面提过一次,这里再单独强调一下。
标准 MD5 每个块结束后要做:

```
self.A = (self.A + a) & 0xFFFFFFFF
self.B = (self.B + b) & 0xFFFFFFFF
self.C = (self.C + c) & 0xFFFFFFFF
self.D = (self.D + d) & 0xFFFFFFFF
```

如果这里被改成:

```
xor
```

交叉相加
只更新一部分寄存器
额外混入随机数/时间戳/计数器,什么LCG函数就是;

```
那么单块时你可能只觉得最终 ABCD 不太对; 多块时就会更明显,因为下一块的初始 ABCD 也会跟着错。
```

所以多块消息场景下,这一层非常好抓。多块的场景也很多,什么hmac就会引入;

## 改尾部digest 🔝

```
还有一种情况是:前面的 MD5 压缩流程都标准,块尾 ABCD 也标准,但最后输出前又做了一层处理。
```

比如:

```
1. ABCD 的拼接顺序改了
```

2. 不按小端输出,改成大端
3. 只取其中8字节或16字节的一部分

```
4. 输出前再做一次 xor/add/LCG
5. md5(md5(msg))
```

这种时候最容易出现的现象就是:

```
你对日志里的 ABCD 很有信心
```

但最后字符串就是和标准 md5 对不上
那就别死盯着 64 轮了,应该回头看:

```
ABCD -> digest
```

这一步中间是不是又包了一层。

## 伪魔改 🔝

还有一类很恶心,看着变了,实际上没变。
比如:

```
1. F/G/H/I 换成等价布尔表达式,这种直接看效果就可以,xhs的案例就是这样;
```

2. rotate 用别的写法实现,依旧是看效果就行

```
3. T 表运行时现算,不直接写死,从trace日志中提取即可
```

4. 常量拆成几段再加起来,这种很典型,shein的案例中就是这样
这种东西本质上不是算法魔改,只是实现写法魔改。
所以别看到代码长得不像 RFC/openssl 写法,就以为核心被改了。判断标准永远应该是:

```
f_value 对不对
M[g] 对不对b_new 对不对
块尾ABCD 对不对
```
