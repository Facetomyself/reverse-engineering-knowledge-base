流密码的本质
所有流密码本质都是 密钥扩展器:把短密钥扩展成任意长度的伪随机流,然后 XOR 明文。每个流密码都分两步:
阶段
作用
类比
1 密钥调度(Key Setup)
短密钥 → 内部状态
往搅拌机里放原料
阶段
作用
类比
2 密钥流生成(PRGA)
内部状态 → 伪随机字节流
持续输出混合物
四种流密码的重心各不相同:

```
RC4:               KSA 复杂(256轮洗牌),PRGA 简单(查表)
Salsa20/ChaCha20:  Key Setup 极简(填矩阵),核心在 20轮ARX
Rabbit:            Key Setup 中等(交叉+4次迭代),G函数平方运算  ← 本文
```

Rabbit 的设计比较均衡:Key Setup 有 4 次迭代做混合,PRGA 靠平方运算提供非线性。它是唯一用乘法(平方)而不是 S-box 或 ARX 做非线性的流密码。

## 1. 密钥初始化

Rabbit 的状态由 8 个 32 位状态变量 + 8 个 32 位计数器 + 1 位进位 组成。

```
def _key_setup(self, key: bytes):
# 将密钥转换为4个32位字
k = [int.from_bytes(key[i:i+4], 'little') for i in range(0, 16, 4)]
# 交叉初始化状态和计数器for i in range(8):if i % 2 == 0:state[i] = k[i % 4]
counter[i] = k[(i+1) % 4]else:state[i] = k[(i+2) % 4]
counter[i] = k[(i+3) % 4]
# 初始化进位
carry = 0
# 迭代4次充分混合for _ in range(4):
_next_state()
# 用混合后的状态重新初始化计数器for i in range(8):
counter[i] ^= state[(i+4) % 8]
```

交叉初始化:密钥字被交错放入状态(state)和计数器(counter),确保密钥的每个部分都影响到多个位置。

def _iv_setup(self, iv: bytes):

# 按照 RFC 4503 的方式用 IV 修改计数器counter[0] ^= v0

## 3. 状态更新与密钥流生成

对计数器进行系统更新是流密码区别于分组密码的关键步骤**。 每一次密钥流生成,Rabbit 都会首先用这一步推开密码状态的“轮转”。
3.1 计数器更新:对抗周期的基石

```
流密码最怕生成重复的状态(也就是死循环周期太短)。Rabbit 为每个计数器配了一个不可思议的固定常数(A
数组),并通过一个跨越所有计数器的全局进位 carry 串联它们:
流密码就怕状态进入循环周期,Rabbit 通过给每个计数器加上一个带魔法数字的固定常数(A),并通过 carry
```

串联进位,保证它的周期极长:

```
A = [0x4D34D34D, 0xD34D34D3, 0x34D34D34, 0x4D34D34D,
0xD34D34D3, 0x34D34D34, 0x4D34D34D, 0xD34D34D3]
old_carry = carryfor i in range(8):
val = counter[i] + A[i] + carry
counter[i] = val & 0xFFFFFFFF
carry = val >> 32  # 溢出作为进位传递到下一个字
原理与效果: A[i] 看起来像一堆魔法乱码(各种 4D34D34D),但它们其实来自于根号 2 和 根号 3 之类
无理数的小数部分。 在这个循环里,counter[i] 会源源不断地与 A 叠加,并且它的溢出位并没有丢
掉,而是赋值给了 carry,在下一次循环中被当作 +1 加给了下一个计数器。 这种利用 常数增加 + 级
```

联进位 的设计,保证了 Rabbit 的内部周期极其绵长(达到 $2^{256}$ 量级),几乎不可能出现短循环陷阱。
3.2 G 函数(核心非线性):不用 S盒,用平方
我们在 RC4 里看到了查表洗牌,在 Salsa20 里看到了单纯的模加法。Rabbit 最独特的地方来了——它用平方运算来实现非线性混淆:

```
g = [0] * 8for i in range(8):
val = (state[i] + counter[i]) & 0xFFFFFFFF
sq = val * val     # 32位值平方,变成64位结果
g[i] = ((sq >> 32) ^ sq) & 0xFFFFFFFF  # 将平方的高32位与低32位做异或
```

为什么偏不用查表或者普通的位运算? 对于现代 CPU 来说,32 位数字的“乘法(平方)指令”不仅速度快,几乎 1 个周期就能算完,而且它是极好的非线性制造机。 32位数字相乘后变成 64位长。把高32位

```
折回和低32位异或(^),相当于把高低位狠狠揉捏在一起。结果就是:输入只要稍微有一丁点不同,输
```

出结果立刻天差地别,并且找不出简单的线性代数推导式。这就是极致压缩性能下的非线性核心。
3.3 新状态混合:经典的 ARX 回归
将这8个 g 函数的结果提取出来后,Rabbit 并不是简单异或,而是像 Salsa20/ChaCha20 那样用加法和左移,实现彻底的融合:

```
new_state = [0] * 8
# 将每一个状态,混合自己、紧接其后的循环左移16位结果、以及再往后的循环左移16位或8位结果
new_state[0] = (g[0] + rotl(g[7], 16) + rotl(g[6], 16)) & 0xFFFFFFFF
new_state[1] = (g[1] + rotl(g[0], 8)  + g[7]) & 0xFFFFFFFF
new_state[2] = (g[2] + rotl(g[1], 16) + rotl(g[0], 16)) & 0xFFFFFFFF
# ...剩余以此类推
state = new_state
原理解密: g 值已经足够混乱了,但如果不进行扩散,每个词组的混淆就只能限制在局部。 这里的做法
非常鸡贼:让当前的 g[x],加上自己左侧的 g(挪位 16或8位)再相加。 回想一下 —— 模加法
```

(Addition)、循环位移 (Rotation)、在之后的过程里还要用到异或 (XOR) —— 是不是又回到了和ChaCha20 一模一样的基本组件(ARX 结构)? ARX 这种结构能用最少的指令跑出最强的雪崩效应。

```
注意:网上部分教程和代码在这一步写成了异或(以为是 g[0] ^ ...),这样失去了模加法带来的进位
```

雪崩效应!

## 6. 常见变种与非标准实现

Rabbit 知道的人少,用的人也少;而且结构特殊,因此魔改也相对较少。

6.3 著名实现脱轨案例:CyberChef 或者前端 cryptojs 密码学库
我们实现的代码或者某些语言的标准密码学库跑出了官方 RFC 4503 全部的 Test Vector 数据,但在安全圈常用的在线加解密网站 CyberChef 或者 cryptojs 密码学库上测试 Rabbit,不管调整大小端序都对不齐结果(在我

```
们的案例中它会输出类似 38a6c7... 而不是预期的结果)。
```

这时候别怀疑自己,这是因为CyberChef 内部的 Rabbit 存在极其诡异的魔改解析逻辑。CyberChef 的 Rabbit模块很难和标准的 RFC 工具对齐,核心原因在于它执行了以下几个在任何官方 Rabbit 文档内都找不到的“风骚操作”(特别是在涉及到非 16 字节整数倍对齐的碎块处理时):
1. 诡异的大端组合解析(针对其特有 Big 模式):它会将输入的小端 Key 和 IV 在转为 32 位整型(Words)
前,全部倒序组合。正常应该是顺着填入,但它自己使用了一套反向组合公式读取字块。
2. 截断流末尾当开头去异或(针对其核心异或提取):这是最致命的一点。如果你输入的明文(比如

```
xiaofeng)只有 8 字节,它不足 Rabbit 一轮产出的 16 字节密钥池。标准的流密码法则应该是,取密钥
```

池的前 8 个字节去异或。而 CyberChef 却会去读取该块密钥流的最后部分字节来倒序配对异或!
为了证明其魔改,我们直接翻阅 CyberChef 原生 js 源码库(src/core/operations/Rabbit.mjs) 中的源码。它的异

```
或提取阶段 extract() 函数是这样写的:

* Extract keystream
*/

// 这里它先算出了最后无法被 16 字节整除的“小尾巴”的起点和长度

}
正因为这一段原生纯 JS 逻辑存在,导致哪怕在网页上我们正确地选对了 Endianness: Little 的选项,只要

S 的末尾(S[8]到S[15])去异或你的明文,而不是用最开头的 S[0]到S[7]。这种反常识的截位拼接注定了它

和其他任何常规 Rabbit 实现的完全割裂。

```
在每一次调用 _next_state 之后,生成 16 字节密钥流:
```

2. CryptoJS / CyberChef 内部强加的双重端序反转魔改 由于它内部使用 32-bit WordArray (本质上是大端存
```

储),所以它硬生生地在生成字数组后,对这 4 个完整的大字(而非字节)做了极其扭曲的内存端序翻转拼合!
