# 一、流密码总论

## 1.1 什么是流密码?

加密方式分两大类:分组密码和流密码。
通俗理解:
分组密码像快递打包:你写了一封信,快递公司要求"每个包裹必须装满 16 个字"。信不够 16 个字?拿填充物塞满再封箱。每个箱子单独加锁,锁法一样但钥匙不同。
流密码像水管加密:你一边写信,信纸一边通过一根管道流出去。管道里有一条"密码带",信上每个字经过管道时,和密码带上对应的字做一次异或,就变成了密文。写多少加密多少,不需要凑满一箱。

```
分组密码:  [明文] → 切成固定大小的块 → 每块单独加密 → [密文块1][密文块2]...
"HelloWorld!!" → ["Hell"]["oWor"]["ld!!"] → 逐块加密(不够要填充)
流密码:    [明文] → 逐字节和密钥流异或 → [密文]
"HelloWorld!!" → 每个字符 ⊕ 密钥流对应字节 → 来多少加密多少
```

## 1.2 流密码的核心思想

流密码做的事情其实很简单——把短密钥"拉长",然后和明文逐字节异或。

```
举个例子:你的密钥只有 3 个字节 abc,但明文有 8 个字节 xiaofeng。密钥不够长怎么办?
第1步:密钥扩展(把短密钥"拉长"成和明文一样长的伪随机流)
密钥: "abc" (3字节)
↓ 经过一系列复杂的搅拌/洗牌...
密钥流: b3 b8 26 ae 0a a3 30 7c  (8字节,看起来完全随机)
第2步:逐字节异或
明文:    x    i    a    o    f    e    n    g
78   69   61   6f   66   65   6e   67
密钥流:  b3   b8   26   ae   0a   a3   30   7c
─────────────────────────────────────
密文:    cb   d1   47   c1   6c   c6   5e   1b
```

利用上面这个简易表格很好理解。
不同的流密码,区别就在于第 1 步"怎么把短密钥拉长成密钥流":RC4 靠洗牌,Salsa20/ChaCha20 靠矩阵搅拌,Rabbit 靠平方运算,ZUC 靠 LFSR + S-box 非线性函数。但第 2 步都一样——异或。

短密钥 → 内部状态
RC4 最复杂,Salsa20 最简单
2 密钥流生成(PRGA)
内部状态 → 伪随机流
这里是各算法的核心区别

```
加密就是异或:密文 = 明文 ⊕ 密钥流 解密也是异或:明文 = 密文 ⊕ 密钥流(同一个密钥流,异或两次
```

流密码的安全性取决于一件事:密钥流够不够随机。如果密钥流是真随机的,就是一次性密码本(OTP),理论上不可破解。流密码用伪随机来逼近这个理想。

## 1.3 流密码与一次性密码本(OTP)

历史上最安全的加密方式是一次性密码本(One-Time Pad):密钥和明文一样长,完全随机,只用一次。理论上绝对不可破解。
但问题是:如果你要加密 1GB 的文件,就需要 1GB 的密钥——这没法用。
流密码就是 OTP 的"实用化版本":用一个短密钥(比如 32 字节)通过算法"拉长"成 1GB 的伪随机密钥流。虽然不是真随机,但足够接近,实际中在可控计算范围内很难被攻破。

```
OTP:    真随机密钥(和明文一样长) ⊕ 明文 = 密文    ← 绝对安全,但密钥太长不实用
流密码: 伪随机密钥流(由短密钥生成) ⊕ 明文 = 密文  ← 实用,安全性取决于算法质量
```

## 1.4 流密码的两种类型

流密码按密钥流的生成方式分为两类:
1 同步流密码(Synchronous)—— 密钥流只取决于密钥和 IV,和明文/密文无关。

```
密钥 + IV → [密钥流生成器] → K1 K2 K3 K4 ...
⊕  ⊕  ⊕  ⊕
明文:                          P1 P2 P3 P4 ...
```

发送方和接收方必须严格同步,丢一个字节后面全错
传输中某个 bit 被翻转,只影响那一个 bit(不会扩散)
本系列的 RC4/Salsa20/ChaCha20/Rabbit/ZUC 都是同步流密码AES-CTR 和 AES-GCM 也属于同步流密码——CTR 模式用计数器生成密钥流,GCM 在 CTR 的基础上加了认证(GMAC),加密部分本质一样
2 自同步流密码(Self-synchronizing)—— 密钥流取决于之前的密文。

```
密钥 + 前n个密文 → [密钥流生成器] → Ki
⊕
明文:                                Pi
```

即使传输中丢了几个字节,接收 n 个正确密文后能自动恢复同步但一个 bit 错误会影响后续 n 个 bit(有限扩散)
分组密码的 CFB 模式就是一种自同步流密码
为什么要知道这个分类? 因为它直接影响实际使用:同步流密码(RC4/ChaCha20 等)如果传输丢包,
必须重新同步或重传;自同步流密码能自动恢复,但有错误扩散。现代网络协议(TLS/WireGuard)选择同步流密码,配合可靠传输层(TCP)保证不丢包。

## 1.5 CTR / GCM 模式:分组密码变流密码

我们前面已经学了分组密码(AES/DES/Blowfish/Twofish),其实只要用 CTR(计数器)模式(Counter),分组密码就变成流密码了。而 GCM(Galois/Counter Mode)= CTR 加密 + GMAC 认证,加密部分和 CTR 完全一样,只是额外加了一个 Galois 域上的 MAC 来保证完整性(防篡改)。

```
AES-CTR:
AES(key, nonce||0) → 密钥流块0 (16字节)
AES(key, nonce||1) → 密钥流块1 (16字节)
...
密文 = 明文 ⊕ 密钥流
ChaCha20:
ChaCha20_block(key, nonce, 0) → 密钥流块0 (64字节)
ChaCha20_block(key, nonce, 1) → 密钥流块1 (64字节)
...
密文 = 明文 ⊕ 密钥流
```

结构完全一样! 区别只是生成每个密钥流块的方法不同。所以 AES-CTR 和 ChaCha20 本质上是同一类东西。

## 1.8 关键安全原则

1. 永远不要重用密钥流

```
如果用同一个密钥+nonce加密两段不同明文:
C1 = P1 ⊕ K
C2 = P2 ⊕ K
攻击者算 C1 ⊕ C2 = P1 ⊕ P2,密钥流消失了!
```

这就是 WEP 被破解的根本原因——RC4 没有 nonce,密钥重用。
2. 流密码不提供完整性
流密码只管加密,不防篡改。所以实际应用总是配合 MAC 使用:

```
ChaCha20 + Poly1305 = ChaCha20-Poly1305(AEAD)
AES-CTR + GMAC = AES-GCM(AEAD)
```

3. Nonce 不需要保密,但必须唯一 同一密钥 + 不同 nonce → 完全不同的密钥流

下面带大家手搓一个最简单的流密码练练手:rc4,也是我们最常遇见的流密码; 很多案例中都或多或少会用到的,我印象中第一次遇到这个算法是在 boss直聘 案例的sp参数算法中;
RC4 算法核心主要分为两步:

```

```

## 2.2 密钥调度算法 (KSA) —— "洗牌"

```
KSA 的目标:用密钥把一个有序数组 [0, 1, 2, ..., 255] 打乱成密钥依赖的排列。
```

通俗理解:想象一副 256 张的扑克牌,按 0~255 编号整齐排列。KSA 就是根据密钥,把这副牌彻底洗乱。洗完之后,每张牌的位置取决于密钥——不同密钥洗出不同的顺序。

```
def _ksa(self, key: bytes) -> list:
key_length = len(key)
# 1. 初始化 S-box: [0, 1, 2, ..., 255]
S = list(range(256))
# 2. 用密钥洗牌(256 轮交换)
j = 0for i in range(256):
j = (j + S[i] + key[i % key_length]) % 256
S[i], S[j] = S[j], S[i]  # 交换
return S
核心公式就一行:j = (j + S[i] + key[i % key_length]) % 256
```

这份公式只需要有印象即可,不需要记

```
j 是上一轮的结果(累积的)
S[i] 是当前位置的值
key[i % key_length] 是密钥循环取字节
```

三者加起来取模 256,得到要交换的位置
密钥只在这里用到!之后的 PRGA 阶段完全不再碰密钥。

## 2.3 伪随机生成 + 加密 (PRGA) —— "边发牌边加密"

这是很多人最容易困惑的地方。 S-box 不是一个静态的密码本,它是一个动态变化的转盘:
每处理一个字节,S-box 内部都会再交换一次位置(自己再洗一次)。 这里我理解的是为了防止知道字节之间的某种转换关系,然后大量测试拿到一个字典,然后通过查字典进行加密解密;

```
所以即使明文里有重复的字(比如 xiaofeng 里的两个 f),生成的密钥流字节也不同
def _prga(self, S: list, data: bytes) -> bytes:
i = 0
j = 0
result = []for byte in data:
# 1. S-box 转动(每次都变!)
i = (i + 1) % 256
j = (j + S[i]) % 256
S[i], S[j] = S[j], S[i]  # 再次交换
# 2. 生成密钥流字节 K
K = S[(S[i] + S[j]) % 256]
# 3. 异或加密result.append(byte ^ K)
return bytes(result)
```

每一步做了三件事:

```
1. 转动 S-box:i 每次 +1,j 根据 S[i] 跳转,然后交换 S[i]↔S[j]
2. 取牌:用 S[i] + S[j] 算出一个索引,从 S-box 查出密钥字节 K
```

3. 异或:明文字节 ⊕ K = 密文字节
测试数据(逐字节加密过程):

## 2.4 为什么加密 = 解密?

RC4 加密就是异或,而异或的核心特性:A ⊕ B ⊕ B = A

```
加密: 明文 ⊕ K = 密文
解密: 密文 ⊕ K = 明文  (因为 明文 ⊕ K ⊕ K = 明文)
```

只要用同样的密钥重新跑一次 KSA + PRGA,生成的密钥流完全一样,异或回去就得到原文。
测试数据:

```
加密: 'x'(0x78) ⊕ K(0x97) = 0xef  (密文)
解密: 0xef ⊕ K(0x97) = 0x78 = 'x'  (原文)
解密成功: True
```

## 2.5 RC4 的安全问题

虽然 RC4 简洁优雅,但它有几个已知弱点:
1. 密钥流偏差:前几个字节的密钥流不够随机(和密钥有统计相关性),攻击者可以利用大量密文推断密钥

```
2. Nonce 重用灾难:如果用同一个密钥加密两段不同的明文,攻击者异或两个密文就能消除密钥流:C1
⊕ C2 = P1 ⊕ P2
```

3. WEP 被破解:Wi-Fi 的 WEP 协议因为 RC4 + 弱 IV 设计被快速破解,是 RC4 退出历史舞台的标志性事件
实践中的缓解措施:丢弃前 256~1024 字节的密钥流(RC4-drop),但现在更推荐直接用 ChaCha20 替代。

## 2.6 小结

RC4 是流密码的入门教材,理解了"密钥流 ⊕ 明文"的核心思想,后面学 Salsa20/ChaCha20/Rabbit/ZUC会非常顺畅。完整的五种流密码对比见上面 1.6 节的表格。

# 三、常见变种与非标准实现

RC4 代码极短,因此魔改点非常集中且容易识别。

## 3.1 常见配置差异(非标准配置)

1. RC4-Drop (抛弃前 N 字节)
这是最广泛使用的变种(甚至比标准版更常见)。 原因:RC4 初始阶段的密钥流有统计偏差,不够随机。 做法:在 KSA 后,PRGA 预跑 N 轮(通常是 256, 768 或 1024 轮),丢弃这些输出,然后再开始加密明文。
识别:如果你看代码里在加密循环之前,有一个空转的循环(比如循环 1024 次),那就是 RC4-Drop。
2. 密钥长度
RC4 支持 1~256 字节的变长密钥。最常见是 16 字节(128位)或 32 字节(256位)。有些旧系统可能用 5 字节(40位,极不安全)。

## 3.2 算法核心修改(真正的魔改)

1. S-box 初始化修改

```
标准 RC4 初始化是 S[i] = i。 魔改:S[i] = 255 - i(逆序)或 S[i] = i * 3 % 256 等奇怪的填充方
```

2. 状态数组大小 (N)
标准 N=256 (2^8)。 魔改:
N=512:数组开到 512,模数变成 512。
