## 正文

问题：unidbg中使用DynarmicFactory后端工厂导致的无限debugger
复现环境：样本：酷安v9.6.3的x-app-token；使用的hook方式是emulator.attach().addBreakPoint；其他样本目前没有这个问题
解决办法：使用其他后端，测试均无这问题；
原因： Dynarmic 的断点实现是半成品，只能触发断点进调试器，不支持断点回调机制。

unidbg使用dunarmic产生无限debugger断点触发时的调用链:
Dynarmic 引擎
    ↓ 触发 EXCEPTION_BREAKPOINT
DynarmicBackend.handleExceptionRaised(pc, exception=8)
    ↓ 传递 svcNumber=0 (被写死的)
interruptHookNotifier.notifyCallSVC(this, EXCP_BKPT, 0)
    ↓
AbstractARMDebugger.brk(pc, svcNumber=0)
    ↓ 无法找到对应的 BreakPointCallback
直接调用 debug() → 进入调试器循环

核心问题：DynarmicBackend.handleExceptionRaised() 传递的 svcNumber 永远是 0，而不是 bkpt 指令中的立即数。

对比 Unicorn2：Unicorn2 后端在触发断点时，会正确解析 bkpt 指令中的编号，传递给回调系统，所以能正确执行 BreakPointCallback。
Dynarmic：断点触发 → 找不到回调 → 进入调试器 → 你按 c 继续 → PC 没变 → 再次触发断点 → 无限循环
Unicorn2：断点触发 → 找到回调 → 执行回调 → 回调返回 true → 跳过调试器 → 正常继续
