## 正文

## 一句话结论

这套功能解决的是：**目标 App 可以照常打开 `FLAG_SECURE` / `SurfaceView.setSecure(true)`，App 自己看到的保护状态也尽量保持不变，但系统实际截图、录屏、scrcpy/qtscrcpy 拉屏时不再因为 secure layer 变黑**。

它不是“普通三方 App 准确检测到投屏”的方案。普通 App 对 scrcpy/qtscrcpy 这种底层拉屏通常拿不到可靠事件；所以我们在 ROM 层绕过的是屏幕采集黑屏保护，而不是在 demo 里假装检测到了投屏。

## 当前状态

| 能力 | 状态 | ROMManager 开关 | 核心位置 |
| --- | --- | --- | --- |
| Window 级 `FLAG_SECURE` 绕过 | 已实现并刷机实测 | `screen_secure_bypass` | `WindowState.isSecureLocked()` |
| `SurfaceView` / `SurfaceControl` 子层 secure 绕过 | 已实现并刷机实测 | `screen_secure_bypass` | `SurfaceControl.Builder/Transaction` |
| 远控/注入输入特征伪装 | 已实现并刷机实测 | `input_touch_spoof` | `InputDispatcher` |
| 普通 App 层实时发现 scrcpy/qtscrcpy 投屏 | 不承诺 | 无 | 需要 ROM/native 侧链路，不放 demo 里伪造 |
| DRM / protected buffer 绕过 | 未做 | 无 | `hasProtectedContent=true` 属于另一条链路 |

## 入口与配置

ROMManager 入口：

```text
ROMManager -> 应用设置 -> 目标 App -> 调试 Debug
  - 屏幕内容保护绕过
  - 真人触摸伪装
```

对应属性：

```text
persist.rommgr.app.<package>.screen_secure_bypass=1
persist.rommgr.app.<package>.input_touch_spoof=1
```

ROMManager 勾选这两个开关后会立即：

1. 写入 per-app property；
2. 自动 `force-stop` 目标 App；
3. 如果目标 App 有启动入口，则自动重新启动。

这么做的原因是窗口和 Surface 状态通常在 Activity/Surface 创建阶段计算，只改 property 不重启目标进程很容易看不到效果。

## 为什么一开始“暂停能看，播放黑”

以 `cn.ieway.evplayer` 为例：

```text
APK:   /home/xiaofeng/Desktop/reverse/samples/cn.ieway.evplayer/1.8.2.apk
视频:  /home/xiaofeng/Desktop/reverse/samples/cn.ieway.evplayer/boss_1.ev4a
包名:  cn.ieway.evplayer
播放:  cn.ieway.evplayer/.ui.player.EVPlayerActivity
内核:  libijkplayer.so / libijksdl.so / libijkffmpeg.so
```

逆向和运行态看到它播放视频时走 IJK + `SurfaceView`。旧版只改了 WindowManager：

```text
WindowState.isSecureLocked() -> false
```

这只能处理窗口级 `FLAG_SECURE`。播放时视频画面在独立的 `SurfaceView` / BLAST 子层里，App 又单独把子层设成 secure：

```text
SurfaceFlinger 播放态：
SurfaceView[cn.ieway.evplayer/...EVPlayerActivity](BLAST)
  isSecure=true
  hasProtectedContent=false
```

所以现象就是：

- 暂停态：UI 层能被采集，看起来没问题；
- 播放态：真正的视频 SurfaceView 子层还是 secure，采集结果黑屏或 0 字节。

这不是 DRM：`hasProtectedContent=false`。它只是普通 secure layer 没被吃掉。

## 实现分层

### 1. Window 级 secure 绕过

Patch：

```text
patches/20260710-screen-guard-bypass/frameworks_base_screen_guard_bypass.patch
```

文件：

```text
frameworks/base/services/core/java/com/android/server/wm/WindowState.java
```

逻辑：

```java
boolean isSecureLocked() {
    if (isXfScreenSecureBypassEnabled()) {
        return false;
    }
    // 原始 FLAG_SECURE / DevicePolicy 判断
}
```

效果：App 可以继续设置 `WindowManager.LayoutParams.FLAG_SECURE`，但 WindowManager 不再把这个窗口当 secure layer 参与截图/录屏黑屏判断。

### 2. SurfaceView / SurfaceControl secure 子层绕过

Patch：

```text
patches/20260710-surface-secure-bypass/frameworks_base_surface_secure_bypass.patch
```

文件：

```text
frameworks/base/core/java/android/view/SurfaceControl.java
```

覆盖点：

```text
SurfaceControl.Builder.build()
SurfaceControl.Builder.setFlags()
SurfaceControl.Builder.setSecure()
SurfaceControl.Transaction.setSecure()
```

这些位置都会读取：

```text
persist.rommgr.app.<pkg>.screen_secure_bypass
```

命中后把 `SurfaceControl.SECURE` 从真正发给 SurfaceFlinger 的 flags 里清掉。

关键语义：**不要求目标 App 不调用 `setSecure(true)`，而是在 framework 侧让这个 secure 标志不落到 SurfaceFlinger。**

### 3. 远控/注入输入伪装

Patch：

```text
patches/20260710-screen-guard-bypass/frameworks_native_input_touch_spoof.patch
patches/20260710-input-touch-spoof-jitter/frameworks_native_input_touch_spoof_jitter.patch
```

文件：

```text
frameworks/native/services/inputflinger/dispatcher/InputTarget.h
frameworks/native/services/inputflinger/dispatcher/Entry.h
frameworks/native/services/inputflinger/dispatcher/Entry.cpp
frameworks/native/services/inputflinger/dispatcher/InputDispatcher.cpp
```

数据流：

```text
WindowInfo.packageName / ownerUid
  -> InputTarget.targetPackageName / targetOwnerUid
  -> DispatchEntry.targetPackageName / targetOwnerUid
  -> startDispatchCycleLocked() publishMotionEvent 前按目标 App 改写 MotionEvent
```

合成输入命中条件：

```text
deviceId < 0
或 source == TOUCHSCREEN(0x1002)
或 source 命中 MOUSE
ACTION_CANCEL 不改
```

伪装后的稳定字段：

```text
deviceId    = 4
source      = 0x5002
工具类型    = FINGER
buttonState = 0
```

触摸形态字段带 jitter，不再固定：

```text
pressure      = 0.30~0.88；UP/POINTER_UP 为 0.22~0.48
size          = 1.04~1.68
touchMajor    = 8.4~15.6
touchMinor    = 4.8~touchMajor-0.45
toolMajor     = touchMajor * 1.04~1.22
toolMinor     = touchMinor * 1.02~1.16
orientation   = -0.32~0.32
```

jitter seed 来自：

```text
targetPackageName + targetOwnerUid + downTime + eventTime + pointerId + action
```

## 典型行为链路

```text
目标 App
  ├─ Window.addFlags(FLAG_SECURE)
  │    └─ WindowState.isSecureLocked()
  │         └─ screen_secure_bypass=1 -> 返回 false
  │
  ├─ SurfaceView.setSecure(true) / SurfaceControl.setSecure(true)
  │    └─ SurfaceControl Builder / Transaction
  │         └─ screen_secure_bypass=1 -> 清掉 SECURE bit
  │
  └─ 检测远控/注入输入 MotionEvent
       └─ InputDispatcher 派发前
            └─ input_touch_spoof=1 -> 改写为接近真机触摸字段
```

## 常见问题排查

### 开了开关还是黑屏 / screencap 仍是 0 字节

按顺序看：

1. property 是否为 1：

```bash
adb -s 35051FDH2000NQ shell getprop persist.rommgr.app.<pkg>.screen_secure_bypass
```

2. 目标 App 是否重启过。没重启时旧窗口/旧 Surface 可能还保留 secure 状态。

3. SurfaceFlinger 里是否还有 secure 子层：

```bash
adb -s 35051FDH2000NQ shell dumpsys SurfaceFlinger | grep -iE '<pkg>|SurfaceView|isSecure|hasProtectedContent'
```

- `isSecure=true`：说明 Window 或 SurfaceControl 绕过没覆盖到这个 layer。
- `hasProtectedContent=true`：不是本功能范围，可能是 DRM/protected buffer。

### App 自查 FLAG_SECURE 不能被破坏怎么办

当前设计就是尽量不直接清 App 的业务 flag。Window 级绕过在 `WindowState.isSecureLocked()` 返回 false；Surface 级绕过在送 SurfaceFlinger 前清 flags。目标 App 正常调用 `FLAG_SECURE` / `setSecure(true)` 的路径仍然能跑。

### 为什么不做“普通 App 投屏检测”

因为 scrcpy/qtscrcpy 这类链路经常不是 App 可见的 `DisplayManager` / `MediaRouter` 事件。demo 如果用文件落盘、路由名、外接显示等间接信号去猜，会误导验收。当前策略是：

- demo 只展示三方 App 能稳定看到的内容保护和 MotionEvent；
- 真正影响截图/录屏/投屏画面的是 ROM/framework 层；
- 不把猜测写成“检测成功”。

## 留坑：目标 App 自己发起截图/录屏的分流策略（未实现）

当前版本为了让外部采集可见，做的是统一清掉命中 App 的 Window/Surface secure 效果：

```text
App 自查 FLAG_SECURE / setSecure(true) -> 仍然像开启保护
SurfaceFlinger 实际 layer secure 状态 -> isSecure=false
外部 screencap / screenrecord / scrcpy / qtscrcpy -> 能采到真实画面
```

这会留下一个可被强检测 App 利用的矛盾：如果目标 App 自己申请 `MediaProjection`、调用可用的 capture 路径，或在系统/特权/root 场景下触发 `SurfaceControl` capture，它可能发现：

```text
我明明打开了 FLAG_SECURE，但自测录屏/截图没有黑屏。
```

因此后续需要做“按采集调用者分流”的策略，而不是简单全局把 secure 效果关掉。目标语义：

```text
外部采集者：
  SystemUI 截图 / screenrecord / scrcpy / qtscrcpy / 电脑侧投屏 -> 放行真实画面

目标 App 自己或同 UID 自测采集：
  MediaProjection / captureLayers / captureDisplay / 自测截图 -> 仍返回黑屏、空图或保持 secure 失败语义
```

候选落点：

```text
frameworks/base/services/core/java/com/android/server/media/projection/MediaProjectionManagerService.java
frameworks/base/services/core/java/com/android/server/display/DisplayManagerService.java
frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp
frameworks/native/services/surfaceflinger/Layer.cpp
frameworks/native/include/gui/DisplayCaptureArgs.h / LayerCaptureArgs.h
```

可能需要的信息：

```text
caller uid/pid/package
top/resumed package
被采集 layer owner uid/package
ROMManager per-app policy
```

未来验收口径：

```text
1. 外部 scrcpy/qtscrcpy/screenrecord 采目标 App：仍能看到真实画面。
2. 目标 App 自己用 MediaProjection 做自测采集：看到黑屏/空图/失败语义。
3. App 自查 FLAG_SECURE 仍为开启。
4. SurfaceFlinger dumpsys 对外部采集链路仍能看到当前绕过效果，不能回退播放态黑屏问题。
```

这个留坑先只记录，不在当前版本实现。

## 边界

- `deviceId=4` / `source=0x5002` 是 Pixel 7 实测值；Pixel 5 或其它机型最好后续从 InputReader 缓存真实触屏设备特征，而不是硬编码。
- 当前输入伪装在 InputDispatcher 层，不是 uinput/KPM 级物理注入；极端目标若验证更底层签名或事件 provenance，后续要上 uinput/KPM。
- 当前 secure 绕过处理的是 Window/Surface layer 标志；不处理真实 DRM、Widevine、TEE protected path。
- passive scrcpy/qtscrcpy 拉屏本身不一定能被普通 App 发现，但其画面黑屏保护可以在 ROM 层被绕过。
