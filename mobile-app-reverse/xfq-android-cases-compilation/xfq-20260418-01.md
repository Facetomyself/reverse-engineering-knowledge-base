## 3. 这个算法到底魔改了什么 🔝

这一节单独补上,明确回答“和标准 AES 相比,到底改了哪里”。
3.1 魔改点一:前 4 字节不是普通 key,而是算法头 🔝
key_hex 解码后的前 4 字节是:

```
1b 2a eb 17
```

它们的作用不是单纯参与 AES 扩展,而是:

```
a7[1] == 0x2Aa7[2] == 0xEBa7[3] ^ a7[0] == 0x0C
```

也就是:
前 4 字节在这里更像“模式头 / 版本头 / 路径选择头”。
3.2 魔改点二:轮密钥生成完全不是标准 AES key schedule 🔝
标准 AES 会基于 16/24/32 字节 key 做标准扩展。
这个样本不是。

```
它先拿到 180 字节 key_material,然后生成真正参与分组加密的 176 字节:
rk[i] = key_material[i + 4] ^ key_material[(i + 1) % 3]
```

即:
前 4 字节不直接进入正常轮密钥
用前 3 字节做滚动异或种子
后 176 字节被重新混成轮密钥
这一步是最大魔改点。
3.3 魔改点三:AddRoundKey 不再是普通 XOR 🔝
标准 AES 的轮密钥叠加是:

```
state[i] ^ round_key[i]
```

当前样本不是。
它改成了 nibble 级查表混合:

```
def _mix(tbl, left, right):
hi = tbl[(left & 0xF0) | (right >> 4)] & 0xF0
lo = tbl[((left & 0x0F) << 4) | (right & 0x0F)] >> 4
return hi | lo
```

即:
左右字节拆成高低半字节
组合索引
进表
拼回新字节
所以它不是线性的 byte XOR,而是查表非线性混合。
3.4 魔改点四:S-box 不是标准 AES S-box 🔝
标准 AES S-box 开头通常是:

```
63 7c 77 7b ...
当前样本 _S 开头是:
ff 7e e2 88 4f fa b9 2e ...
```

显然不是标准 AES S-box。
所以即便轮结构像 AES,替换盒本身也已经换了。
3.5 魔改点五:中间轮 T-box 全部是自定义的 🔝
标准 AES 常见优化版也会有 T-box,但表内容固定。
这里用到的:

```
_T0
_T1
_T2
_T3
```

表值都不是标准 AES 的 T 表。
换句话说:
它保留了“T-box 实现 AES 风格轮函数”的外形,但具体表已经完全换掉。
3.6 保留不变的部分 🔝
没改或者基本保持一致的部分:
分组长度:16 字节
轮结构:仍然是 10 轮 AES-like 结构
模式:ECB
padding:PKCS7
输出包装:Base64
所以更准确的描述不是“自定义加密”,而是:
AES 外形 + 自定义 key 派生 + 自定义 S/T 表 + 自定义 nibble 混合

## 5. 最终算法描述(可直接抄给别人) 🔝

```
当前样本 laesEncryptStringWithBase64 的逻辑可以概括为:
```

1. 把明文字符串按 UTF-8 编码成字节

```
2. 把 key_hex 解析成 180 字节 key_material
```

3. 校验头部:

```

key_material[3] ^ key_material[0] == 0x0C
```

4. 生成 176 字节轮密钥:

```
rk[i] = key_material[i + 4] ^ key_material[(i + 1) % 3]
```

5. 明文做 PKCS7 padding
6. 按 16 字节分组
7. 每个 block 走自定义 AES-like 表驱动轮函数
8. 输出密文字节做 Base64
