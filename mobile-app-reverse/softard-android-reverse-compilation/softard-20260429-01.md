##  一、SO 文件也是有身份证的

Android 的 SO 文件（  ` .so  ` ）是  ** ELF 格式  ** （Executable and Linkable
Format），Linux 下可执行文件、动态库都用这个格式，PC 上的  ` .so  ` /  ` .elf  ` ，Android 上的 native
库，本质一样。

ELF 有一个很容易让初学者困惑的特点：  ** 同一份文件，有两套完全不同的"读法"  ** 。


    ELF 文件  ├── Sections（节）   ← 给编译器、链接器、逆向工具用  └── Segments（段）   ← 给操作系统加载器用

  * ** Sections  ** 是"内容是什么"：每个 Section 都有名字和用途，逆向常见的有：

Section  |  权限  |  内容
---|---|---
` .text  ` |  ` r-x  ` |  编译后的机器码，函数实现在这里
` .rodata  ` |  ` r--  ` |  只读数据，硬编码的字符串常量在这里
` .data  ` |  ` rw-  ` |  已初始化的全局变量和静态变量
` .bss  ` |  ` rw-  ` |  未初始化的全局变量，文件里不占空间，加载时补零
` .plt  ` |  ` r-x  ` |  动态链接跳板代码，调用外部函数时的中转站
` .got  ` /  ` .got.plt  ` |  ` rw-  ` |  全局偏移表，存外部函数的运行时真实地址
` .dynamic  ` |  ` rw-  ` |  动态链接元信息，记录依赖哪些库、符号表在哪里
` .dynsym  ` |  ` r--  ` |  动态符号表，导出和导入的符号列表
` .dynstr  ` |  ` r--  ` |  符号名字符串池，  ` .dynsym  ` 里的名字指向这里
` .init_array  ` |  ` rw-  ` |  函数指针数组，SO 加载时 linker 会依次调用，壳常在这里放解密代码
` .eh_frame  ` |  ` r--  ` |  异常处理信息，C++ 异常展开用，逆向时通常忽略

  * ** Segments  ** 是"怎么加载进内存"：加载器按 Segment 把文件内容 mmap 进进程地址空间，一个 Segment 通常包含多个 Section

这两套描述的受众完全不同，运行时只有 Segments 是必须的。所以加固厂商会做一件事：  ** 故意破坏 ELF 的 Section Header
** 。IDA 解析不了 Section，没法正确识别代码和数据的边界，分析难度大幅提升。但程序照样能跑——因为系统加载器根本不看 Section
Header，它只看 Segment Header，那部分是完整的。

` strip  ` 命令减小 SO 体积，本质也是做同样的事：删掉符号表和 Section Header，程序运行不受任何影响。


##  二、文件头：SO 的身份证

ELF 文件的开头是固定  ** 64 字节  ** 的文件头（64 位平台），存了这个文件最基本的信息。


几个逆向最常用的字段：

偏移  |  字段  |  逆向用途
---|---|---
` 0x00  ` |  magic  ` 7F 45 4C 46  ` |  即  ` \x7fELF  ` ，扫内存找 SO 的特征
` 0x04  ` |  Class  |  ` 02  ` = 64 位，  ` 01  ` = 32 位，判断架构
` 0x12  ` |  Machine  |  ` 0xB7  ` = ARM64，  ` 0x28  ` = ARM32
` 0x10  ` |  Type  |  ` ET_DYN (3)  ` = 动态库（SO 文件）
` 0x20  ` |  ` e_phoff  ` |  Segment 表在文件里的偏移，加载器从这里找
` 0x38  ` |  ` e_shoff  ` |  Section 表在文件里的偏移，加固时常被清零

` Machine  ` 字段很实用——拿到一个 SO 不确定是 32 位还是 64 位时，看这个字段就行，不用靠文件名猜。

其实也可以通过读Machine字段判断环境是否是模拟器，这个不展开说了。 以后做虚拟机的时候会带大家写代码手动解析ELF文件。


##  三、Segments：加载器的地图

用  ` readelf -l  ` 看 Segment 信息：


    readelf -l libxxx.so

输出大概长这样：


    说明---  基本信息
      Elf file type is DYN     ← SO 文件（动态库），不是可执行文件  Entry point 0x121c       ← 入口地址，SO 加载完后 linker 会跳这里，通常就是 JNI_OnLoad  10 program headers       ← 共 10 个 Segment
      ---  逐个 Segment 解读
      PHDR     0x40   R       ← Program Header Table 本身被映射进内存，只读  INTERP   0x270  R       ← 指定动态链接器路径：/system/bin/linker64                             确认这是 ARM64 Android SO
      三个 LOAD（真正被加载进内存的内容）：
      LOAD  0x000000  R E  FileSiz=0x2400  MemSiz=0x2400    → 代码段，可读可执行    → 包含：.text .plt .rodata .dynsym .dynstr .hash .eh_frame 等    → Entry point 0x121c 就在这段里
      LOAD  0x002400  RW   FileSiz=0x388   MemSiz=0x388    → 数据段，可读可写    → 包含：.init_array .fini_array .dynamic .got .got.plt .data.rel.ro
      LOAD  0x002788  RW   FileSiz=0x008   MemSiz=0x058   ← 注意！    → FileSiz ≠ MemSiz，差了 0x50 字节    → 多出来的这部分是 .bss（未初始化全局变量），文件里不占空间    → 加载时内核补零
      其余几个：
      DYNAMIC      → 指向 .dynamic section，linker 从这里读依赖库、符号表位置等信息
      GNU_RELRO    FileSiz=0x388  MemSiz=0xc00    → "Relocation Read-Only"：linker 完成重定位后，把这块内存权限改成只读    → 覆盖了 .got .dynamic 等，防止 GOT 被恶意篡改    → 注意 MemSiz(0xc00) > FileSiz(0x388)，多出来的是页对齐填充
      GNU_STACK    FileSiz=0  MemSiz=0  Flg=RW（没有 X）    → 标记栈不可执行（NX/DEP 保护开启）    → 如果这里是 RWE 就说明关了 NX，是个安全风险
      NOTE         → 存 Build ID 和 Android ABI 标识，调试时用
      ---  Section → Segment 对应关系
      Segment 02（R E，代码段）    .text .plt .rodata .dynsym .dynstr .hash .eh_frame ...
      Segment 03（RW，数据段）    .init_array .fini_array .dynamic .got .got.plt
      Segment 04（RW，BSS）    .data .bss

` GNU_RELRO  ` 覆盖了 GOT——意味着 linker 重定位完成后 .got 变成只读，直接写 GOT 做 PLT Hook 会触发
SIGSEGV。需要先用  ` mprotect  ` 改权限，或者改在 linker 完成之前的时机操作。这在实际 Hook 开发里是个常见坑。

` VirtAddr  ` 是加载到内存后的期望地址，对于 SO 文件（  ` ET_DYN  ` 类型）这个值通常从  ` 0  ` 开始，实际加载地址由
ASLR 随机决定，运行时基址加上这个偏移才是真正的地址。下面介绍一下GOT。


##  四、PLT/GOT：ASLR 时代的函数调用难题

这是 ELF 最值得深究的机制之一，搞清楚之后很多逆向操作都会豁然开朗。

** 问题是这样的  ** ：一个 SO 里调用了  ` malloc  ` ，但编译时根本不知道  ` malloc  ` 在哪——ASLR
每次加载地址都不一样，而  ` libc.so  ` 的基址是随机的。怎么办？

同时还有另一个约束：ARM64 的  ` BL  ` 指令是 4 字节，编译时把跳转偏移写死进去的。代码段  ` r-x  `
不可写，运行时无法修改这条指令。

** 解决方案是 PLT + GOT 分工  ** ：


    你的代码  └─ BL  plt_malloc（编译时写死的固定偏移，跳到 PLT 桩）        └─ PLT[malloc]：              LDR x16, [got_malloc]   ← 读 GOT 里存的地址              BR  x16                 ← 跳过去                    └─ 第一次调用：GOT 里存的是 linker 的解析函数                       linker 找到 malloc 真实地址，写入 GOT[malloc]                       之后每次调用：GOT 里已经写好 malloc 真实地址，直接跳转

  * ** GOT  ** （Global Offset Table，  ` .got  ` Section，  ` rw-  ` 权限）：存运行时真实函数地址，可以被 linker 写入
  * ** PLT  ** （Procedure Linkage Table，  ` .plt  ` Section，  ` r-x  ` 权限）：一段固定的可执行跳板代码，读 GOT 后跳转

代码段不可写，所以不能直接在调用点填入真实地址。PLT 提供了一个"编译时可以写死偏移"的固定中转站，GOT 存着可变的真实地址。两者职责分离，绕开了
W^X 的约束。

** 这个机制对逆向有什么用？  **

** PLT/GOT Hook  ** ——把 GOT 里某个函数的地址替换成你自己的函数地址，所有调用这个函数的地方都被劫持了。GOT 是  ` rw-
` 权限，可以直接写。这是不少 Hook 框架的底层实现之一。

用  ` nm -D  ` 可以看到所有外部导入函数（它们在 GOT 里各有一格）：


    nm -D libxxx.so

符号类型含义：


    T  → .text 代码段，大写表示全局导出（可被外部调用）t  → .text 代码段，小写表示本地（外部不可见）U  → Undefined，从外部导入，对应 GOT 里的一格D  → .data 数据段B  → .bss 未初始化数据段

一个业务 SO 通常有大量  ` U  ` （  ` malloc  ` 、  ` pthread_create  ` 、  `
__android_log_print  ` ……），每个  ` U  ` 在 GOT 里有一格，运行时由 linker 填入真实地址。

##  五、JNI 函数注册：逆向怎么找入口

Java 调用 native 方法，JVM 要找到 SO 里对应的 C 函数。有两种注册方式：

###  静态注册

函数名遵循固定命名规则：


    Java_包名_类名_方法名

包名里的  ` .  ` 换成  ` _  ` ，例如：


    JNIEXPORT jstring JNICALLJava_com_example_app_MainActivity_stringFromJNI(JNIEnv* env, jobject thiz) {    return (*env)->NewStringUTF(env, "Hello from C");}

逆向时直接在 IDA 或  ` nm -D  ` 的输出里搜  ` Java_  `
前缀就能找到。优点是一眼就看出是哪个类的哪个方法，缺点是包名和方法名完全暴露。

###  动态注册

在  ` JNI_OnLoad  ` 里调  ` RegisterNatives  ` 手动绑定：


    static const JNINativeMethod methods[] = {    { "nativeCheck", "(Ljava/lang/String;)Z", (void*)real_check_func },};
    JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM* vm, void* reserved) {    JNIEnv* env;    (*vm)->GetEnv(vm, (void**)&env, JNI_VERSION_1_6);    jclass clazz = (*env)->FindClass(env, "com/example/app/MainActivity");    (*env)->RegisterNatives(env, clazz, methods, 1);    return JNI_VERSION_1_6;}

` methods  ` 数组里每一项是  ` { "Java方法名", "方法签名", 函数指针 }  ` 。

逆向路径变成：  ** 找  ` JNI_OnLoad  ` → 找  ` RegisterNatives  ` 调用 → 跟进第三个参数（methods
数组）→ 读函数指针 → 跳到真正的实现  ** 。


|  静态注册  |  动态注册
---|---|---
定位方式  |  直接搜  ` Java_  ` 前缀  |  先找  ` JNI_OnLoad  ` ，再追函数指针
名字暴露度  |  高，包名方法名全暴露  |  低，混淆后函数名无意义
加固常见手段  |  去掉符号（strip）  |  混淆  ` JNI_OnLoad  ` 函数体，IDA 难以识别

大部分正经 APP 的核心逻辑都用动态注册。加固壳会进一步混淆  ` JNI_OnLoad  ` ，让 IDA 找不到  ` RegisterNatives
` 调用，或者把真正的注册放在另一个被混淆的函数里，需要一层层追。


##  六、工具速查

分析 SO 用得很频繁的命令：


    # 查所有导出/导入符号，-D 只看动态符号表nm -D libxxx.so
    # 查 Segments（加载信息）readelf -l libxxx.so
    # 查 Sections（内容分区）readelf -S libxxx.so
    # 查动态链接信息（依赖哪些库、GOT 地址等）readelf -d libxxx.so

如果 SO 被 strip 了，  ` nm  ` 看不到符号，就只能靠  ` readelf -l  ` 确认基本结构，然后上 IDA 做静态分析，从函数
prologue/epilogue 特征和交叉引用重建逻辑。


##  小结

概念  |  逆向用途
---|---
ELF Sections vs Segments  |  加固破坏 Sections 让 IDA 难解析，Segments 必须保留程序才能运行
ELF Header  ` Machine  ` 字段  |  判断 32/64 位及 CPU 架构
PT_LOAD Segment  |  SO 真正被加载进内存的部分，基址从这里算
PLT/GOT  |  动态链接的跳板机制；GOT 是  ` rw-  ` ，可以被 Hook 替换函数指针
静态注册 JNI  |  搜  ` Java_  ` 前缀直接定位
动态注册 JNI  |  从  ` JNI_OnLoad  ` →  ` RegisterNatives  ` → 函数指针追下去
