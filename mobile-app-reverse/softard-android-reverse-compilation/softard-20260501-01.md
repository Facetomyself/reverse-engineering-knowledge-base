##  ART 不是一个简单的解释器

很多人以为 Android 虚拟机就是"逐行解释执行字节码"，其实 ART 有三套执行方式，会根据方法的"热度"自动切换：

Interpreter（解释执行）  ：最基础的模式，逐条读 Dalvik
字节码执行。慢，但灵活。任何方法都能走这条路，不需要提前编译。加固壳最喜欢在这一层做手脚——因为字节码可以在运行时动态填入，解释器不在意你什么时候塞进来的，执行时有就行。

JIT（即时编译）  ：Android 7
引入。虚拟机在运行时监控哪些方法被频繁调用，把这些"热点方法"的字节码编译成机器码，缓存在内存里。下次再调用，直接执行机器码，速度大幅提升。同时 JIT
会把热点方法记录到 .prof 文件里，留给下一步用。

AOT（提前编译）  ：系统在设备空闲充电时，读取 .prof 文件，用 dex2oat 把热点方法编译成 .oat 文件（本质是
ELF），持久化到磁盘。下次启动直接加载机器码，最快。


    Interpreter（所有方法的默认起点）    ↓ 热点触发JIT（运行时编译，结果缓存在内存）    ↓ .prof 积累，设备空闲时AOT（持久化机器码，下次启动直接用）

现在很多人以为安装 App 时系统就做了完整的 AOT，其实不是。Android 7+ 默认是  speed-profile 混合模式
：安装时几乎不编译，首次运行靠 Interpreter + JIT，等跑了一段时间积累了热点数据，才后台偷偷去编译。这意味着  Interpreter
始终存在  ，不会消失——那些不够热的冷路径代码，永远走解释器。

##  每个 Java 方法背后都有一张"身份证"

ART 虚拟机里，每个 Java 方法在内存中都对应一个 C++ 对象：  ArtMethod  。可以把它理解成方法的身份证，虚拟机要执行任何 Java
方法，第一步都是找到它的 ArtMethod，然后根据里面的信息决定怎么跑。


    struct ArtMethod {    uint32_t declaring_class_;       // 属于哪个类    uint32_t access_flags_;          // public/private/static 等    uint32_t dex_code_item_offset_;  // 字节码在 dex 文件里的偏移    uint64_t entry_point_;           // 执行入口地址    // ...}

两个最关键的字段：

dex_code_item_offset_  ：指向 dex 文件里这个方法的字节码位置。  方法抽取壳就是把这个字段挖空
，让解释器找不到字节码，然后在方法被调用前把正确偏移填回来。

entry_point_  ：方法的执行入口指针，决定用哪种方式执行。这个指针会随着方法状态变化：


    解释执行：entry_point_ → artQuickToInterpreterBridge（全局共用一个固定地址）JIT编译后：entry_point_ → JIT cache 里该方法独立的机器码地址AOT编译后：entry_point_ → .oat 文件中的机器码

Hook 工具改的就是这里  。把  entry_point_  换成自己的函数地址，目标方法一被调用，虚拟机读指针，结果跳进了你的 hook 函数。

这里有个细节：方法被 JIT 编译后，调用方可能把地址做了内联缓存，直接跳机器码，完全绕过  entry_point_  。所以 Frida 在 hook
之前，会先强制把方法切回解释模式——解释器入口  artQuickToInterpreterBridge
是全局唯一固定地址，没有内联缓存问题，替换后所有调用都必须经过，hook 才稳定生效。

##  手机开机后发生了什么

理解 Android 启动流程，才能搞清楚壳在哪里介入、Frida 在什么时机可以操作。

开机后，第一个用户态进程是  Zygote  。它率先启动，做一件很重要的事：把 ART 虚拟机、Android framework 的全部类、常用 SO
全部预加载进内存。这个过程很耗时，但只做一次。

之后每次有 App 要启动，系统通知 Zygote，Zygote 执行  fork()  产生子进程。关键在于：  Zygote 只 fork，不 exec
。普通进程创建是 fork 之后立刻 exec，exec 会用新程序覆盖子进程内存，之前继承的东西全清空。Zygote 不 exec，子进程直接继承
Zygote 预加载的所有内存——ART、framework、常用类全现成，一行不用重新加载。

配合  COW（写时复制）  ：fork
后父子进程共享所有内存页，只有某个进程要写某页时，才给它单独复制一份。只读的代码页（framework、libart）永远共享，物理内存只有一份。结果是所有
App 进程共用同一份 framework 代码，启动快、内存省。


    开机 → Zygote 预加载（ART + framework + 常用SO）  ↓ forkApp子进程（继承所有预加载内容，COW）  ↓ActivityThread.main()  ↓Application.attachBaseContext()  ← 壳在这里介入  ↓Application.onCreate()  ↓MainActivity → static初始化 → 业务代码

##  壳为什么抢在 attachBaseContext 里动手

加固壳需要在业务代码执行前完成解密、加载真实 dex、修复 ArtMethod。  attachBaseContext()  是 Application
生命周期里最早的回调，此时 Context 刚绑定，ContentProvider 还没初始化，任何业务代码都没跑。比它更晚的  onCreate()
已经有部分初始化发生，壳来不及。

壳在  attachBaseContext()  里的操作顺序：


    1. 加载壳 SO（dlopen / System.loadLibrary）2. SO 里解密/解压真实 dex（AES解密、zip解压等）3. DexClassLoader 加载真实 dex 到内存4. 替换 ClassLoader5. 修复 ArtMethod（填回 dex_code_item_offset_）

这也是脱壳的核心思路：壳必须在内存里还原出完整的 dex 才能让 App 正常运行。只要在还原完成后、执行前的时机 dump 内存，就能拿到原始 dex。
