## 正文

上篇讲了怎么用 findcrypt3 识别加密算法。但这件事是有对手的——开发者可以主动对抗，让 findcrypt
扫不到特征常量。这篇把攻防两侧的思路都摆出来对着看。

有一个根本矛盾绕不开：  ** 算法运行时必须用到正确的值，所以常量一定存在于内存某处  **
，区别只是存在哪、什么时候出现、以什么形式出现。防御方围绕这三个维度做文章，逆向方围绕这三个维度去破。这里只是简单抛个砖，实际安全对抗是一个系统化工程，不是单改某个代码就能完全防住的。


##  一、运行时计算

** 防：常量不写死，运行时算出来。  **

最简单的做法是异或：


    uint32_t a = 0x12345678 ^ 0x75316579;  // 结果是 0x67452301，但原始值不出现在代码里

更碎的写法是拆分赋值：


    uint32_t a = 0x67000000;a |= 0x00450000;a |= 0x00002300;a |= 0x00000001;

也可以利用常量本身的数学来源重新推导，比如 SHA1 轮常量  ` 0x5A827999  ` 来自  ` floor(sqrt(2) * 2^30)  `
，直接算就行：


    uint32_t k0 = (uint32_t)(sqrt(2.0) * (1u << 30));

或者存一张偏移表，用时还原：


    static uint32_t table[] = { 0x67452302, 0xEFCDAB8A ... };  // 每个值 +1 存储uint32_t a = table[0] - 1;

这些手段的共同点是：静态扫描期间原始常量不存在，findcrypt 什么也找不到。


** 攻：F5 一下就看穿了，只能骗自动化工具。  **

IDA F5 出来就是：


    uint32_t a = 0x12345678 ^ 0x75316579;

脚本算一下马上还原。拆分赋值也一样，看完几行赋值语句就能拼出原始值。说白了这个防御手段针对的是 findcrypt 这类自动化扫描，对认真读代码的人——甚至
AI 分析工具——几乎没有障碍。


##  二、静态加密

** 防：常量以变形态存储，加载时才还原。  **

爱加密这类工具会把  ` .rodata  ` 段整体加密，SO 加载时再解密。findcrypt 扫静态文件时看到的全是密文，特征常量全部消失。

编译期混淆和这个思路类似，LLVM  ` -ecs  ` 在编译期把常量替换成加密形式，运行时插入解密 stub，逆向人员静态看到的是：


    .rodata 里一堆乱码↓某函数开头调用解密 stub↓解密完放进寄存器继续用


** 攻：等它自己解密，然后扫内存。  **

段加密只是推迟了常量出现的时机。SO 必须先解密才能运行，  ` JNI_OnLoad  ` 或  ` .init_array  `
里一定有解密逻辑，解密完内存里就是明文。在  ` JNI_OnLoad  ` 返回之后扫：


    function scanForMD5() {    const pattern = "01 23 45 67 89 ab cd ef fe dc ba 98 76 54 32 10";    Process.enumerateRanges('r--').forEach(range => {        Memory.scanSync(range.base, range.size, pattern).forEach(match => {            console.log("MD5 IV found at: " + match.address);        });    });}

另外解密 stub 本身也是个信号——看到函数开头有一段"读乱码 → 调解密函数 → 继续执行"的结构，基本可以确认这里在藏东西。


##  三、时机对抗

** 防：常量只在运行时短暂存在，用完立刻销毁。  **

用完清零：


    void md5_init(MD5_CTX *ctx) {    ctx->a = compute_a();    // ... 做完运算 ...    memset(ctx, 0, sizeof(MD5_CTX));  // 用完立刻清零}

或者直接用栈上临时变量，函数返回栈帧就销毁了：


    void compute() {    uint32_t sbox[256];  // 栈上分配    init_sbox(sbox);    // ...}  // 返回，sbox 消失

堆和全局内存随时可以被 Frida 遍历扫描，栈帧随函数返回消失，扫内存的窗口被压缩到毫秒级。


** 攻：不扫内存，直接 hook 数据流。  **

不找常量在哪，而是找算法一定会经过的地方。hook 函数入口，在清零之前就进去了：


    Interceptor.attach(Module.findExportByName("libxxx.so", "AES_set_encrypt_key"), {    onEnter(args) {        // 刚进来，S-Box 还在    }});

更彻底的方法是 hook 数据流入口，不管常量怎么藏，数据流入算法时必然经过这里：


    Interceptor.attach(md5_update_addr, {    onEnter(args) {        console.log(hexdump(args[1], { length: args[2].toInt32() }));    }});

栈上变量窗口期短，但加密运算本身需要时间，几十毫秒是有的，高频轮询也能概率捕获：


    setInterval(() => { /* 扫栈帧范围 */ }, 1);


##  四、魔改常量

** 防：把标准常量换成自定义值，让算法看起来完全不是标准实现。  **

以 MD5 为例，初始化向量全部换掉：


    // 标准 MD5uint32_t a = 0x67452301;uint32_t b = 0xEFCDAB89;
    // 魔改后uint32_t a = 0xDEADBEEF;uint32_t b = 0xCAFEBABE;

AES 也可以换 S-Box，只要加解密两端用同一张自定义置换表，算法就能跑通，但 findcrypt
扫不到，肉眼也认不出来。用标准库去验算结果对不上，逆向人员很容易以为碰到了一个完全自定义的算法，花大量时间从头逆。

代价是算法不再兼容标准库，而且标准算法的安全性分析结论不再适用——不过魔改之后引入了什么弱点，没人说得清楚。


** 攻：不认常量，认骨架，用已知明文验证。  **

无论常量怎么改，算法的结构特征和输入输出行为是改不了的。喂一个已知输入，观察输出的规律：

  * 输出长度固定 16 字节，无论输入多长 → 分组密码骨架（AES 系）
  * 输出长度固定 32 字节，无论输入多长 → 256-bit 摘要骨架
  * 换密钥输出就变，不换密钥输出不变 → 有密钥参与，是加密不是 hash

认出骨架之后，魔改常量只影响具体结果，不影响算法类型的判断。剩下的问题就变成：把魔改后的参数抠出来，用同结构的标准库替换实现。
