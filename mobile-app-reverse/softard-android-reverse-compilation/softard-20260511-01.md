##  第一步：用 jadx 找入口

老流程，jadx 打开 APK，先搜fork，发现没有。然后再找verify的代码，看一下算法是怎么校验的。


可以确定校验逻辑是在  ` CodeCheck.a()  ` 内，打开  ` CodeCheck  ` 看到代码非常简单：


    /* loaded from: classes.dex */  public class CodeCheck {      private native boolean bar(byte[] bArr);
        public boolean a(String str) {          return bar(str.getBytes());      }  }

出现了  ` native  ` 关键字——这个方法的实现不在 Java 里，所以代码逻辑在 C/C++ 编译出来的 SO
文件里。那我们就要去找引用的库了。

继续搜  ` System.loadLibrary  ` ，找到：


    static {    System.loadLibrary("foo");}

这样就知道我们需要分析对应文件是  ` libfoo.so  ` 。解压 APK，在  ` lib/arm64-v8a/  ` 下确认它的确存在。


之前我们讲过ELF文件基础知识，忘记的可以快速复习一下： [ 某厂安全研发的逆向笔记（三）：SO 文件剖析——必须搞懂的 ELF 格式
](https://mp.weixin.qq.com/s?__biz=MzAwMDM2NzMyNg==&mid=2458237303&idx=1&sn=3085fb6a4cbe7d7d78d18c039578078f&scene=21#wechat_redirect)
，也提到了  ` IDA Pro  ` ，这次我们就实操一遍。


##  第二步：使用IDA64 打开 arm64-v8a的SO

IDA 打开  ` libfoo.so  ` ，等工具完成结构分析，打开  ** Exports 窗口  ** ：


发现没有  ` jni_onload  ` ，而且函数名都带  ` Java_  ` 前缀，说明这是静态注册的 JNI 命名规则，直接对应 Java 层的
` CodeCheck.bar  ` 。所以很容易就定位到我们要分析的代码就在  `
Java_sg_vantagepoint_uncrackable2_CodeCheck_bar  ` 里面。

双击  ` bar  ` ，可以看到实现的汇编代码：


有点难读，可以按  ` F5  ` 让IDA生成伪 C 代码：


    bool __fastcall Java_sg_vantagepoint_uncrackable2_CodeCheck_bar(__int64 a1, __int64 a2, __int64 a3){  _BOOL8 result; // x0  const char *v6; // x21  char v7[24]; // [xsp+0h] [xbp-40h] BYREF  __int64 v8; // [xsp+18h] [xbp-28h]
      result = 0LL;  v8 = *(_QWORD *)(_ReadStatusReg(ARM64_SYSREG(3, 3, 13, 0, 2)) + 40);  if ( byte_1300C == 1 )  {    strcpy(v7, "Thanks for all the fish");    v6 = (const char *)(*(__int64 (__fastcall **)(__int64, __int64, _QWORD))(*(_QWORD *)a1 + 1472LL))(a1, a3, 0LL);    return (*(unsigned int (__fastcall **)(__int64, __int64))(*(_QWORD *)a1 + 1368LL))(a1, a3) == 23        && !strncmp(v6, v7, 0x17u);  }  return result;}

答案就明晃晃的摆在这里：  **` Thanks for all the fish  ` ** （23个字符）。

但这里出现了一个奇怪的条件：  ` byte_1300C == 1  ` 。如果这个开关不为 1，就直接返回 false，输入正确答案都不行。


##  第三步：追开关，找到反调试

按  ` X  ` 查  ` byte_1300C  ` 的交叉引用，


发现赋值的地方在  ` init  ` 函数：


    __int64 sched_traditional_with_pset_runqueue_init(){  __int64 result; // x0
      result = sub_918();  byte_1300C = 1;  return result;}

所以这个  ` sub_918()  ` 是一个关键函数。双击进去看一下代码：


再看一眼  ` sub_8DC  ` :


所以  ` sub_918  ` 里有  ` fork  ` 、  ` ptrace  ` ——这是双进程反调试：子进程 attach
父进程占坑，外部调试器无法再 attach 进来。细节下篇讲，这里只需要知道一件事：  ** 把  ` sub_918  ` 变成空函数，反调试就失效了。
** 所以这里也解释了为什么有一些手机会出现  ` Abort message: 'libbinder ProcessState can not be
used after fork'  ` 这样的crash。

总结一下调用链，就是在调用init之后，创建进程保护，如果init正常执行完，就会运行给  ` byte_1300C  ` 赋值1：


    onCreate() → loadLibrary("foo") → init() → sub_918() → byte_1300C = 1


##  第四步：patch SO，绕过反调试

所以为了解决crash，可以让  ` sub_918  ` 进入后立刻返回，不再做什么fork操作。要改代码就需要找到代码地址。

` sub_918  ` 地址就是  ` 0x918  ` ，可以找到这个地址的第一条指令：


    偏移 0x918：FF 83 00 D1  →  SUB SP, SP, #0x30

我们需要做的是把它改成  ` RET  ` 指令：  ` C0 03 5F D6  ` ，运行到这里直接跳出。

** 用 010 editor或者其他工具 打开SO  ** ，直接跳转到 0x918地址，核对内容是  ` FF 83 00 D1  ` ，然后直接修改成
` C0 03 5F D6  ` ，改完保存。


保存后的SO如果再用IDA打开，可以看到原来的  ` sub_918  ` 方法被解析成了空方法，方法内部就是RET跳出。


最后就是把这个so文件替换掉原始文件，重新打包安装。安装后运行，发现app不崩溃了。然后输入  ` Thanks for all the fish  `
，恭喜你，轻松解决了村口的这只拦路猫。
