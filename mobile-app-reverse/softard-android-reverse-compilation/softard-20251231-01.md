## 正文

上一篇不是猜测是string_ids_off值错误引起解析异常嘛。  但猜测终究是猜测，咱们干技术的还是要找到证据才能放心。

##  359b0


    .text:00000000000359A0                 LDR             X8, [SP,#0xB0+var_98].text:00000000000359A4                 ADD             X0, SP, #0xB0+var_60.text:00000000000359A8                 LDR             W8, [X8,#0x3C].text:00000000000359AC                 ADD             X8, X20, X8.text:00000000000359B0                 LDR             W8, [X8,X21,LSL#2]

崩溃点附近的指令就是这些。所以先理解汇编指令：  ARM64 使用 64 位通用寄存器（X0-X31），其低 32 位可单独作为 32
位寄存器使用（W0-W31），修改Wn会影响Xn的低 32 位，修改Xn会覆盖Wn的全部值。  X0在 ARM64
函数调用规范（AAPCS64）中是第一个参数 / 返回值寄存器，X20-X21是调用者保存寄存器（用于保存函数内上下文）。  我把注释写到指令后面：


    LDR    X8, [SP,#0xB0+var_98]  计算地址基址SP + 偏移0xB0 + var_98，读8字节写到X8寄存器ADD    X0, SP, #0xB0+var_60   计算栈指针SP与立即数的和，将结果（一个栈内存地址）存储到X0寄存器LDR    W8, [X8,#0x3C]         计算有效地址X8+0x3C偏移然后写入X8寄存器的低32位ADD    X8, X20, X8            计算X20和X8的和，写入X8LDR    W8, [X8,X21,LSL#2]     将X21的值左移2位然后与X8相加，加载到W8对应的c代码：const DexStringId *string_ids = (const DexStringId *) (dex_base + header->string_ids_off);const uint8_t *string_data = dex_base + string_ids[id].string_data_off;// 这里崩，359b0

所以就能把代码和汇编做一个简单关联：

  * X8->string_ids
  * X21->id
  * LSL  #2  ->DexStringId结构体是4字节
  * [X8,X21,LSL  #2  ]->string_ids[id]
  * LDR W8->读取string_ids[id]->string_data_off

因此就有了排查方向：

  1. 数组越界，就看X21
  2. string_ids基址不对看X8
  3. string_data_off不对，看W8
  4. dex_base不对，看X20

通过日志可以看到

  1. x21 0000000000000000 说明id是合法的。
  2. x8 0000007b84ac5870地址看起来正常，但是memory near x8都是空，说明X8指向了无法访问的区域。这是引起SEGV_ACCERR的原因。
  3. x20 0000007b44ac5800，内存有dex035的标识，说明在这里读的dex文件，0000007b44ac5800就是dex的基址。

通过代码看，string_ids = dex_base + header->string_ids_off对应着X8 = X20 +
header->string_ids_off。  X8和X20的地址都是有的，所以最后就需要确认dex的string_ids_off是多少。

##  Dex分析

上面的日志里面memory near x20:部分明显可以看到dex035，这个就是dex文件的magic值，所以可以直接解析这部分内存值。
关于Dex怎么解析，下面贴一个结构体，就按照顺序读就可以了。


    typedef struct {    uint8_t magic[8];           // 魔数 "dex\n035\0"    uint32_t checksum;          // adler32 校验和    uint8_t signature[20];      // SHA-1 签名    uint32_t file_size;         // 文件大小    uint32_t header_size;       // 标准为 0x70    uint32_t endian_tag;        // 字节序标记    uint32_t link_size;         // 链接数据大小    uint32_t link_off;          // 链接数据偏移    uint32_t map_off;           // map_list 偏移    uint32_t string_ids_size;   // 字符串数量    uint32_t string_ids_off;    // 字符串索引偏移    uint32_t type_ids_size;     // 类型数量    uint32_t type_ids_off;      // 类型索引偏移    uint32_t proto_ids_size;    // 原型数量    uint32_t proto_ids_off;     // 原型索引偏移    uint32_t field_ids_size;    // 域数量    uint32_t field_ids_off;     // 域索引偏移    uint32_t method_ids_size;   // 方法数量    uint32_t method_ids_off;    // 方法索引偏移    uint32_t class_defs_size;   // 类定义数量    uint32_t class_defs_off;    // 类定义索引偏移    uint32_t data_size;         // 数据部分大小    uint32_t data_off;          // 数据部分偏移} DexHeader;

可以看到这里string_ids_off异常的大。然后再看一下值，0x40000070，带入到上面的计算公式，  string_ids = dex_base

0000007b84ac5870 = 0000007b44ac5800 + 40000070  数据全对上了，大脑皮层瞬间得到了按摩。
现在明确是string_ids_off异常引起的crash。但具体这个异常是怎么出现的，这个就让架构团队去挠头想吧。
