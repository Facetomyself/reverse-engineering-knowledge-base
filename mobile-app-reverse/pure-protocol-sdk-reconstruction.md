# App 纯协议 SDK 重建：从首次设备注册到可维护协议客户端

> 来源: 方法论整理（设备注册 / 拦截器式协议客户端）
> 原始发布时间: 2026-09-03
> 归档日期: 2026-09-03
> 分类: 移动 App 逆向 — 纯协议 SDK 重建
>
> 把 Android App 的设备注册、公共参数、指纹与事件埋点重建成可脱离原 App 运行的 Python 协议客户端。主线不是单接口重放，而是拦截器式架构、多 HAR 对照、指纹语义和注册完备性；扩容只是后续成本问题，不能倒过来当完成标准。

## 定位

[App 逆向全局地图](./app-reverse-global-map.md) 把一次请求拆成 UI、业务、OkHttp、Interceptor、JNI、SO、TLS 七层，终点停在「模拟请求能通」。空壳、错机房、未激活设备要先过 [协议准入四关](./protocol-admission-four-gates.md)，再进入本文：当目标不是调通一个接口，而是用 Python 写出一套跟真实 SDK 同构的设备注册、公共参数和事件上报时，缺的是目录合同、证据语料和完备性门，不是再搜一遍 `addInterceptor`。

本文只讨论 **App 纯协议客户端**。它和 Web 侧的纯算 / 补环境 / V8 RPC / 自动化落地不是同一条链：

| 平面 | 权威文档 | 本文是否覆盖 |
|------|----------|--------------|
| Web JS 参数落地 | `docs/web-reverse-landing.md`、[sign-landing-methods.md](../web-reverse/sign-landing-methods.md) | 否 |
| HTTP 采集控制面 | [high-concurrency-http-collector-control-plane.md](../collection-engineering/high-concurrency-http-collector-control-plane.md) | 只引用节奏与身份隔离，不写生产并发数字 |
| App 请求生命周期 | [app-reverse-global-map.md](./app-reverse-global-map.md) | 前置地图 |
| App 协议准入（空壳诊断） | [protocol-admission-four-gates.md](./protocol-admission-four-gates.md) | 先过四关再重建客户端 |
| 真机刷机与身份门 | [app-reverse-environment-setup.md](./app-reverse-environment-setup.md)、Pixel 6 刷机文档 | 只要求干净首次开机，不重复刷机步骤 |

完成门槛也要分开写：

| 门槛 | 含义 | 不够格的证据 |
|------|------|----------------|
| `localReproduced` | 本地能按算法生成与 HAR 对齐的参数 | 脚本不报错、字段看起来像 |
| `serverAccepted` | 独立 TLS 会话拿到业务 readback | HTTP 200、空壳 JSON、挑战页 |
| `registrationComplete` | 干净设备能走完注册与后续低权限读接口 | 只重放了注册包里的一条 |
| `sessionConsistent` | 后续业务包的上下文、事件和身份来自同一套 SDK 状态 | 手写了一条业务 URL |

HTTP 200 不构成完成。注册成功也不等于后面所有接口都能当采集入口。

## 总流程

```text
干净首次开机 + 透明抓包
        ↓
HAR 语料入库（可对照、可回放）
        ↓
算法拆分 → algorithms/
        ↓
拦截器重建 → interceptors/ + apis/
        ↓
多环境指纹对照 → 字段语义与生成规则
        ↓
注册完备性（传输指纹 / 发送顺序 / SDK 状态机）
        ↓
业务请求的上下文链
        ↓
会话生命周期与成本节奏
```

AI 适合做机械整理：HAR 接口清单、Java interceptor 对照、字段表、骨架代码。人要守三件事：语料是不是干净首次注册、指纹是不是被 VPN / 模拟器污染、验收是不是业务 readback。没有这三件事，后面的目录再整齐也只是一份能编译的猜测。

下面七个阶段按依赖排列。前一阶段的产物是后一阶段的输入，不要并行「先写采集器再补算法」。

## 1. 干净首次注册与 HAR 语料

设备注册协议对「这是不是一台刚出生的设备」敏感。分析样本如果混了旧 `ANDROID_ID`、旧广告 ID、旧 SDK 目录或上一次注册残留，后续所有对照都会被污染。

### 1.1 刷到可复现的首次开机

目标是 **第一次设备注册**，不是「这台手机还能再装一次 App」。

推荐路径：

1. 用可脚本化的 Pixel 刷机流程把设备打回已知 ROM。公开起点是 [LunFengChen/auto-flash](https://github.com/LunFengChen/auto-flash)；本环境的 Pixel 6 身份门与定制包验收仍以刷机文档和 `pixel6-control` 为准，二者不要混成一套命令。
2. 刷机后只装分析所需的证书、抓包组件和目标 APK，不要先登录日常账号、不要先连会改 TLS 的系统代理。
3. 每次对照实验尽量回到同一基线：同一 ROM 版本、同一 APK 版本、同一「未注册」状态。要对比变量时，一次只改一类：ROM、APK、网络、SIM、出口。

模拟器可以做 Java 层侦察，不适合当注册语料的主样本。设备指纹、TEE、蜂窝、传感器和首次开机状态在模拟器上通常不可信。

### 1.2 抓包平面

抓包要同时满足「包全」和「环境干净」：

| 要求 | 做法 | 常见失败 |
|------|------|----------|
| 明文可见 | 用户 CA 或系统信任链生效，Pinning 已在分析环境解除 | 只看到 CONNECT |
| 时序完整 | 从进程冷启动记到注册结束，不要中途开关代理 | 缺引导包、缺延迟上报 |
| 环境不被污染 | **透明 / 无痕代理**，不要让设备感知到 VPN 或系统 HTTP proxy | 后续生成的指纹全是 VPN 环境 |
| 可对照 | 导出 HAR，按实验条件命名后归档 | 只留一份「大概能看」的抓包 |

VPN 出口、系统级 HTTP proxy、抓包 App 自己的 VPN 服务，都会写进网络指纹、接口列表、甚至 Java 层的代理检测字段。分析阶段一旦把这些字段当成正常设备的值，协议客户端会把「天然风控环境」固化进生成器。

### 1.3 HAR 语料合同

后续要对比多份 HAR，所以第一份就不能当一次性草稿纸。建议按实验维度归档，而不是按日期随便起名：

```text
evidence/har/
  <date>-<rom>-<apk>-<net>-<sim>-<runId>/
    capture.har
    manifest.json
    notes.md
```

`manifest.json` 只记可公开的实验维度：ROM 版本、APK 版本与 SHA-256、是否插卡、Wi-Fi / 蜂窝、是否首次开机、抓包工具、代理类型（透明 / VPN / 系统 proxy）。Cookie、token、设备标识、出口 IP 原值不进知识库，也不进共享 evidence。

一份注册 HAR 至少要能回答：

1. 冷启动后按时间排序的全部请求，而不是「看起来像注册」的那几条。
2. 哪些包在拿到 `deviceId` / install token 之前，哪些必须在之后。
3. 哪些是同步阻塞，哪些是延迟批量上报。
4. 业务包与埋点包是否混在同一条时间线上。

只抓一条注册成功的「主包」，后面一定会漏引导、漏 ACK、漏延迟日志。

## 2. 参数算法拆分

这一阶段的产品不是采集器，而是 **每个核心参数一份可单测的算法模块**。

### 2.1 先整理接口，再还原算法

把注册 HAR 和若干业务 HAR 交给分析流程时，输出应先是表，而不是脚本：

| 列 | 作用 |
|----|------|
| path / method | 接口身份 |
| 出现阶段 | 冷启动 / 注册 / 登录后 / 延迟上报 |
| 公共头 | 所有包都有的签名、设备、会话头 |
| 接口特有参数 | 只在该 path 出现的字段 |
| 编码形态 | hex / Base64 / protobuf / 自定义拼接 |
| 稳定还是一次一变 | 对照多份 HAR 才能下结论 |
| 依赖前置密文 | 是否先要 token、did、session key |

表稳定之后，才按参数拆算法。一个参数一个文件，禁止把签名、对称加密、编码和指纹打包进同一个 `utils.py`。

```text
algorithms/
  sign.py          # 主签名：canonical 字段、摘要、输出编码
  sign3.py         # 第二层签名或校验头
  did.py           # 设备标识派生
  fp_cipher.py     # 指纹明文 ↔ 上报密文
  body_codec.py    # body 压缩 / 填充 / 自定义编码
```

每个文件只回答四件事：明文输入是什么、字节怎么拼、用哪组密钥或派生规则、输出编码是什么。密钥来源、IV、salt、证书摘要必须写成命名输入，不要在模块里写死一份抓包值。

### 2.2 验收

算法模块的验收是 **样本对拍**，不是「请求发出去了」：

1. 从 HAR 抽出一组已知明文 / 密文对，脱敏后做 fixture。
2. 同一参数至少覆盖两条独立 HAR，避免把一次请求的随机量写成常量。
3. 编码、填充、字段顺序、空值是否参与摘要，都要单独测。
4. Native 层算法在 Java 层对不齐时，用 garlic / jadx 对到 JNI，再用 rizin 或 trace 收口；不要用「先 Hook 出参、以后再补」当完成。

这一阶段结束，手里应该有全套可复用的加解密与编码脚本。还没有协议客户端。

## 3. 拦截器式协议客户端

App 几乎不会在每个 Activity 里手写签名。公共参数是 OkHttp / 自研 HTTP 栈上的 interceptor 链：先补公共头，再拼前置密文，再算 sig，再算第二层校验，最后才发送。Python 侧应按同一机制写，而不是给每个 path 复制一份签名函数。

### 3.1 为什么不用「一函数一接口」

按接口堆函数的短期速度更快，但下一周加一条业务 API 时，公共头、签名、密文拼接会分叉。拦截器把「请求在出站前被改了什么」从业务 path 里抽出来，后面加 API 只声明 path、方法、body 和它依赖哪几条 interceptor。

典型短视频 / 社交 SDK 会拆成多层，例如 `sign`、`sign3`、设备头、会话头、body 加密。名字随目标变化，结构不变：

```text
Request
  → DeviceHeaderInterceptor
  → SessionInterceptor        # 依赖已注册的 did / token
  → BodyCipherInterceptor
  → SignInterceptor
  → Sign3Interceptor
  → Transport
```

分析入口是 garlic / jadx 里的 `addInterceptor` / `intercept(`，再对照 HAR 看每层实际写入了哪些头和 query。不要只按抓包猜测拼接顺序。

### 3.2 目录合同

```text
interceptors/
  device_header.py    # 设备与应用身份头
  session.py          # 注册后才有的 did / token / 会话字段
  body_cipher.py      # 前置密文、压缩、填充
  sign.py             # 调用 algorithms/sign.py
  sign3.py            # 调用 algorithms/sign3.py
  chain.py            # 显式声明默认链与可选链

apis/
  device_register.py
  log_config.py
  event_batch.py
  feed_list.py
  ...
```

每个 API 文件写清四件事：

1. path、method、Content-Type。
2. 走哪条 interceptor 链；有的埋点包不走业务签名，有的业务包不走日志加密。
3. 哪些字段来自 SDK 状态，哪些来自调用方。
4. 这个接口在真实 App 里的职责，以及它依赖的前置接口。

`apis/` 不实现算法。`interceptors/` 不写业务 path。`algorithms/` 不发请求。三层一旦混写，后面就无法单测，也无法把新接口安全加进去。

### 3.3 业务包要故意抓多

注册 HAR 只够还原注册链。interceptor 的完整行为要靠业务包对照：列表、详情、搜索、评论、上传、设置页，以及用户在界面上「乱点」触发的包。包少时，AI 很容易把某条业务链上的特例写成公共 interceptor。

这一阶段结束，代码应足够清晰：加新 API 等于加一个声明文件，而不是改签名实现。

## 4. 指纹语义

算法能加密一段指纹，不等于知道这段指纹该长什么样。注册失败或低权限接口异常，多数不是签名写错，而是指纹字段语义没闭合。

### 4.1 多环境对照，不要只看一份密文

重复「刷机 → 首次注册 → 导出 HAR」，并系统改变变量：

| 变量 | 为什么要切 | 期望看到的差异 |
|------|------------|----------------|
| ROM / 系统版本 | `os.version`、build fingerprint、安全补丁 | 系统字段变，应用字段相对稳 |
| APK 版本 | 采集项增减、编码版本、灰度字段 | 新增键、字段长度、版本枚举 |
| Wi-Fi / 蜂窝 | 网络类型、接口名、MCC/MNC、代理标记 | 网络簇变化 |
| 插卡 / 不插卡 | IMSI、运营商、蜂窝能力 | 空值与真实值的合法形态 |
| 出口 IP / 地区 | 时区、语言、IP 侧风控，不是设备字段本身 | 设备簇应保持稳定 |
| 有无 VPN / 系统 proxy | 污染对照 | 这些样本只当负例，不进生成器 |

对照方法是：用第 2 阶段已经还原的加解密，把多份指纹解成同一张字段表，再按「谁随 ROM 变、谁随 APK 变、谁随网络变、谁必须稳定」聚类。稳定簇才是设备身份，变化簇才是环境描述。不要把一次抓包里的全部字节当成必须复刻的常量。

### 4.2 静动态证据一起收

字段表只说明「这个键会变」。语义要靠代码：

1. Java 层：garlic / jadx 追采集器、provider、缓存文件和上报前的 merge。
2. Native 层：rizin 看 JNI 导出、字符串和结构体；必要时再加 trace，而不是一上来全量 dump。
3. 运行时：Frida / 明文 Hook 只用来验证「这个 Java 字段是否真的写进了上报明文」，不替代静态语义。

VPN 污染、模拟器特征、调试构建、Xposed / Frida 自身痕迹，都要在字段表里单独标成「分析环境伪影」。生成规则不得复用这些伪影。

### 4.3 真实指纹语料

规则写到能注册、低权限读接口能返回业务数据，就可以停一轮。若仍失败，优先怀疑指纹，而不是再改签名。

补语料的两条路都可以用，而且通常都要迭代，不必一次写完美：

| 路径 | 适用 | 风险 |
|------|------|------|
| 最小采集 demo | 只要若干 provider 的合法取值 | 自己实现的采集项容易漏、容易写错空值 |
| 重打包或 Hook 原 App，把明文指纹送到本机接收端 | 要原汁原味的字段集合 | 重打包被完整性校验；Hook 被检测；样本仍要脱敏 |

目标是几十到上百套 **真实设备** 的字段对照，不是再造一套随机生成器。逐字段看：哪些必须与硬件一致，哪些允许同类设备复用，哪些其实是安装后生成的持久量，哪些每次冷启动都会变。

这一阶段结束的最低标准：干净设备能注册，后续低权限接口能拿到业务数据。更高标准是字段语义表可解释，而不是「这组值碰巧能过」。

## 5. 注册完备性

签名和指纹对齐之后，还要处理传输层和时序。很多目标在 HTTP 参数过了之后，仍会看客户端是不是「像那套 SDK」。

### 5.1 传输指纹

Python `requests` 默认是 urllib3 + 系统 OpenSSL，和 App 里的 OkHttp / Cronet / 自研栈不是同一条 TLS 指纹。是否被校验，只能用证据回答，不能先验假设「他们不看」。

一个可复现的取证办法：

1. 在本机起一个只解析 ClientHello 的接收端，记录 JA3 / JA4 / ALPN / 套件顺序等可见字段。
2. 用与目标 App 相同大版本的 OkHttp（或它实际使用的引擎）发一条探测，得到真实传输指纹。
3. 协议客户端选用能复现该指纹的 HTTP/TLS 栈；不要先用 `requests` 把业务跑通，再回头补指纹。

还要单独检查：

- Native 层是否另有一条 socket，不走 OkHttp。
- WebView / 内置浏览器是否在注册或风控流程里贡献了另一组 TLS / HTTP/2 指纹。
- HTTP/2 设置帧、UA、头部顺序是否也被当成传输身份。

传输指纹通过，只说明 ClientHello 像；不说明应用层注册已完成。

### 5.2 发送顺序：三层保真，不要停在第一层

注册不是单请求。包与包之间有数据依赖，也有并行。下面三层都能「看起来在发注册包」，完备性差一整档。

#### 方案 A：按一份 HAR 的时间线重放

做法：打开抓包，按时间把包依次发完。

问题：

1. 这一份 HAR 的顺序不一定是 SDK 的唯一合法顺序，只是这一次调度的结果。
2. 单次注册、单一网络、单一 ROM，事件集合往往偏窄。
3. 延迟上报、失败重试、前后台切换，在一次干净抓包里经常看不到。

它适合当 **对照时间线**，不适合当实现。

#### 方案 B：按模块依赖做成 DAG

静态上看，SDK 通常是多模块、多线程：配置拉取、设备注册、日志通道、指纹上报各走各的。某些包必须等前面模块返回 `deviceId` / token / 密钥后才能继续，其余包可以并行。

做法：从代码还原「谁等谁」，实现成有向依赖，而不是线性脚本。

这层对多数目标已经够用。剩余风险是：它仍可能漏掉代码里存在、但这次 HAR 没出现的事件；它也不保证调度时间、批量窗口和真实 App 一致。

#### 方案 C：把 SDK 状态机移植成 Python 类

埋点与日志往往不是「调用业务 API 时顺便发一条」。它们有自己的初始化、缓冲、阈值、前后台和定时器。更稳的做法是继续逆向事件 SDK，把它的公开生命周期做成与 Java 接近的调用面：

```text
sdk.init(app_context)
sdk.register()          # 设备注册，写回 did / token
sdk.fp_collect()        # 指纹动态采集与上报
sdk.on_foreground()
sdk.track(event)
sdk.flush()
```

Python 调用方式和 Java 接近，事件何时进缓冲、何时批量发出、哪些条件才会上报，都留在 SDK 内部。延迟上报、满足 N 条才 flush、某个字段为空就跳过，都应从代码证据扣进状态机，而不是在采集脚本里 `sleep` 凑时序。

方案 C 成本最高。只有注册完备性已经成为阻塞，且方案 B 的遗漏已经有证据时才升级。不要为了「看起来更像」先移植四百个日志包。

### 5.3 怎么选

```text
先用多份注册 HAR 列事件集合
        ↓
用代码证明依赖边 → 方案 B
        ↓
仍有「HAR 里没有、代码里会发」的事件
        ↓
只把这条事件链升级到方案 C
```

不要把整套日志 SDK 一次性搬完。每升一层，都要用「干净设备注册 + 低权限读接口」重新验收。

## 6. 业务请求的上下文链

注册完成之后，业务包仍可能带上一跳上下文：上一条内容的 id、搜索词、来源页、会话内的位置、推荐参数。只复刻 path 和签名、把上下文留空或复制注册 HAR 里的旧值，是另一类失败。

分析时至少问三句：

1. 真实用户要看到这条内容，中间会经过哪些接口？
2. 当前包里哪些字段明显引用了上一跳（列表 id、搜索词、refer、session cursor）？
3. 这些字段是 interceptor 自动带的，还是业务层写入的？

上下文链没有通用公式。原则只有一条：业务 API 的入参必须来自 SDK 状态和上一跳响应，不能来自分析者脑子里的「这个接口应该长这样」。缺证据就标 `insufficient-evidence`，不要用空字符串或随机数填满。

## 7. 会话生命周期与成本节奏

前面各层足够完整之后，才谈会话怎么用。这一层最容易被写成运营手册；知识库只保留协议侧约束。

### 7.1 会话要像使用，而不是像定时器

SDK 里的事件、昼夜、前后台、版本灰度，都会变成上报字段或接口组合。协议客户端如果用固定间隔刷同一条业务路径、从不进入详情、从不触发 SDK 自己的空闲 / 后台逻辑，等于在应用层自报「这不是交互会话」。

需要从代码和 HAR 确认的是机制，不是某个站点的操作清单：

- 哪些事件由页面停留、滚动、失败重试触发，而不是由采集循环触发。
- 哪些接口在夜间、后台、弱网下本来就不会打。
- 应用版本、渠道、灰度开关是否会改变 interceptor 链或指纹版本。

### 7.2 节奏是身份摊销，不是 QPS

一台刚注册的设备如果立刻承担全部业务并发，失败通常不能归因成「签名又飘了」。更常见的是：设备身份、出口和指纹数量不够，单设备被摊到了不该由它承担的请求密度。

反过来也对：为了让一个低权限读接口「更像真机」，补了几百条注册期日志，而每条业务数据的价值低于这些包消耗的代理与账号成本，这条链路在工程上就不成立。协议可以继续完善，但不应把完善本身当成必须交货的采集方案。

小样本过一天，说明不了策略。很多识别只在量级上去之后才稳定出现。能登记的结论是「当前规则在这一批身份上还没被打掉」，不是「明天还能跑」。

并发、Sticky 出口、429 / 403 分层和 checkpoint，走采集控制面，不在本文展开。

## 目录合同与验收

项目内建议固定成下面这棵树。路径落在对应 workspace，HAR 与真实指纹原件不进 Git。

```text
workspace/<project>/
  evidence/har/<run>/     # 多环境 HAR + manifest
  algorithms/             # 一参数一文件，只做编解码
  interceptors/           # 公共头、签名、前置密文、链
  apis/                   # path / 方法 / 链声明 / 职责
  sdk/                    # init / register / fp_collect / track
  fixtures/               # 脱敏后的明文密文对
```

阶段门：

| 阶段 | 必须留下的产物 | 通过条件 |
|------|----------------|----------|
| HAR 语料 | 至少一份干净首次注册 HAR，外加若干业务 HAR | 冷启动到注册结束的时间线完整，代理类型写明 |
| 算法 | `algorithms/` + fixture | 多 HAR 对拍通过，编码 / 空值 / 字段顺序单测过 |
| 拦截器 | `interceptors/` + `apis/` | 新 API 不必改签名实现；链与 Java interceptor 能对上 |
| 指纹 | 字段语义表 + 生成规则 | 干净设备可注册；低权限读接口有业务 readback |
| 注册完备 | 传输指纹记录 + 依赖 DAG 或 SDK 状态机 | 顺序来自代码依赖，不是单份 HAR 抄写 |
| 业务上下文 | 参数谱系里写清上一跳来源 | 上下文字段有 HAR 或代码证据 |
| 节奏 | 只写身份数量、出口与成本边界 | 不把单设备高并发写成已完成 |

## 速查

| 问题 | 先看 |
|------|------|
| 注册包签名对不上 | `algorithms/` 对拍，再看 interceptor 拼字段顺序 |
| 能签但不能注册 | 指纹语义、首次开机状态、VPN / 代理污染 |
| 能注册但读接口空 | 缺引导包、缺 did 依赖、上下文链为空 |
| `requests` 能发但不能用 | 传输指纹、HTTP/2、Native / WebView 旁路 |
| 按 HAR 顺序重放仍飘 | 升级到模块 DAG；仍漏事件再移植 SDK 状态机 |
| 小流量正常、放量后死 | 身份与出口数量，而不是再补一条签名 |
| 为读接口补了大量日志包 | 先算成本；不值得就停在方案 B |

全局地图解决「请求从哪一层被改」。本文解决「改完之后，如何收成一套能维护的 Python SDK」。能维护的标志不是接口数量，而是算法、拦截器、指纹和状态机四层不再互相污染。
