## 一、功能目标

在 ROM 内部（不借助 Frida）实现三类 JNI 可观测能力：

| 能力                     | 触发时机                             | 开关属性                              |
| ---------------------- | -------------------------------- | --------------------------------- |
| so 加载记录（dlopen）        | app 每次加载 .so                     | `persist.rommgr.dlopen_log`       |
| RegisterNatives 动态绑定记录 | app 调用 `JNIEnv->RegisterNatives` | `persist.rommgr.register_natives` |
| Implicit JNI 绑定记录      | ART 按命名规则（`Java_包名_方法名`）自动解析     | 同上                                |
| native 偏移即时查询          | 用户在 ROMManager 输入类名+方法名触发        | `persist.rommgr.query_native`     |

所有结果均以 JSON 打到 logcat `xf-rom` tag，ROMManager UI 实时展示。

## 三、各插装点实现细节

### 3.1 bionic dlopen — `bionic/linker/linker.cpp`

插装位置：`do_dlopen()` 函数成功返回前（`handle != nullptr` 分支）。

```cpp
// xf: dlopen 监控 —— 仅 app 进程（uid ≥ 10000），由 persist.rommgr.dlopen_log 控制
if (getuid() >= 10000) {
    char prop[PROP_VALUE_MAX] = {};
    __system_property_get("persist.rommgr.dlopen_log", prop);
    if (prop[0] == '1') {
        __android_log_print(ANDROID_LOG_INFO, "xf-rom",
            "{\"event\":\"dlopen\",\"so\":\"%s\",\"pid\":%d}", name, getpid());
    }
}
```

**头文件限制**：`linker.cpp` 处于 bionic bootstrap 阶段，不能 `#include <android/log.h>`。  
解法：linker 的 `Android.bp` defaults 已含 `-llog`，直接用 `__android_log_print` 弱引用符号即可，linker64 自身符号表已包含该符号。

### 3.2 ART RegisterNatives — `art/runtime/jni/jni_internal.cc`

插装位置：`RegisterNativeMethods()` 函数体，遍历每个 `JNINativeMethod` 条目。

每条记录：

- `class`：点分类名（`com.example.Foo`）
- `method` + `signature`：JNINativeMethod 的 name + signature 字段
- `so`：用 `dladdr(fnPtr, &di)` 反查 `di.dli_fname`
- `offset`：`fnPtr - di.dli_fbase`（so 内偏移）

host build guard：改动全部包在 `#ifdef ART_TARGET_ANDROID` 内，host 构建跳过，不影响 ART host tests。

### 3.3 ART ImplicitNative — `art/runtime/jni/java_vm_ext.cc`

插装位置：`FindNativeMethodInternal()` 找到符号后（`dlsym` 返回非 null 分支）。

输出：

```json
{"event":"ImplicitNative","symbol":"Java_com_Foo_bar","so":"/data/app/.../libfoo.so","offset":"0x17f8"}
```

偏移同样通过 `dladdr()` 计算。与 RegisterNatives 共用同一开关 `persist.rommgr.register_natives`。

### 3.4 query_native 即时查询 — `art/runtime/jni/java_vm_ext.cc`

**背景**：早期方案是"等下一次 RegisterNatives 命中才回报"，如果目标 app 启动时已完成所有绑定、后续不再调用，query 就永远等不到结果。

**最终方案**：ART 启动时在 `JavaVMExt::Create()` 里起一个后台 poll thread（`XfQueryNativePollThread`），每 300 ms 读一次 `persist.rommgr.query_native`。非空时解析 `类名#方法名[#签名]`，立即通过 `ClassLinker::VisitClasses` 遍历所有已加载 class，找到目标类后枚举其 native ArtMethod，调 `ArtMethod::GetEntryPointFromJni()` + `dladdr()` 解析 so + 偏移，打 `QueryNativeResult` 事件，清空 prop。

响应时间：< 300 ms（poll 间隔），无需触发任何方法调用。

```
setprop persist.rommgr.query_native "com.android.inputmethod.latin.BinaryDictionary#openNative"
# → logcat: {"event":"QueryNativeResult","class":"...BinaryDictionary","method":"openNative",
#             "signature":"(...)Z","so":"libjni_latinime.so","offset":"0x6c170"}
```

ROMManager `NativeQueryPage.java` 对应改为轮询 `logcat -s xf-rom:I` 匹配 `QueryNativeResult`，超时 5 s（原 10 s，ClassLinker 路径通常 < 300 ms 可响应）。

## 四、sepolicy（4 轮踩坑后定型）

**目标**：ROMManager（`priv_app`/`platform_app`）可写 `persist.rommgr.*`；三方 app（`appdomain`）可读；system/vendor 进程不受干扰。

### 最终配置

```
# public/property.te
system_restricted_prop(rommgr_prop)

# private/property_contexts
persist.rommgr.    u:object_r:rommgr_prop:s0

# private/property.te（neverallow 豁免列表）
neverallow { ... -rommgr_prop } ...;   # core_property_type 豁免

# private/shell.te
set_prop(shell, rommgr_prop)

# private/zygote.te
get_prop(zygote, rommgr_prop)

# private/app.te
get_prop(appdomain, rommgr_prop)
```

**以上全部同步 `prebuilts/api/33.0/`**（REL 版冻结快照），否则 `sepolicy_freeze_test` 必挂。

### 踩坑过程

| 轮次    | 错误做法                                                          | 现象                                     | 根因                                                                                                   |
| ----- | ------------------------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 1     | 放进 `not_compatible_property()` 块                              | `unknown type rommgr_prop` 编译失败        | M4 宏展开该块时上下文为空，类型还未定义                                                                                |
| 2     | 漏掉 `core_property_type` neverallow 豁免                         | `sepolicy_freeze_test` 报 neverallow 违反 | `rommgr_prop` 被 core_property 规则兜底覆盖                                                                 |
| 3     | 用 `system_public_prop`                                        | Treble compat 28～32 测试失败               | public prop 在旧版 compat 策略里有额外约束                                                                      |
| 4     | 用 `system_internal_prop`                                      | app 进程读 prop 被 SELinux 拒绝，插装永远拿到 false | internal 宏包含 `neverallow { domain -coredomain } file no_rw_file_perms`，`untrusted_app` 不是 coredomain |
| **✅** | `system_restricted_prop` + `get_prop(appdomain, rommgr_prop)` | 全部测试通过，app 可读                          | restricted 只限制 set，不限制 file read                                                                     |

### 验证命令

```bash
# 编译
m -j8 sepolicy_tests treble_sepolicy_tests sepolicy_freeze_test
# 期望：neverallows 0，treble 28~32 全 PASS，freeze PASS
```

## 五、uid ≥ 10000 守卫（关键 bug fix）

**问题**：bionic linker 和 libart 在系统所有进程中运行（system_server、各 vendor HAL 等）。未加守卫时直接读 prop，导致这些进程尝试访问 `rommgr_prop`，SELinux 拦截后产生大量 AVC denial——实测 931 条（主要来自 `hal_drm_widevine`、`hal_audio_default`、`vold` 等）。

**修法**：三处插装（bionic linker、jni_internal、java_vm_ext）均在读 prop 之前加：

```cpp
if (getuid() < 10000) return;   // 只对 app 进程（uid ≥ 10000）激活
```

修复后重刷，`adb shell dmesg | grep avc | grep rommgr` 输出为空，零 AVC。
