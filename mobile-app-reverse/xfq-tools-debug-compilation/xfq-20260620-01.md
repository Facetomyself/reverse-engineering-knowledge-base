## 一、功能目标

在 ROM 内部实现一个 Java 层算法采集能力，用于逆向分析 App 的加解密、签名、编码、压缩和参数来源，不依赖 Frida。

| 能力 | 触发时机 | 产物 |
|------|----------|------|
| JCA/JCE 算法采集 | 目标 App 调用 Cipher/Mac/MessageDigest/Signature/KeyFactory 等 Java API | `xf.crypto` logcat + `/data/misc/rommgr/<pkg>/crypto.jsonl` |
| 参数来源追踪 | 构造 IV/GCM/OAEP/PBE/PSS/EC 等 Spec 或 AlgorithmParameters/KeyStore | `mode=param` 事件 |
| 编码/压缩采集 | Base64、URLCodec、Deflater/Inflater、部分平台 Protobuf/第三方编码类 | `mode=encode/decode/zip/unzip` 事件 |
| ROMManager 日志页 | 用户在 App 详情里打开“查看加解密记录” | 固定包名日志列表、搜索、统计、展开详情、字段复制、导出 |
| 覆盖测试 APK | 手动安装 `com.xf.cryptohooktest` 后触发各类算法 | PASS/FAIL logcat + `crypto.jsonl` 覆盖验证 |

核心要求：

1. **按 App opt-in**：不开目标 App 的 `java_trace` 不采集。
2. **按算法范围 opt-in**：只开主开关但没开算法按钮时不落算法数据。
3. **运行时可读**：logcat 用长分隔块便于人工看，文件保留完整 JSON 便于 UI/脚本分析。
4. **UI 类似算法助手**：列表先折叠，只显示关键摘要；点进去再看 key/iv/aad/in/out/callstacks 等详情。
5. **测试 APK 不内置**：`XfCryptoHookTest` 只作为普通 `/data/app` 安装验证，不进入 system image。

## 三、整体数据流

```text
ROMManager AppDetail
  ├─ Java Crypto Hook 主开关
  │    persist.rommgr.app.<pkg>.java_trace = 1/0
  └─ AlgoHookPage 算法范围开关
       persist.rommgr.app.<pkg>.hook_* = 1/0

目标 App 进程（uid >= 10000）
  └─ bootclasspath/libcore hook 点
       ├─ 先走 XfCryptoHook.appTraceMaybeEnabled() 轻量预门禁
       ├─ 再按 cls/alg/mode 路由到 hook_* 范围
       ├─ 通过后延迟采集 callstacks
       └─ 输出：logcat xf.crypto + /data/misc/rommgr/<pkg>/crypto.jsonl

ROMManager CryptoLogPage
  └─ tail crypto.jsonl 最近窗口
       ├─ parse JSON
       ├─ 搜索/统计
       ├─ 折叠卡片摘要
       └─ 展开 key/iv/aad/in/out/params/callstacks 详情
```

## 四、开关模型

### 4.1 主开关

```text
persist.rommgr.app.<pkg>.java_trace
```

主开关为 `1` 时，目标 App 才允许进入 Java 算法采集逻辑。

### 4.2 算法范围开关

| prop key | UI 含义 | 说明 |
|----------|---------|------|
| `hook_cipher` | 全部对称/未知 Cipher | 对 Cipher 类兜底 |
| `hook_aes` | AES | AES/GCM/CBC/CTR/Wrap 等 |
| `hook_des` | DES/3DES | DES、DESede |
| `hook_sm4` | SM4 | Provider 支持或测试 provider 场景 |
| `hook_asym` | 非对称/密钥协商总开关 | asymmetric 兜底；UI 应理解为 RSA/EC/DH/XDH 等大类总开关 |
| `hook_rsa` | RSA/EC/DH/XDH | 历史 key 名叫 rsa，但实际覆盖 RSA、EC、DH、XDH、X25519、X448 等 |
| `hook_sig` | 签名/验签 | Signature.sign/verify，含 RSA/ECDSA/Ed25519 等 |
| `hook_hash` / `hook_sha` | Hash | MessageDigest；`hook_sha` 是兼容旧 key |
| `hook_hmac` | HMAC | Mac.doFinal |
| `hook_keygen` | KeyGen | SecretKeySpec、KeyGenerator、KeyPairGenerator |
| `hook_keyderive` | KDF/Agreement/KeyFactory | PBKDF、KeyAgreement、KeyFactory |
| `hook_random` | SecureRandom | seed、nextBytes、generateSeed |
| `hook_params` | 参数来源 | IV/GCM/OAEP/PBE/PSS/EC/KeyStore/AlgorithmParameters |
| `hook_encoding` | 编码/序列化总开关 | Base64、URLCodec、Protobuf 等兜底 |
| `hook_b64` / `hook_b64_java` / `hook_b64_android` | Base64 | Java/Android Base64 |
| `hook_hex` | Hex | bouncycastle Hex 等 |
| `hook_urlcodec` | URLCodec | URLEncoder/URLDecoder |
| `hook_protobuf` | Protobuf | 平台 protobuf lite |
| `hook_compress` | 压缩/解压总开关 | 压缩类兜底 |
| `hook_zip` | Deflate/GZip/Zip 等 | Deflater/Inflater 以及上层 zip/gzip 间接路径 |

> 命名债：`hook_rsa` 是历史遗留 key，实际已经扩成 RSA/EC/DH/XDH；为兼容已写入的 prop 不建议随便改 key，UI 文案应表达为“RSA/EC/DH/XDH”。

## 五、`XfCryptoHook` 核心设计

### 5.1 两级门禁

热路径不能一进来就读 `/proc`、打日志或采栈，否则容易影响 zygote/system_server/早期 app 初始化。

因此分两级：

1. `appTraceMaybeEnabled()`：轻量预门禁，只做 uid/package/prop 快速判断。
2. `emit()`：最终门禁，确认 app、主开关、算法范围、过滤条件后才生成日志。

```java
if (!XfCryptoHook.appTraceMaybeEnabled()) return;
// 采集必要参数后
XfCryptoHook.emit(cls, method, alg, mode, key, iv, in, out, extra, null);
```

`callstacks` 不在各 hook 点提前采集，而是在 `emit()` 确认会输出后再采，避免无效开销。

### 5.2 算法路由

`algKey(alg, cls)` 先看 class，再看算法名：

- class 更精确：`SecretKeySpec` 必须归 `hook_keygen`，不能因为算法名是 AES 就被 `hook_aes` 接管。
- 参数类统一归 `hook_params`。
- Signature 类优先归 `hook_sig`，避免 `SHA256withRSA` 被误判为 hash。
- 未识别 Cipher 使用 `hook_cipher`/`hook_unknown` 兜底。

### 5.3 JSON 字段

`crypto.jsonl` 一行一个事件，核心字段：

```text
ts, id, pkg, cls, method, alg, mode,
key, iv, aad, in, out, tagLen,
callstacks,
额外参数字段（paramKind/sourceClass/provider/format/specClass/...）
```

`mode` 取值：

```text
encrypt / decrypt / wrap / unwrap
hash / mac / sign / verify
keygen / keyderive / random / param
encode / decode / zip / unzip
```

### 5.4 logcat 展示

logcat 用 `xf.crypto`，每条事件一块：

```text
============================== #15 -> decrypt | AES/GCM/NoPadding | Cipher.doFinal ==============================
  key(32B)       : ...
  iv(12B)        : ...
  aad            : ...
  in(60B) hex    : ...
  out(44B) hex   : ...
  out(44B) b64   : ...
  callstacks     : ...
============================== #15 <- decrypt | AES/GCM/NoPadding | Cipher.doFinal ==============================
```

文件里写完整 JSON；logcat 保持人工可读。

## 六、各类 Hook 点说明

### 6.1 Cipher

覆盖：

- `doFinal()` encrypt/decrypt
- `updateAAD()` AAD 累积
- `wrap()` / `unwrap()`
- GCM tagLen、IV、key material、输入/输出

重点：

- GCM 的 AAD 不在 `doFinal()` 参数里，需要从 `updateAAD()` 累积。
- wrap/unwrap 要记录 wrapping key 和被包裹 key；只有 `getEncoded()` 可导出时记录 key material，否则标记不可导出。

### 6.2 Hash / Mac / Signature

- `MessageDigest.digest()`：记录 input/output。
- `Mac.doFinal()`：记录 key/input/output。
- `Signature.sign()` / `verify()`：记录 key/input/signature 或 verify result。

注意：`SHA256withRSA` 这类名称包含 SHA，但语义是 Signature，路由时必须先匹配签名。

### 6.3 KeyGen / KDF / Agreement / KeyFactory

- `SecretKeySpec`：记录原始 key 来源。
- `KeyGenerator` / `KeyPairGenerator`：记录生成结果（可导出时）。
- `SecretKeyFactory`：PBKDF 等派生结果。
- `KeyAgreement`：ECDH/XDH shared secret。
- `KeyFactory`：`generatePublic/generatePrivate/getKeySpec/translateKey` 的输入输出类型和 encoded material。

### 6.4 参数来源

`mode=param`，用于回答“IV、GCM tag、OAEP/PSS 参数、曲线名、KeyStore alias 是哪里来的”。

典型字段：

```text
paramKind, sourceClass, provider, format, specClass,
alias, storeType, keyClass, keyAlg, keyFormat, entryClass, exportable,
tagLen, offset, len, passwordLen, hasSalt, iterationCount, keyLength
```

PBE password 默认不记录明文，只记录长度和派生参数。

### 6.5 编码、序列化、压缩

- Base64：Java/Android/BouncyCastle 平台类。
- URLCodec：`URLEncoder` / `URLDecoder`。
- Protobuf：平台 protobuf lite 的 `toByteArray` / parse 路径。
- Deflate/Inflate：底层 `Deflater` / `Inflater`；GZip/Zip 上层流最终会体现为 deflate/inflate 事件。

## 七、ROMManager 页面设计

### 7.1 App 详情

`AppDetailPage` 在 Java Crypto 分组里做两件事：

1. `Java Crypto Hook` 行：右侧 Switch 控制主开关，点击行进入算法范围页。
2. `查看加解密记录` 行：进入日志页，固定当前 App 包名。

### 7.2 AlgoHookPage

按用途分组，不按包名搜索：

- 对称算法
- 非对称/签名
- Hash/HMAC/KDF/随机数
- 参数来源
- 编码/序列化
- 压缩/解压

UI 文案要面向人读，内部 prop key 可以保留兼容名。例如 `hook_asym` 展示为“非对称/密钥协商总开关”。

### 7.3 CryptoLogPage

读取固定包名：

```text
/data/misc/rommgr/<pkg>/crypto.jsonl
```

行为：

- tail 最近窗口，不全量读大文件。
- 默认展示最新 100 条。
- 折叠卡片显示：mode pill、方法、算法、编号、短时间、IN/OUT/key/iv/aad/params/callstacks 摘要。
- 点击展开显示：`epoch_ms`、key/iv/aad/input/output/base64、参数来源、`callstacks`。
- 搜索范围：时间、算法、方法、mode、key/iv/aad/in/out、params、callstacks。
- 支持统计、字段长按复制、导出当前过滤结果。
- 已移除实时刷新，保留手动“加载最新”和搜索防抖。

## 十、踩坑与后续维护规则

1. **热路径先预门禁**：libcore/bootclasspath hook 必须先 `appTraceMaybeEnabled()`，不要一上来采栈/读重资源/打日志。
2. **callstacks 延迟采集**：只有确认事件会输出后才采，避免关开关时仍有高开销。
3. **prop key 尽量兼容**：`hook_rsa`、`hook_asym` 这种历史名可以通过 UI 文案修正，不要轻易改 key 破坏已写配置。
4. **测试 APK 不内置**：它只是验证工具，必须普通安装；system image 里不应出现 `XfCryptoHookTest`。
5. **product-only 刷机要同步 vbmeta**：Pixel 7 改 product 后要配套同构建的 `vbmeta_system.img` / `vbmeta.img`，否则可能 AVB 不一致。
6. **notes 只写功能最终态和关键坑**：中间救援过程、反复尝试、临时现象不要塞进功能笔记；需要时单独写 debug 记录。
